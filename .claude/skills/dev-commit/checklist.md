# 検査のチェックリスト(dev-commit / dev-push / dev-pr 共通)

機械的な検査(`scripts/lib/pr-secrets-check.ts` とフック)は、正規表現で拾えるものだけを止める。
このチェックリストは、**文脈で判断するもの**を、人の目の代わりに確認するためのもの。
履歴に載った値は消しにくい。迷ったら止めて、報告する。

## 見るもの

1. **認証情報**: アクセスキー、シークレット、トークン、パスワード、秘密鍵、接続文字列、Cookie、署名付き URL
2. **環境固有の値**: クラウドのアカウント ID、プロファイル名、ホストゾーン ID、リソース ID・ARN、バケット名、
   ユーザープールの ID・クライアント ID、配信ドメイン、独自ドメイン、IP アドレス、社内のホスト名・URL
3. **個人情報**: 氏名、メールアドレス、電話番号、住所、ローカルのユーザー名・パス(`/Users/…` など)、
   意図しないメールアドレス(作者情報にも注意。許可するのは GitHub の noreply アドレスと、Claude の署名の行(`Co-Authored-By:`)で使う noreply アドレス(完全一致だけ)のみ)
4. **組織・案件の情報**: 会社名、部署名、社内システム名、案件のコード名、顧客名、取引先名
5. **書いてはいけない名前**: `.pr-secrets-denylist`(手元専用、gitignore 済み)に書かれた語。
   社外・非公開の名称や、このリポジトリの外の事情・経緯を示す語も、
   コード・コメント・ドキュメント・commit・Issue・PR のどこにも書かない。判断に迷う語は、止めて人に確認する
6. **ログ・出力の貼り付け**: スタックトレース、コマンド出力、画面の説明に、上の値が混ざっていないか
7. **プレースホルダーの書き方**: 実値の代わりに `<プロファイル名>` や `example.com` になっているか。
   実在しそうな値(それらしい 12 桁、ランダムに見える ID)は、ダミーでも本物と区別がつかないので指摘する
8. **文体**: 出来事を語る書き方になっていないか。一般的な注意書きの形で書く

## 整合を見るもの

文書や下書きが、実装・設定・既存の文書と食い違っていないかを確認する。漏えいの確認(上の「見るもの」)とは別の観点で、同じ検査役が行う。

1. **記述と実装の一致**: 文書・コメント・スキル・下書きの記述が、コードや設定の値(既定値、コマンド名、オプション、環境変数名)と合っている
2. **参照先の実在**: 参照しているファイル、文書、節(見出し)、コマンド、スクリプト名、npm スクリプトが実在する。リンクが切れていない
3. **数値・件数・既定値**: 書かれた数値、件数、上限、既定値が、定義元と合っている
4. **他の文書との矛盾**: 同じ事柄を述べる別の文書と食い違っていない

- **初回の検査で、照合を網羅する。** 差分に書かれた数、範囲、名前、一覧、上限・既定値のすべてを、定義元と突き合わせる。
  1 か所を見つけたところで止めず、同じ語を差分の全体と、差分が参照する文書から検索して、同じ種類の箇所も確かめる。
  再検査のたびに新しい食い違いが出るのは、初回の照合が一部で止まっているため。
- 読む範囲は、差分が参照しているファイルと節だけ。参照先と定義元を確かめるために読む。無関係なファイルは読まない。
  依頼に「検索した語」が書かれているときは、その語で検索して見つかった箇所も読んでよい(`.env`、秘密鍵の類、`pipeline-work/` は、検索の対象にも読む対象にもしない)
- 重さは、漏えいは `BLOCK`、整合は `WARN` を基本にする。手順どおりに動かすと漏えいや破壊的な操作につながる食い違い
  (承認なしで push できる手順など)は `BLOCK`
- どの検査で必須か
  - commit・push: 差分に、文書(`.md`)、設定、スキル、エージェントの定義、スクリプトを含むとき
  - PR・Issue の下書き: 常に
- 報告は、漏えいと同じく、値を引用せず、場所と種類だけを書く
  - 良い例: `docs/foo.md 12 行目: 参照先の文書が存在しない(重大度: WARN)`

## 対象

- 差分の**追加行**だけでなく、ファイル名、コミットメッセージ、ブランチ名、PR・Issue のタイトルと本文も対象
- テストのフィクスチャ、ドキュメント、リリースノートも対象(利用者にも見える)
- `.env`(gitignore 済み)に置くべき値が、コードやドキュメントに書かれていないか

## 報告のしかた(必ず守る)

- **見つけた値そのものを、報告に書かない。** 報告がログや会話に残るため。場所と種類だけ書く
  - 良い例: `docs/foo.md 12 行目: アカウント ID らしき 12 桁の数字(重大度: BLOCK)`
  - 悪い例: 値を引用する
- 各指摘に、次のいずれかの重大度を付ける
  - `BLOCK`: 認証情報、環境固有の値、個人情報、拒否リストの語、書いてはいけない名前や経緯。止める
  - `WARN`: 判断が要るもの(社内名称かもしれない、実在しそうなダミー値など)と、整合の食い違い。人に見せて決めてもらう
- 最後に、全体の判定を 1 行で書く: `判定: OK` / `判定: WARN` / `判定: BLOCK`
- 確認できなかったこと(差分が大きすぎて全部は読めなかった、など)は、正直に書く。「問題なし」と断定しない
- 判定の前に、「置いた前提」を 1〜3 行で書く(依頼に書かれていなくて自分で決めたこと。読んだ範囲、仮定した事実、確かめていないこと。なければ「なし」)

## 直し方の指針

- 値は `.env` に置き、コードには環境変数名だけを書く
- 説明のために値が要るときは、プレースホルダーにする
- すでにコミット済みの値は、新しいコミットで消すだけでは履歴に残る。**push 前**なら、コミットを作り直す
  (`git reset --soft` で戻して、直して、コミットし直す)。push 後は、履歴を書き換えず、人に相談する
