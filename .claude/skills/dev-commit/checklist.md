# 検査のチェックリスト(dev-commit / dev-push / dev-pr 共通)

機械的な検査(`scripts/lib/pr-secrets-check.ts` とフック)は、正規表現で拾えるものだけを止める。
このチェックリストは、**文脈で判断するもの**を、人の目の代わりに確認するためのもの。
履歴に載った値は消しにくい。迷ったら止めて、報告する。
下の項目のうち、どれを判定の理由にし、どれを `参考:` にとどめるかは、依頼が書く検査の程度(`low`・`medium`・`high`)で決まる(定義は `inspector-rules.md` の「判定の範囲」だけに置く)。

## 見るもの

1. **認証情報**: アクセスキー、シークレット、トークン、パスワード、秘密鍵、接続文字列、Cookie、署名付き URL
2. **環境固有の値**: クラウドのアカウント ID、プロファイル名、ホストゾーン ID、リソース ID・ARN、バケット名、
   ユーザープールの ID・クライアント ID、配信ドメイン、独自ドメイン、IP アドレス、社内のホスト名・URL
3. **個人情報**: 氏名、メールアドレス、電話番号、住所、ローカルのユーザー名・パス(`/Users/…` など)、
   意図しないメールアドレス(作者情報にも注意。許可するのは GitHub の noreply アドレスと、Claude の署名の行(`Co-Authored-By:`)で使う noreply アドレス(完全一致だけ)のみ。例外として、作者が Dependabot のコミットのメッセージの署名の行(`Signed-off-by:`)にある、Dependabot のアドレスを認める)
4. **組織・案件の情報**: 会社名、部署名、社内システム名、案件のコード名、顧客名、取引先名
5. **書いてはいけない名前**: `.pr-secrets-denylist`(手元専用、gitignore 済み)に書かれた語。
   社外・非公開の名称や、このリポジトリの外の事情・経緯を示す語も、
   コード・コメント・ドキュメント・commit・Issue・PR のどこにも書かない。判断に迷う語は、止めて人に確認する
6. **ログ・出力の貼り付け**: スタックトレース、コマンド出力、画面の説明に、上の値が混ざっていないか
7. **プレースホルダーの書き方**: 実値の代わりに `<プロファイル名>` や `example.com` になっているか。
   実在しそうな値(それらしい 12 桁、ランダムに見える ID)は、ダミーでも本物と区別がつかないので指摘する。次の形は、指摘しない(形に当てはまらないものは、従来どおり指摘する)
   - コード例・例データの値: 接続先は、予約済みのドメイン(`example.com`・`example.org`・`example.net` とそのサブドメイン、`.example`・`.test`・`.invalid`・`.localhost` で終わる名前。この一覧にない名前は指摘する)。権限・グループ・役割の名前は、職能や権限を表す一般名(`admin`、`reader`、`analyst` など)。
     組織の名称として特定できる名前は、従来どおり指摘する。番号やコードは、`<番号>` の形か、`X` を並べた形(図や表の例データの番号も同じ)。
   - テストで、許可されないアドレスのダミーを組み立てる値: 存在しないトップレベルドメイン(国や地域に割り当てない 2 文字のコード。例: `.zz`)で終わるドメイン。
     予約済みでも存在しないトップレベルドメインでもないドメインで組み立てる形(`["名前", "ドメイン"].join("@")`)は、テストのファイル(`.test.*`・`.spec.*`)では機械検査が止める
     (`scripts/lib/pr-secrets-check.ts` の `isPlaceholderDomain`。組み立て方が違う形は拾えないので、従来どおり指摘する)
   - 作問パイプラインが付ける ID: 接頭辞 `f`・`d`・`p`・`e` のどれか 1 文字と `-` に、sha256 の先頭 12 文字の 16 進が続く形で、
     接頭辞の前に英数字・`-`・`_` が続かず(語頭から始まり)、作問パイプラインのデータや作業用の置き場の ID の項目として現れるもの
     (事実カード・下書き・出題計画の項目・評価データの ID。生成は、`packages/pipeline/src/facts/extract.ts` の `cardId`、`draft/schema.ts` の `draftId`、
     `draft/rewrite.ts` の書き直しの ID、`plan/plan.ts` の `planItemId`・`focusItemId`、`eval/dataset.ts` と `judge-eval/dataset.ts` の `caseId`)。
     この形に当てはまるときだけ、12 文字がたまたま数字だけになっても、アカウント ID の形としては指摘しない。
     資源名などの語のうしろに `-` でつないだ 12 桁(接頭辞が 2 文字以上の語、または上の 4 種類以外の文字)は、この例外に当たらず、従来どおり指摘する。単独の 12 桁の数字と、`account` や ARN の文脈の 12 桁は、従来どおり指摘する。
     機械検査(`scripts/lib/pr-secrets-check.ts` の「アカウント ID」)は、`account=` や ARN などの文脈つきの 12 桁だけを止め、接頭辞つきの形は止めない(`scripts/lib/pr-secrets-check.test.ts` が確かめる)
8. **文体**: 出来事を語る書き方になっていないか。一般的な注意書きの形で書く

- 出題の傾向の蒸留(`docs/source-policy.md` の「出題の傾向の蒸留」)の記述は、方針が書いてよいと定める形(設問の型や論点の分布を、割合や中央値などの要約の値で書いたもの)を、指摘しない。
  方針が書かないと定めるもの(材料の件数と出どころ。所感や例題の数が読み取れる形、割合の分母に材料の件数を添えた形、収集元)は、従来どおり指摘する。
  試験の出題数、問題データの問題数、配点は、材料の件数ではないので、この例外の対象ではない。方針の文言は `docs/source-policy.md` にだけ置き、ここでは参照する。

## 整合を見るもの

文書や下書きが、実装・設定・既存の文書と食い違っていないかを確認する。漏えいの確認(上の「見るもの」)とは別の観点で、同じ検査役が行う。

1. **記述と実装の一致**: 文書・コメント・スキル・下書きの記述が、コードや設定の値(既定値、コマンド名、オプション、環境変数名)と合っている。
   実装の振る舞い(件数の切り詰め、上限、置き場、候補の定義、結果に持つ項目、終了コード、再実行・再依頼の条件)の記述は、境界の場合(件数が 0・1・上限ちょうど・上限超え、空、重複)と、
   全分岐(dry-run、一部だけ成功、全件失敗)まで合っている。依頼や報告に照合の記録(開いた関数・定数の名前、確かめた境界の場合)があれば、読んで、照合の抜けを探す
2. **参照先の実在**: 参照しているファイル、文書、節(見出し)、コマンド、スクリプト名、npm スクリプトが実在する。リンクが切れていない。
   実在するだけでなく、書かれた内容がそこにあるか(内容の一致)も、参照先を開いて確かめる(ADR・Issue の番号が別の決定を指していないか、挙げた節がその決まりを書いているか)
3. **数値・件数・既定値**: 書かれた数値、件数、上限、既定値が、定義元と合っている
4. **他の文書との矛盾**: 同じ事柄を述べる別の文書と食い違っていない

- スキル・手順・エージェントの定義を足す、または変える差分では、次も照合する。
  - 既存の決まり(`CLAUDE.md` の「検査と承認の流れ」の表、関係するスキルの判定ごとの動き)と、同じ操作の扱いが食い違っていない。既存のスキルの手順を言い換えず、参照しているか(変える点だけを書いているか)。
  - エージェントの定義は、依頼の値の形(配列の入れ子、件数、順序、添字の基準)を、単数と複数の語の使い分けも含めて、曖昧にせず書いているか。
  - 人やメインのセッションが順に実行する手順は、前の段の出力が次の段の入力になっているか(入力の出どころを、依頼を作る関数と役の定義まで追う)。依頼に確かめの記録(`/dev-commit` の Step 0 の 8)がなく、通して実行していない手順は、整合の食い違いとして指摘する。
- **初回の検査で、照合を網羅する。** 差分に書かれた数、範囲、名前、一覧、上限・既定値のすべてを、定義元と突き合わせる。
  1 か所を見つけたところで止めず、同じ語を差分の全体と、差分が参照する文書から検索して、同じ種類の箇所も確かめる。
  再検査のたびに新しい食い違いが出るのは、初回の照合が一部で止まっているため。
- 再検査の依頼(前回の指摘の一覧がある依頼)では、整合を見る範囲は、`inspector-rules.md` の「判定の範囲」に従う。上の網羅は、初回の検査の決まりである。
- 読む範囲は、差分が参照しているファイルと節だけ。参照先と定義元を確かめるために読む。無関係なファイルは読まない。
  依頼に「検索した語」が書かれているときは、その語で検索して見つかった箇所も読んでよい(`.env`、秘密鍵の類、`pipeline-work/` は、検索の対象にも読む対象にもしない)
- 重さは、漏えいは `BLOCK`、整合は `WARN` を基本にする。手順どおりに動かすと漏えいや破壊的な操作につながる食い違い
  (承認なしで push できる手順など)は `BLOCK`
- どの検査で必須か
  - commit・push: 差分に、文書(`.md`)、設定、スキル、エージェントの定義、スクリプトを含むとき
  - PR・Issue の下書き: 常に
- 報告は、漏えいと同じく、値を引用せず、場所と種類だけを書く
  - 良い例: `docs/foo.md 12 行目: 参照先の文書が存在しない(重大度: WARN)`

## 対象

- 差分の**追加行**だけでなく、ファイル名、コミットメッセージ、ブランチ名、PR・Issue のタイトルと本文も対象
- テストのフィクスチャ、ドキュメント、リリースノートも対象(利用者にも見える)
- `.env`(gitignore 済み)に置くべき値が、コードやドキュメントに書かれていないか

## 報告のしかた(必ず守る)

- **見つけた値そのものを、報告に書かない。** 報告がログや会話に残るため。場所と種類だけ書く
  - 良い例: `docs/foo.md 12 行目: アカウント ID らしき 12 桁の数字(重大度: BLOCK)`
  - 悪い例: 値を引用する
- 各指摘に、次のいずれかの重大度を付ける
  - `BLOCK`: 認証情報、環境固有の値、個人情報、拒否リストの語、書いてはいけない名前や経緯。止める
  - `WARN`: 判断が要るもの(社内名称かもしれない、実在しそうなダミー値など)と、整合の食い違い。人に見せて決めてもらう
- 判定の範囲の外の気づきは、`参考:` の欄に書く(判定には含めない)。報告の末尾に、読んだ範囲の行も書く(`inspector-rules.md` の「判定の範囲」と「報告」)
- 最後に、全体の判定を 1 行で書く: `判定: OK` / `判定: WARN` / `判定: BLOCK`
- 確認できなかったこと(差分が大きすぎて全部は読めなかった、など)は、正直に書く。「問題なし」と断定しない
- 判定の前に、「置いた前提」を 1〜3 行で書く(依頼に書かれていなくて自分で決めたこと。読んだ範囲、仮定した事実、確かめていないこと。なければ「なし」)

## 直し方の指針

- 値は `.env` に置き、コードには環境変数名だけを書く
- 説明のために値が要るときは、プレースホルダーにする
- すでにコミット済みの値は、新しいコミットで消すだけでは履歴に残る。**push 前**なら、コミットを作り直す
  (`git reset --soft` で戻して、直して、コミットし直す)。push 後は、履歴を書き換えず、人に相談する
