# 書く側の共通の決まり(コミットメッセージ案、PR・Issue の下書き)

メインのセッションが、コミットメッセージ案と、PR・Issue のタイトルと本文を書くときに従う決まり。共通の決まりは、この文書にだけ書く。
書く側(メインのセッション)と確かめる側(検査役のサブエージェント)は別にする(`CLAUDE.md` の「検査と承認の流れ」)。検査役は、書いた側の文脈を引き継がない目で確かめる。

## 範囲

- 書いてよい場所は、`.drafts/` の下だけ(コミットメッセージ案は `.drafts/commit-msg.txt`、PR・Issue の下書きは `.drafts/pr-<ブランチ名>.md`・`.drafts/issues/`)。それ以外は、この手順では編集しない。
- `.env`、秘密鍵の類、拒否リスト(`.pr-secrets-denylist`)、取得した本文の置き場(`pipeline-work/`)は開かない。

## 書き方

- `checklist.md` の「見るもの」を守る。認証情報、環境固有の値、個人情報、社外や非公開の名称、このリポジトリの外の事情や経緯を示す語は書かない。
- コード例・例データの値(接続先、グループ名・役割名、番号)は、`checklist.md` の「プレースホルダーの書き方」の形で書く。
  図や表の例データの番号・コードも、書く前に `<番号>` か `X` を並べた形に置き換える(個人の番号に見える桁の並びを、ダミーのつもりで書かない)。
- 一般的な現在形で書き、出来事を語らない。
- 書いたあとに、回数・版・行為者・過去の出来事を表す語(「回」「版にまたがって」「先日」「した結果」「直した」「なった」など)を、書いた下書き全体で検索し(Grep ツール。書いたファイルを指定する)、
  上の「出来事を語らない」に反するものが残っていないことを確かめる。会話や材料に出来事の事実(回数、版、取得し直した結果、過去の作業)があっても、本文には書かず、現在の問題と決まりの形に直す。
  現在の状態を説明する文に出る語(「なった」など)は、文脈で判断する。機械検査にしない理由: 語の検索は、現在形の説明にも出る語で誤検出が多く、判断が文脈に依るため。
  検査役の確認(`checklist.md` の「見るもの」8 の文体)と、この自己確認に任せる。
- 署名の行(`Co-Authored-By:`)と、Claude のセッションへのリンク(`Claude-Session:` の行など)は、メッセージ案と下書きに書かない(書くよう頼まれたときも書かない)。署名の行は、コミットの直前に、メインのセッションが足す(`/dev-commit` の Step 5)。
- 文書に数・範囲・名前(経路の一覧、上限の値、報告に出す項目など)を書くときは、定義元の定数・関数・ファイルの名前を添え、書く前にそれを開いて照合する。
  外部の仕様の数値(クラウドのサービスの上限など)は、記憶で書かず、公式の文書の節を確かめてから書く。確かめた節の名前は、文書(数値の近く)に添え、検査役への依頼の照合の記録にも書く。
  文書に書いた関数・定数・経路の名前が実在するかは、機械検査しない(`npm run check:docs` が見るのは、相対リンクの先と `npm run` のスクリプト名だけ)。文書ごとに名前の書き方が違い、拾う形を決めると、誤検出と取りこぼしが増えるため。
  検査役の整合の確認(`checklist.md`)と、この決まりに任せる。
- 文書に実装の振る舞い(件数の切り詰め、上限、置き場、候補の定義、結果に持つ項目、終了コード、再実行・再依頼の条件、書き込みを巻き戻す範囲)を書くときは、上の照合に加えて、
  実装の関数を開き、境界の場合まで照合してから書く。境界の場合は、件数が 0・1・上限ちょうど・上限超え、空、重複、dry-run・一部だけ成功・全件失敗を含む全分岐である。
  成功の経路だけを見て書かない(文書の記述は、実装の分岐より狭く、または広くなりやすい)。照合した記録は、下の「照合の記録」に残す。
  守ったかは、機械では確かめない。振る舞いの記述は、実装の一覧との突き合わせでは拾えないため。検査役の整合の確認(`checklist.md` の「整合を見るもの」)に任せる。
- 文書に、実装の一覧を列挙する表(理由コード、欠陥の種類、設定の項目など)を新しく書くときは、その表と実装の一覧を突き合わせるテストを、同じ差分で書く
  (前例: `packages/pipeline/src/draft/docs.test.ts` の「スタイルガイドと規則の一致」)。表の形が決まった個別のテストなら、誤検出が出ない。
  `npm run check:docs` の一般の検査にはしない(文書ごとに表の形が違い、誤検出と取りこぼしが増えるため)。
- 材料や記憶にある参照(ADR・Issue の番号、文書の節の名前)は、書く前に、その文書を開いて、書く内容がそこにあることを確かめる(参照先が実在するだけでなく、内容が合うこと)。
  確かめられない参照は書かず、確認が必要なものとして(参照の種類と、書こうとした場所を)人に挙げる。上の数・範囲・名前の照合とは別に、参照の内容の一致を決める項目である。
- 画面の文言(ボタンの名前、見出し、メッセージ)を引用して書くときは、文言を組み立てるコードを開き、条件で変わる形(件数や状態で名前が変わる場合)をすべて確かめてから書く。
  一部の形だけを引用して、ほかの形を書き落とさない。書き直しで、直した語が分かっているときは、その語で書いた下書き全体を検索し、同じ語の古い言い方を残さない。
- メッセージや下書きに、項目や行の種別・件数を書くときは、差分の該当行と照合し、数え直してから書く。
  - リリースノートの項目の種別は、差分の `type` の値(`feat`・`fix`・`docs`・`dev`。定義元は `scripts/lib/release-notes-check.ts` の `ITEM_TYPES`)で書く。
    画面の表示名(`packages/app/src/lib/release-notes.ts` の `RELEASE_ITEM_LABELS`)や、「開発者向け」「利用者向け」などの言い換えを使うときは、どの `type` に当たるかを添える。
  - リリースノートの項目を書くときは、`CONTRIBUTING.md` の「リリースノートの書き方」に従う。利用者向けの項目(`feat`・`fix`・`docs`)には、内部の語(コードの書式、ファイル名・パス、コマンド、検査・スクリプトの名前、Issue・PR の番号、理由コード、役の名前)を書かない。
    利用者の操作と表示が変わらない変更(検査、スクリプト、CI、作問パイプラインの内部、開発の文書、ふるまいの変わらない依存の更新)は `dev` にする。内部の変更でも利用者に影響があるものは、利用者向けの種類で影響を書く(種類の選び方は `CONTRIBUTING.md` の「リリースノートの書き方」)。
  - 設定の値の由来(計算式や根拠)が材料にあっても、差分に現れない計算や根拠は、メッセージの事実として書かない(書いてよいのは、差分にある値)。
  - 機械検査にしない理由: 種別の妥当さと、値の由来の読み分けは、文脈の判断を含み、機械で決めると偽の合格が出るため。検査役の整合の確認(`checklist.md` の「整合を見るもの」)に任せる。
- スキル・手順を足す、または変えるときは、先に `CLAUDE.md` の「検査と承認の流れ」の表と、関係するスキルの判定ごとの動きを開いて、同じ操作の決まりと食い違わないかを照合する。
  既存のスキルの手順は言い換えず、参照して、変える点(時機など)だけを書く。
- エージェントの定義には、依頼の値の形(配列の入れ子、件数、順序、添字の基準)を明記する。配列の入れ子を単数の語で説明しない。
- 実データで確かめた結果を文書に書くときは、条件と注意の形(「〜すると〜になる」「〜する」)で書く。確かめた経過や、数値の変化は書かない。
- 判断に迷う語は書かず、検査役への依頼に「確認が必要な語がある」とだけ書く(語そのものは書かない)。

## 照合の記録

- 検査役への依頼に、**「置いた前提」**を 1〜3 行で添える。自分で決めたこと(読んだ範囲、仮定した事実、確かめていないこと)を書く。なければ「置いた前提: なし」。
  検査役が前提のズレに気づくための記録。語そのものが値のときは、書かない。
- 実装の振る舞いや参照(ADR・Issue の番号、文書の節)を書いたときは、「置いた前提」に、開いた定義元の関数・定数の名前(参照は、文書と節の名前)と、確かめた境界の場合を書く。
  確かめていないものは「確かめていない」と書く。検査役は、この記録から、照合の抜けを探す。
