# 作成役の共通の決まり(commit-writer / draft-writer)

2 つの作成役の定義(`.claude/agents/commit-writer.md`、`draft-writer.md`)は、モデル・書く対象と書式・Bash で許すコマンドだけが違う。
共通の決まりは、この文書にだけ書く。

## 範囲

- 依頼で指定された作業ツリーの中だけで作業する。git は、作業ディレクトリのその作業ツリーで実行する(別のパスを指す `git -C` は使わない)。
- 書いてよい場所は、各定義が決める。それ以外は編集しない。
- git の書き込み、ネットワーク操作、リダイレクト(`>`)は使わない。
- `.env`、秘密鍵の類、拒否リスト(`.pr-secrets-denylist`)、取得した本文の置き場(`pipeline-work/`)は開かない。

## 書き方

- `checklist.md` の「見るもの」を守る。認証情報、環境固有の値、個人情報、社外や非公開の名称、このリポジトリの外の事情や経緯を示す語は書かない。
- 一般的な現在形で書き、出来事を語らない。
- 署名の行(`Co-Authored-By:`)と、Claude のセッションへのリンク(`Claude-Session:` の行など)は書かない。署名の行はメインのセッションが足す。
- 文書に数・範囲・名前(経路の一覧、上限の値、報告に出す項目など)を書くときは、定義元の定数・関数・ファイルの名前を添え、書く前にそれを開いて照合する。
  外部の仕様の数値(クラウドのサービスの上限など)は、記憶で書かず、公式の文書の節を確かめてから書く。確かめた節の名前は、文書(数値の近く)に添え、報告の「置いた前提」にも書く。
  文書に書いた関数・定数・経路の名前が実在するかは、機械検査しない(`npm run check:docs` が見るのは、相対リンクの先と `npm run` のスクリプト名だけ)。文書ごとに名前の書き方が違い、拾う形を決めると、誤検出と取りこぼしが増えるため。
  検査役の整合の確認(`checklist.md`)と、この決まりに任せる。
- スキル・手順を足す、または変えるときは、先に `CLAUDE.md` の「検査と承認の流れ」の表と、関係するスキルの判定ごとの動きを開いて、同じ操作の決まりと食い違わないかを照合する。
  既存のスキルの手順は言い換えず、参照して、変える点(時機など)だけを書く。
- エージェントの定義には、依頼の値の形(配列の入れ子、件数、順序、添字の基準)を明記する。配列の入れ子を単数の語で説明しない。
- 実データで確かめた結果を文書に書くときは、条件と注意の形(「〜すると〜になる」「〜する」)で書く。確かめた経過や、数値の変化は書かない。
- 判断に迷う語は書かず、報告に「確認が必要な語がある」とだけ書く(語そのものは書かない)。

## 報告

- 報告の最後に、**「置いた前提」**の欄を 1〜3 行で書く。依頼に書かれていなくて自分で決めたこと(読んだ範囲、仮定した事実、確かめていないこと)を書く。なければ「置いた前提: なし」。
  メインが前提のズレに気づくための欄。語そのものが値のときは、書かない。
