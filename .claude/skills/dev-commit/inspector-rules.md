# 検査役の共通の決まり(inspector / inspector-deep)

2 つの検査役の定義(`.claude/agents/inspector.md`、`inspector-deep.md`)は、名前・説明・モデルだけが違う。
それ以外の決まりは、この文書にだけ書く。

## 道具と範囲

- **読み取り専用。** 道具は Read / Grep / Glob だけで、Bash は持たない。編集、git の操作、ネットワーク操作はできない。
- 依頼で指定された作業ツリーの中だけを読む。範囲の外は読まない。整合の確認(`checklist.md` の「整合を見るもの」)のために読んでよいのは、
  差分が参照しているファイルと節だけ。ただし、依頼に「検索した語」が書かれているときは、その語で作業ツリーを検索し、
  見つかった箇所を読んでよい(同じ記述の洗い出しを確かめるため)。このときも、`.env`、秘密鍵の類、`pipeline-work/`(下の開かないファイルの項目)は、検索の対象にも読む対象にもしない。
- 依頼された範囲の全部を読む。最後のコミットだけで済ませない。
- `.env`、秘密鍵の類、取得した本文の置き場(`pipeline-work/`)は開かない。

## 入力

メインのセッションが `.drafts/inspect/` に書き出している(`scripts/prepare-inspection.ts`)。

- `diff.patch`: 差分(commit はステージした差分、push は範囲の全コミットの差分で、競合を解消したマージの内容を含む、PR は基準との差分)。
  ただし `covered.txt` に挙げたコミットの差分は省く
- `diff-1.patch`、`diff-2.patch`、…と `parts.txt`: 差分が目安の行数(`scripts/lib/inspection-input.ts` の `INSPECT_PART_LINES`)を超えたときは、
  `diff.patch` の代わりに、差分を分担ごとのファイルに分けて書き出し、分担の一覧(分担の名前、ファイル、行数、最初のファイル)を `parts.txt` に書く。
  依頼で担当の分担を指定されたら、そのファイルの全部を読む。ほかの分担のファイルは読まなくてよいが、`files.txt` と `commits.txt` は読み、
  整合の確認のために、差分が参照するファイルを読んでよい(上の「道具と範囲」)
- `files.txt`: 変更されたファイルの一覧(push はコミットごとの一覧と範囲の正味の差分、PR は基準との正味の差分)
- `commits.txt`: コミットの作者・コミッター・メッセージ(commit は、これから作るコミットの作者)
- `covered.txt`: 検査済みのため差分のファイルから差分を省いたコミット(push と PR のとき)。「なし」とあれば、省いたものはない
- `stamp.txt`: 入力全体のスタンプ(`スタンプ: …` の行)。報告に書き写す
- `branch.txt`: ブランチ名
- `denylist.txt`: 拒否リストの置き場のパス(1 行 1 件)。「なし」とあれば、拒否リストが見つからない
- 依頼で渡された下書きやメッセージ案のファイル

## 検査済みのコミット

`covered.txt` に挙げられたコミットの差分は、commit のときに検査済み(台帳に記録があり、検査の基準と拒否リストが同じ)なので、読み直さない。
マージコミットを含む範囲では、台帳を使わず、すべての差分を出している(競合を解消したマージの内容を含む)。メッセージと作者は `commits.txt` にあり、
毎回確認する。ブランチ名と、下書きやメッセージ案も、毎回確認する。

## 拒否リスト

- `denylist.txt` に書かれた置き場のファイルを読み、その語が対象のどこにもないかを確認する。
- 「なし」のとき、または読めなかったときは、照合できなかったと報告する。「問題なし」と断定しない。
- 語そのものは、報告に書かない。

## 版のブランチの番号

版のブランチ(名前に版を使うもの。例: `chore/#352-v0.59.0`)では、コミットの `Closes`・`Refs` の番号が、ブランチ名の番号と違っても、指摘しない(`CONTRIBUTING.md` の「ブランチ」)。
Issue の番号が実在するか、版の Issue かは、検査役からは確かめない。

## 署名とセッションのリンク

- コミットメッセージ末尾の `Co-Authored-By:` の署名の行は、定型である。指摘しない。形が定型と違うものは指摘する。
- Claude のセッションへのリンク(`Claude-Session:` の行など)は、これから作るコミットのメッセージ案と、PR・Issue の下書きにあれば
  `BLOCK` にする。push の範囲にある、すでに作られたコミットのメッセージは、指摘しない。

## 依頼ごとの追加項目

依頼に「追加項目」があれば、チェックリストの項目に加えて確認する。追加項目の重さは、依頼が指定する(指定がなければ `WARN`)。
追加項目は、依頼の文面の中で渡す。この文書とチェックリストには書き足さない。整合の確認は、追加項目ではなく、チェックリストの項目である。

## 報告

- 報告の形は、チェックリスト(`checklist.md`)の「報告のしかた(必ず守る)」に従う。値を引用せず、場所と種類だけを書く。
- 読み切れなかったこと、確認できなかったことは、正直に報告する。「問題なし」と断定しない。
- 報告の先頭に、`stamp.txt` の `スタンプ:` の値を、そのまま 1 行で書き写す(`入力のスタンプ: …`)。読めなかったときは「入力のスタンプ: 読めなかった」と書き、`OK` にしない。
  メインは、このスタンプがいまの入力と一致するかを機械で確かめ、違えば、その判定を採用しない。
- 報告の最後(`判定:` の行の前)に、**「置いた前提」**の欄を 1〜3 行で書く。依頼に書かれていなくて自分で決めたこと(読んだ範囲、仮定した事実、確かめていないこと)を書く。なければ「置いた前提: なし」。
- 最後に 1 行で `判定: OK` / `判定: WARN` / `判定: BLOCK`。
