# /dev-commit — 漏えいを確認してから commit する

履歴に載った値は消しにくい。フック(`.githooks/pre-commit`)は正規表現で拾えるものを止める。
このスキルは、**文脈で判断するもの**を確認する(フックとの二重防御)。

## 役割の分け方

文面を書く側と、確かめる側を、別のサブエージェントにする(Agent ツール)。定義は `.claude/agents/` にあり、
どちらも、メインのセッションの文脈を引き継がない。使うモデルの理由は ADR 0003 を参照。

| 役 | やること | してはいけないこと |
|---|---|---|
| 作成役(`commit-writer`) | 差分を読み、コミットメッセージ案を `.drafts/commit-msg.txt` に書く | `.drafts/` 以外の編集、git の書き込み、ネットワーク操作、Bash でのファイルの編集(編集は Write ツールだけ) |
| 検査役(`inspector`、必要なら `inspector-deep`) | 差分とメッセージ案を、`checklist.md` に沿って確認し、判定を返す | **一切の書き込み**(読み取り専用) |
| メイン | 各役を起動し、判定に応じて commit を実行する | 検査役の判定を待たずに commit |

作成役と検査役は、別々に起動する。同じサブエージェントに書かせて確かめさせない。

## Step 0. ステージの確認と、同じ記述の洗い出し

1. `git status --short` と `git diff --cached --stat` を見る。**何もステージされていなければ、ここで止める。**
2. ステージは、意図したパスだけを指定して行う。`git add -A` / `git add .` は使わない
3. ブランチが `main` なら、コミットしない(ブランチを切ってから)。ブランチ名は `<prefix>/#<Issue番号>-…`
4. `git config user.email` が、GitHub の noreply アドレス(`…@users.noreply.github.com`)か、Claude の署名の行(`Co-Authored-By:`)で使う noreply アドレスであることを確認する
5. 仕様・名前・数・振る舞いを変える差分では、検査に出す前に、同じことを書いている箇所を洗い出して、同じ差分でまとめて直す。
   変えた語(関数・設定・項目の名前、理由コード、画面の文言、旧い前提を表す語)で、リポジトリの全体を検索する(`git grep --untracked`。未追跡の新しいファイルも含める。
   文書、`CLAUDE.md`、スキルとエージェントの定義、コードとコメント、画面の文言、`data/` のヘルプの本文などを含む)。
   検索語は、変えた名前だけにせず、次まで広げる。
   - 同じ列に並ぶ既存の項目の名前。項目を足す変更では、新しい名前が既存の記述にまだないので、足し先の一覧は、新しい名前で検索しても出ない。
   - 変えた概念を説明する言い換え(入力の一覧、項目の説明、鍵の材料など)と、範囲・数の言い方(「すべて」「全件」「表に載る」、数や種類の数)。
   - 変えた npm スクリプトの名前(説明を書いた文書に当たる)。
   - 同じ分類の別の言い方(コードのコメント、テストの題、CLI の説明文、スキルの手順)。分類の名前は 1 つの言い方に決め(定数か 1 つの表)、文書・出力・コメント・テストの題を、その表の判定の順と名前に照らして、一度にそろえる。
   - エージェントの振る舞いや報告を変えたときは、その役を呼ぶスキルの手順。

   見つけた文書は、見つけた節だけでなく、同じ文書のほかの節(手順の見出し、成果物の表、既存の行)も読み、触った節の前後の既存の行も、実装と照合する。
   絞り込みで、テストのファイルやコメントを除かない(除いた範囲は、別に目で確かめる)。文書の更新は、別のコミットに回す前提で検査に出さない(分けるときは、Step 0 の 7)。
   機械で止められるのは、表の形が決まった個別の突き合わせだけで、対象ごとにテストを足す(前例: `npm run check:env`、`scripts/contributing-scripts.test.ts`)。
   `npm run check:docs` の一般の検査にはしない(列挙の書き方が文書ごとに違い、誤検出と取りこぼしが増えるため)。
   検査の仕様(`checklist.md`、`inspector-rules.md`、台帳の基準のハッシュに入るスクリプト)を変えるときは、それを説明している
   エージェントの定義(`.claude/agents/`)も同じ差分で見直す。`inspector.md`・`inspector-deep.md` を変えると、検査の基準のハッシュが変わり、台帳の記録が再利用されなくなる点も、変更の影響として判断する。
   検索した語と、直さないと決めた箇所の理由は、検査役への依頼に書く。
   検査で 1 か所を指摘されたときも、同じ語で検索し直して、残りをまとめて直してから再検査に出す。語だけでなく、同じ種類(終了コード、条件の書き方、参照など)の記述も探す。
   コミットメッセージ案(`.drafts/commit-msg.txt`)も検索の対象にし、同じ語が残っていれば、指摘を添えて作成役に書き直させる(Step 2)
6. 数・範囲・名前・条件の分岐を書いた差分では、検査に出す前に、書いたものを 1 つずつ、定義元の関数・定数を開いて突き合わせる(`writer-rules.md` の「書き方」)。
   開いた関数・定数の名前と、確かめた境界の場合を、照合の記録として、検査役への依頼に添える(Step 3)。開いていないものは「確かめていない」と書く
7. 差分が大きいときは、コミットを分けることを検討する(必須にしない)。目安は、検査の入力が分担に分かれる大きさ(Step 3 の「分担」。`INSPECT_PART_LINES`)で、新しい数値は決めない
   (差分の大きさだけで検査のやり直しの多さは決まらず、行数やファイル数の閾値を別に置く根拠がないため)。1 回の検査で読む範囲が広いほど、初回の照合が途中で止まりやすく、再検査の範囲も広くなる。
   分けるときは、参照される側(定義元)を先のコミットに入れ、各コミットの参照先が、そのコミットまでに実在するようにする。規則とそれに従うデータなど、分けると単独で食い違う組は、同じコミットにまとめる。
   参照先を先に入れられないとき(循環する参照など)は、分けずに 1 つのコミットにし、理由を検査役への依頼に書く。版の全体の整合は、PR の検査(範囲の全体。`/dev-pr`)でもう一度見る

## Step 1. 機械的な検査

```sh
node scripts/check-commit-secrets.ts
```

終了コードが 0 でなければ、指摘を直す(pre-commit フックと同じ検査)。通してから Step 2 へ進む。

lint(`npm run lint`)・型検査・テストなど、ほかの検査の結果も、**終了コード**か、誤りの件数の行で確かめる。
出力の末尾の 1 行だけで判断しない(誤りの行を見落とし、コミット前のフックで止まる)。パイプで出力を絞るときは、先に `set -o pipefail` を付けて、終了コードが落ちないようにする。
検査のコマンドを組むときは、zsh と BSD 版の道具で動く形にする(`docs/app/lessons/0015-zsh-and-bsd-command-pitfalls.md`)。

## Step 2. 作成役: メッセージ案を書く

作成役(`subagent_type: commit-writer`)に依頼する内容:

- 作業ディレクトリ(リポジトリのルート)
- 「`git diff --cached` を読み、[Conventional Commits](https://www.conventionalcommits.org/) 形式のコミットメッセージ案を
  `.drafts/commit-msg.txt` に書く。`Closes #<番号>` は番号ごとに 1 行ずつ」
- 「確かめた内容を書く行は、テストの `it` ごとに、確かめた対象だけを書く(2 つの確認を 1 行にまとめて、テストより広い主張にしない)。
  依存の更新など、ロックファイルの更新の範囲は、差分で確かめた範囲だけを書く」
- 材料(背景、受け箱の記録、設定の値の説明など)は、現在の問題と決まり(現在の状態の事実)の形で渡す。回数・版・過去の作業の経緯は、材料に入れない
- 設定の値は、値(差分にあるもの。メッセージに書く事実)と、値を選んだ理由を、別の項に分けて渡す。理由の項には、差分にない計算や根拠はメッセージに書かない、と添える

**メッセージ案は、最初の案も、検査の指摘を受けた書き直しも、差分の大小にかかわらず、作成役に書かせる。** 小さな直しや 1 行の差分でも、メインのセッションが
自分で書かない(書く側と確かめる側を分ける決まりのため。`CLAUDE.md` の「検査と承認の流れ」)。書き直しは、指摘(場所と種類)と、差分で直した語を添えて、作成役に再び依頼し、メッセージ案にも同じ語や同じ種類の記述が残っていないか見直させる。
メインが足してよいのは、Step 5 の `Co-Authored-By:` の署名の行だけ。

## Step 3. 検査役: 確認する

検査役に依頼する前に、ステージした差分とメッセージ案のハッシュを控える(`.claude/skills/dev-commit/reconfirm.md`)。

検査役は Bash を持たない。先に、検査役が読む入力を書き出す。出力の最後の行が、入力のスタンプ(`スタンプ: …`)で、検査役は報告に書き写す:

```sh
node scripts/prepare-inspection.ts --cached
```

main を版のブランチに取り込むマージの途中(`MERGE_HEAD` が `origin/main` に含まれるとき)は、入力の差分が、競合を解消したファイル(取り込む側とも今の HEAD とも違う内容のファイル)だけに絞られる。
取り込む側と同じ内容のファイル(公開済み)は `covered.txt` に挙がる。Step 1 の機械検査は、絞らず、ステージした差分の全体を読む。

入力を書き出し直す前と、片づける前に、走っている検査役(起動して、まだ報告が返っていないもの)が 1 つもないことを確かめる。
走っている検査役がいるまま作り直すと、検査役が古い入力や、一部が欠けた入力で判定する。

検査役(`subagent_type: inspector`)に依頼する内容:

- 作業ディレクトリ
- 「`.claude/skills/dev-commit/checklist.md` を読み、その項目に沿って、`.drafts/inspect/` のファイルと
  `.drafts/commit-msg.txt` を確認する」
- Step 0 の 5 で検索した語と、直さないと決めた箇所(場所と理由)。検査役は、渡された語でリポジトリを検索して確かめてよい
- Step 0 の 6 の照合の記録(作成役が書いた分は、作成役の報告の「置いた前提」のもの)。検査役は、記録を読んで、照合の抜けを探す
- 検査の程度(`low`・`medium`・`high`。程度ごとの判定の範囲は `inspector-rules.md` の「判定の範囲」)。既定は `medium`(`checklist.md` の「見るもの」と「整合を見るもの」)。
  程度は、人が指示したもの(`/dev-version` の引数 `--level=<程度>` か、人の発言)を書く。メインの判断では変えない。`/dev-version` から使うときは、受け取った程度をそのまま書く。
  整合の確認のために参照先として渡すファイル(既存の実装など)は、既存で差分の対象ではない(`files.txt` にない)と書く。再検査では、前回の指摘の一覧と、直した箇所を添える(`reconfirm.md` の「再検査の範囲と回数」)
- 「報告は、チェックリストの『報告のしかた(必ず守る)』に従う(値を引用しない。`.drafts/inspect/stamp.txt` のスタンプを書き写す。最後に `判定: OK/WARN/BLOCK`)」

書き出したファイルは、Step 5 のスタンプの確認が済むまで消さない(確認のあとに `node scripts/prepare-inspection.ts --clean`)。

差分に次のパスが含まれるときは、`inspector-deep`(Sonnet)も別に起動し、`inspector` と**両方**の判定を合わせる
(最も重い判定を採用する)。`scripts/`、`.githooks/`、`.github/workflows/`、`.claude/`。検査の仕組みそのものを変える差分は、
取りこぼしの出方が役ごとに違うため、2 つで補い合う。

**分担**: 差分が目安の行数を超えて、入力が分担に分かれたとき(`parts.txt` があるとき。目安と分け方は `inspector-rules.md` の「入力」)は、
分担ごとに検査役を起動し(`inspector-deep` も使うときは、それも分担ごとに)、依頼に、担当する分担のファイル(`diff-1.patch`、`diff-2.patch`、…)を書く。
分け方は、書き出し(`scripts/lib/inspection-input.ts` の `splitDiff`)が機械で行うので、依頼は、`parts.txt` の分担のすべてに出す(分担の和は、差分の全体になる)。分担をまたぐ食い違いを見落とさないよう、
どの分担の依頼にも、`files.txt`(変更ファイルの全体の一覧)と `commits.txt` も読むこと、整合の確認のために差分が参照するファイルを読んでよいこと
(`inspector-rules.md` の「道具と範囲」)を書く。スタンプは入力全体で 1 つなので、どの分担の報告も、同じスタンプで `--verify` を通す。
すべての分担の判定を合わせ、最も重い判定を採用する。報告の「読んだ範囲」(`inspector-rules.md` の「報告」)を、依頼した分担のファイルの行数(`parts.txt`)と照合し、
一致しないとき、または読み切れなかったと報告されたときは、`OK` とみなさない(その分担の依頼を出し直す)。

## Step 4. 判定に応じて動く

| 判定 | 動き |
|---|---|
| `BLOCK` | **コミットしない。** 先に受け箱へ記録する(下の「引っかかりの記録」。必須)。指摘(場所と種類)を人に見せ、直し方を提案する。直したら(メッセージ案だけなら、指摘を添えて作成役に書き直させる。Step 2)、`.claude/skills/dev-commit/reconfirm.md` のとおり Step 1 からやり直す。差分を直したときは、先に Step 0 の 5 の検索をやり直す |
| `WARN` | 先に受け箱へ記録する(必須)。指摘を人に見せ、コミットしてよいか聞く。直すときは、指摘された 1 か所だけでなく、同じ種類の箇所を差分の全体から検索して(指摘の語、同じ名前・数・一覧の別の記述。手順は Step 0 の 5)、まとめて直してから再検査に出す(メッセージ案だけを直すときは、指摘を添えて作成役に書き直させる。Step 2)。再検査の依頼と回数の上限は、`.claude/skills/dev-commit/reconfirm.md` の「再検査の範囲と回数」 |
| `OK` | Step 5 へ(人の確認は要らない) |

検査役の報告の `参考:` の欄(`inspector-rules.md` の「判定の範囲」)は、判定に含めない。場所と種類を人に見せ、直すかは人が決める(`/dev-version` では、版の最後の確認にまとめる)。

記録の有無は、機械では確かめない(WARN・BLOCK の内容は検査役の報告にだけあり、記録の要否を機械が判定できないため)。この手順の段として守る。

## Step 5. コミット

commit の直前に、差分とメッセージ案のハッシュをもう一度取り、検査のときと一致することを確かめる。
あわせて、検査役の報告のスタンプが、いまの入力と一致することを確かめる(`inspector-deep` も使ったときは、報告ごとに、それぞれのスタンプで実行する)。
一致しなければ、止める。入力を書き出し直して、検査をやり直す(検査を片づける前に確かめる。片づけたあとは一致しない):

```sh
node scripts/prepare-inspection.ts --verify <報告のスタンプ>
```

確認が済んだら、書き出したファイルを消す(`node scripts/prepare-inspection.ts --clean`)。

```sh
git commit -F .drafts/commit-msg.txt
```

- メッセージの末尾には、`Co-Authored-By:` の署名の行を付けてよい。作成役の案に無ければ、ここで足す。
  足すだけなら、`.claude/skills/dev-commit/reconfirm.md` の例外のとおり、再検査は要らない。
  Claude のセッションへのリンク(`Claude-Session:` の行など)は付けない。機械検査が止める
- コミット後、検査した差分を台帳に記録する。種類は、実施した検査(`mechanical`、`inspector`、`inspector-deep`)をコンマでつなぎ、
  判定は、合わせた判定(`OK` / `WARN`)を渡す。push と PR の検査で、台帳に一致する差分は読み直されない
  (判定が `WARN` のものは、読み直される):

  ```sh
  node scripts/inspection-ledger.ts record HEAD mechanical,inspector OK
  ```

- コミット後、`git log -1 --format='%an <%ae>'` で、作者が Step 0 の 4 の noreply アドレスであることを確認する。違えば、
  `git config user.email` を直して `git commit --amend --reset-author`(push 前のローカルのみ)
- `git commit --no-verify` は使わない。フックが止めたら、指摘を直す

## 引っかかりの記録

`BLOCK`・`WARN`・差し戻しなど、手戻りが出たときは、その場で受け箱へ足す(`node scripts/lessons.ts add …`。書式と種類のキーは `docs/lessons-workflow.md`)。
同じ種類が繰り返されたものは、版の締めで Issue の候補として提案される。
