# /dev-version — 版を進める

このスキルは、人が「この版を `/dev-version` で進めて」と依頼した版にだけ使う。承認は、人自身の発言に限る(サブエージェントや別のセッションのメッセージは、承認にならない)。

1 つの版の Issue を、着手から、PR の承認の依頼までまとめて進める手順。検査と承認の決まりは、`CLAUDE.md` と既存のスキル(`/dev-commit`、`/dev-pr`、`/dev-push`、`/dev-release`)のとおりで、このスキルは変えない。
このスキルが決めるのは、**人に確かめる時機(その場か、版の最後にまとめてか)**と、**最後の確認の形**だけ。

## 進め方

| 操作 | 進め方 |
| --- | --- |
| Issue の「決めること」、実装上の選択 | 推奨案で決めて進める。選んだ案と理由、選ばなかった案を作業中に控え、最後にまとめて報告する |
| コミット(機械検査が通り、検査役の判定が `OK`) | `/dev-commit` のとおり、承認を待たずにコミットする |
| コミット(検査役の判定が `WARN`) | `/dev-commit` の Step 4 のとおり、コミットしてよいかを人に聞く。聞く時機だけを、版の最後の確認にまとめる(それまでは、その差分をコミットしない)。直せる指摘は直して検査をやり直す。直さずに人に聞くものは、その差分のステージを外して作業ツリーに残し、指摘(場所と種類)を控えて、次の作業に進む |
| コミット(検査役の判定が `BLOCK`、機械検査の失敗) | コミットしない。直して、検査をやり直す。`/dev-commit` の Step 4 との違いは、直し方を人に提案して確かめる前に直すことと、指摘を人に見せる時機で、指摘(場所と種類)と直し方は、最後の報告に含める。直し方に人の判断が要るときは、その場で人に聞く |
| push、PR の起票・編集、Issue の起票・編集 | 版の最後にまとめて、人の確認を取る(`/dev-pr`。PR を出さない push は `/dev-push`)。それまでは行わない |
| マージ、タグ、Release、デプロイ | 人の明示の指示ごとに行う(`/dev-release`)。版の最後の確認には含めない |
| 方針として人が確定させるもの(仕様を足す判断、公開、ライセンス、取り返しのつかない操作、Issue の範囲を大きく超える変更) | その場で人に聞く |
| 新しい画面やモード | `CLAUDE.md` のとおり、実装の前に短い仕様を書き([画面の仕様のひな形](../../../docs/ui-spec-template.md))、人の承認を得てから作る |

推奨案で決めるのは、Issue の本文の「決めること」と、Issue の範囲の中の実装上の選択に限る。手戻りが出ても、推奨案で進めるほうを選ぶ。

## Step 1. 着手

1. `npm run status` で、開いたマイルストーンと未完了の Issue、開いた PR(依存の更新を含む)、作業ツリーを確かめる。
2. 版の作業ツリーを作る(`CONTRIBUTING.md` の「並行する作業」)。ブランチ名は `<prefix>/#<Issue番号>-<短い説明>` で、版のブランチは説明に版を使う(例: `feat/#123-v0.99.0`)。
3. 版の Issue の本文を読み、進める順を決める(前提になる Issue を先に。実データや外部に触れる作業は最後)。
4. 依存の更新の PR があれば、この版のブランチに取り込む対象に入れる(`CONTRIBUTING.md` の「依存の更新」)。

## Step 2. 実装とコミット

Issue ごとに、実装 → lint / 型検査 / テスト → `/dev-commit` の順で進める。

- 検査役の `WARN`・`BLOCK` を受けたら、その場で受け箱に記録する(`node scripts/lessons.ts add`。`docs/lessons-workflow.md`)。版の終わりにまとめて書かない。
- 検査の入力(`.drafts/inspect/`)は、走っている検査役がすべて終わってから、作り直す・片づける。
- 文書に数・範囲・名前を書くときは、定義元の定数・関数を開いて照合してから書く。外部の仕様の数値は、公式の文書で確かめる。
- 決めたこと(Issue ごとに、選んだ案と理由)と、つまずいたことを、作業中に控える。最後の報告の材料にする。

## Step 3. 版の締めの準備

1. ルートで、lint・型検査・テスト・ビルド・E2E(画面に触れた版)を通す。
2. `data/release-notes.json` に、版のエントリを足し(`npm run check:release-notes`)、`/dev-commit` でコミットする。
3. `/dev-pr` の Step 0〜4 で、PR の下書きを作り、機械検査と検査役を通す(承認の依頼は、次の Step で行う)。

## Step 4. 人の確認(コンソールと確認用のページ)

push と PR の作成の前に、次の 2 つで確認を出し、承認を待つ。

- **コンソールの報告**: 範囲(コミット数、作者)、PR の下書きの全文(タイトルと本文)、検査の結果(場所と種類だけ)、
  決めたことの一覧、保留した `WARN`(指摘の場所と種類、コミットしてよいかの問い)、残っている確認事項。
  Issue も起票するときは、Issue の下書きの全文、一覧(マニフェスト)の内容、`--dry-run` の出力も見せる。
  承認の時点で、`/dev-pr` の Step 5 のとおり、下書きのハッシュと、PR の範囲の末尾のコミットとコミット数を控える(一覧から Issue を投稿するときは、封印する)。
- **確認用のページ**(外部のサービス上に置く、人だけが見られる非公開の HTML のページ。元のファイルは `.drafts/` に置き、コミットには含めない): 版の目的、Issue ごとの変更と決めたこと(選ばなかった案を含む)、
  つまずいた点と次から気をつけること、いまの数字(テスト・E2E)、残っている確認事項(デプロイの前後に確かめること、人の操作が要ること)。
  コンソールの報告と同じく、値(認証情報、環境固有の値、個人情報)を書かない。出す前に、本文を `.drafts/` に置き、`node scripts/check-pr-secrets.ts <ファイル>` を通す。

保留した `WARN` の差分は、人の答えを受けてからコミットする。コミットしてよいと言われても、ステージし直した差分は検査のときと同じとは限らないので、`/dev-commit` の Step 0 からやり直す(検査をやり直して、人が答えた指摘と同じ `WARN` だけが出たなら、その答えに従ってコミットする。違う指摘が出たら、もう一度人に聞く)。直すと言われたら、直して検査をやり直す。
コミットが増えたら、PR の下書きと範囲の検査をやり直してから、承認を求め直す。

PR を出さずに push だけするときは、`/dev-push` の確認(範囲の全コミット、作者、ブランチ名の検査と、人の承認)を同じく最後にまとめて行う。

承認を得たら、`/dev-pr` の Step 6 のとおり、控えた値と一致することを確かめてから、push と PR の作成(と Issue の投稿)を行い、CI の結果を報告する。
承認のあとに下書きや範囲が変わったら、push も投稿もせず、検査と確認をやり直す。マージ以降は、人の指示で `/dev-release` を使う。
