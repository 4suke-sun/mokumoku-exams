# /dev-release — 版のリリースの手順を実行する

手順の本体は `scripts/release.ts` にある。このスキルは、**人の明示の指示の確認**と、**スクリプトの呼び出し**、**版の締めの振り返り**だけを担う。
手順そのものは、このスキルに書き写さない。

このスキルは、モデルが自分の判断では起動しない(`disable-model-invocation: true`)。マージ・タグ・削除は取り消せないので、人が `/dev-release` と打ったときだけ動く。

## 守ること

- 人の明示の指示(「マージして」「リリースして」など)がないときは、マージ・タグ・ブランチの削除を実行しない。
  指示は、その版の分に限る。次の版には持ち越さない。
- `--force` 系の push、`main` への直接の push、履歴の書き換えはしない。
- スクリプトの呼び出しは、`.claude/settings.json` の確認必須(`ask`)に入っている。権限の確認が出たら、許可を人に求める。
  権限の確認を省く動作モードでは、確認にならない。人の指示を、このスキルの中で必ず確かめる。

## Step 1. マージの前の確認(何も変えない)

```sh
node scripts/release.ts <PR の番号> --check
```

CI の全ジョブが成功か、変更がなく動かなかった(skipped、neutral)で、`ci-ok` が成功し、PR が `CLEAN` で、リリースノートの先頭が対象の版であることを確かめる(リモートの情報の取得 `git fetch` で、ローカルの追跡の参照とタグは更新するが、GitHub とファイルの内容は変えない)。
失敗したら、その段階を人に報告して止まる(CI を待つ、競合を解消する、など)。

## Step 2. 実行

人の明示の指示があるときだけ:

```sh
node scripts/release.ts <PR の番号>
```

次を順に行い、段階ごとの結果を表示する。再実行してよい(目的の状態にある段階は「済み」として次へ進む)。

1. マージ(マージコミット。確認した PR の先頭のコミットに固定する)。
2. マージコミットの `data/release-notes.json` の先頭が、対象の版であることの確認。
3. マージコミットへの軽量タグの作成と push。
4. タグの push で `release-tag.yml` が作る Release を、作られるまで待って確認。
5. 版と同名のマイルストーンを閉じる(未完了の Issue があれば、閉じずに止まる)。
6. 作業ブランチの削除(リモートとローカル)。保護対象の名前、フォークからの PR、リモートの先頭が PR の先頭から動いたブランチ、別の作業ツリーで出ているブランチ、`origin/main` に含まれないブランチは、消さずに表示する。
7. 確認の一覧: `Closes` の Issue が閉じていること、`main` が最新であること。

失敗した段階(未完了の Issue が残るマイルストーンを含む)で止まり、どの段階まで終えたかが表示される。原因を直して、同じコマンドを再実行する。

## Step 3. 結果の報告

表(段階・結果・内容)を、そのまま人に見せる。「省略」「失敗」があれば、理由と次の手を添える。

## Step 4. 版の締めの振り返り(必ず行う)

手順の本体は `docs/lessons-workflow.md`。ここでは、版の締めで行うことだけを書く。

引っかかった場面(検査役の指摘、BLOCK・WARN、差し戻し、CI の失敗、サブエージェントの勘違い、手戻り)は、作業中にその場で、受け箱へ足してある
(`node scripts/lessons.ts add …`。置き場は `.git` の共有領域で、作業ツリーをまたいで合算される)。版の締めで、まとめて思い出そうとしない。
足し忘れに気づいたら、この時点で足す。

1. **計測を足す**: この版で使ったサブエージェントの所要時間とトークン(完了の通知の値)を、`node scripts/metrics.ts agent <役> <ミリ秒> <トークン>` で足す。`npm run metrics` で、どこが重いかを見る。
2. **状況を確かめる**: `node scripts/lessons.ts list` で対処していない種類と件数を、`node scripts/lessons.ts repeats` で繰り返し(同じキーが 2 回以上。版をまたいで数える)を見る。
3. **棚卸し**: 似たキーをまとめる。不要になったルール(機械検査で置き換わったもの、使われないもの)の削除候補を挙げる。
4. **提案**: 「繰り返し」を人に見せ、「一緒に起票しますか」と聞く。起票するものは `node scripts/lessons.ts draft` で下書きを `.drafts/issues/` に作り、
   `/dev-pr` の手順(検査と承認)で起票する。一度きりの引っかかりは、提案に含めず、受け箱に残す。
   受け箱から起票する Issue のラベルなどの決まりは、`docs/lessons-workflow.md` の「繰り返しと Issue の候補」を参照する。
5. **昇格先を決める**: 強い順に、機械検査・テスト・フック、チェックリストと役ごとの共通の決まり・エージェントの定義、スキルの手順、`docs/app/lessons/`、`CLAUDE.md`
   (どのタスクでも毎回効くことだけ。最後の手段)。ルールやスキルの書き換えは、勝手に行わず、通常の commit と PR の流れで人の確認を経る。
6. **締める**: 起票した、または昇格した種類は、`node scripts/lessons.ts close <キー> <行き先>` で対処済みにする(これより前の件は数えない)。
7. **回帰**: ルールやエージェントの定義を変えたときは、`docs/lessons-regression.md` の課題を流して、直っていることを確かめる。

サブエージェントの勘違いは、種類(古い入力を読んだ、署名の指示に引きずられた、禁止された語・出来事を語る書き方をした、範囲外を指摘した・編集した、既存の本文を書き換えた、検査の報告に値を引用した、など)を
キーにそろえて記録する。同じ種類が続くときは、そのエージェントの定義か共通の決まりを直す。
