# /pipeline-run — 作問パイプラインを回す

`npm run pipeline -- <段階> <資格コード>` の CLI は、依頼を書き、出力を検査して取り込む(ADR 0009)。モデルを呼ぶのは、Claude Code のエージェントである。
この往復を、通して回す手順をここに置く。段階ごとの規則と理由コードは、[問題を作る手順書](../../../docs/question-production.md)と、段階別の文書にある。この手順に書き写さない。

このスキルは、モデルが自分の判断では起動しない(`disable-model-invocation: true`)。エージェントを多数呼び、費用がかかるので、人が `/pipeline-run <資格コード> [対象の段階]` と指示したときだけ動く。
対象の段階を省くと、収集から人の確認の手前まで進める。**検証役の評価(`eval`)と、公開している問題の判定(`judge`)と判定役の評価(`judge-eval`)は、この既定の流れに含めない**(費用のかかる別枠で、人が指示したときだけ行う)。

## してはいけないこと

- コミット、push、PR の作成、Issue の起票はしない。台帳(出典・事実カード・来歴・判断の記録)の変更は、作業ツリーに残し、`/dev-commit` 以降の手順に渡す。
- 人の判断(承認・保留の解除・却下)を、代わりに書かない。`draft <資格コード> --decide` に渡すシートは、人が書く。
- `pipeline-work/` の本文(取得した本文、依頼、出力)を、報告や会話に貼らない。報告は、種類・場所・件数・理由コードだけにする。
- 資格マスタ・収集の計画・許可ドメインを、勝手に書き換えない。足りないものは、人が足すものとして示して止まる。

## Step 0. 前提を確かめる

人が指示した資格コードで、次を確かめる。足りないものがあれば、**何を誰が足すか**を示して止まる(通常の PR で直す)。

1. 資格コードの形と、資格マスタ(`data/exams.json`)にあること。`npm run pipeline -- status <資格コード>` が、終了コード 2 なら、資格コードの形か、マスタの項目の誤り。
2. 資格マスタに、分野(`domains`)と本番の出題数(`officialQuestionCount`)があること(出題計画と下書きに要る)。
3. 収集の計画(`packages/pipeline/plans/<資格コード>.json`)があること。
4. 出典の URL のドメインが、許可の一覧(`ALLOWED_REFERENCE_HOSTS`)にあること。
5. エージェントの定義(`.claude/agents/` の 7 役)が読めること。`status` が、役のモデルと定義のハッシュを出す。読めなければ、`エージェントの定義の誤り` を出す。

## Step 1. 状態を見る

`npm run pipeline -- status <資格コード>` で、段階ごとの状態を見る。読むだけで、何も書かない。
依頼待ち・取り込み待ち・通過・保留・不採用の件数、理由コードごとの件数、再検証の印、計画の項目ごとの未達の理由、役のモデルと定義のハッシュが出る。
最後の「見積もり」の行が、**依頼待ちの件数 × 役のモデル**で、これが予算の見かたである。トークンも費用も測らない(測れない)。1 回の実行の件数の上限は、設定の `maxItemsPerRun` である。

## Step 2. 段階の順に回す

次の順に進める。人が対象の段階を指定したら、その段階の分だけ行う。

| 段階 | 依頼を書く | 役(エージェント) | 取り込む |
| --- | --- | --- | --- |
| 収集 | `collect <資格コード>` | なし(取得は CLI) | なし |
| 試験ガイド | `collect <資格コード>`(依頼が出る) | `guide-extractor` | `collect <資格コード> --import-guide` |
| 出典の候補(任意) | `collect <資格コード> --candidates` | `source-scout` | `collect <資格コード> --import-candidates` |
| 事実カード | `facts <資格コード>` | `fact-extractor` | `facts <資格コード> --import` |
| 出題計画 | `plan <資格コード>` | なし | なし |
| 下書き | `draft <資格コード>` | `question-drafter` | `draft <資格コード> --import`、続けて `draft <資格コード> --check` |
| 検証(再導出) | `verify <資格コード>` | `question-verifier` | `verify <資格コード> --import` |
| 検証(解説の確認) | `verify <資格コード>`(もう一度) | `question-verifier` | `verify <資格コード> --import` |
| 直し(任意) | `draft <資格コード> --revise` | `question-reviser` | `draft <資格コード> --import`、続けて `draft <資格コード> --check`。直した下書きは、検証からやり直す |

1. 依頼を書く CLI を呼び、報告された依頼のファイル(`...の依頼: <パス>`)を集める。依頼が 0 件なら、その段階は済み(または前の段階を待っている)。
2. **依頼ごとに別のエージェントを起動する。** 各エージェントには、**依頼のファイルの場所だけ**を渡す(本文や指示を足さない)。同時に起動する数は、4 までにする。
3. 出力がそろったら、取り込みの CLI を呼ぶ。報告される停止(`...の取り込みの停止: <鍵> <理由コード>`)を確かめる。
4. 停止した依頼(`output-invalid` など。出力は CLI が消す)は、**同じ依頼を、同じ役のエージェントに出し直させる**。理由コードだけを伝え、本文は伝えない。出し直せる回数は、設定の `facts.maxAttempts`・`draft.maxAttempts`・`verify.maxAttempts`・`candidates.maxAttempts`・`eval.maxAttempts`・`judge.maxAttempts` までである。
5. `request-stale` は、依頼のあとに入力かエージェントの定義が変わったことを示す。失敗に数えない。依頼を書く CLI を呼び直して、新しい依頼を出す。
6. 取り込みの結果、次の段階の依頼が出るなら(検証の再導出のあとの解説の確認など)、同じ手順を繰り返す。

直し(保留の下書きを、ブラッシュアップ役に直させる)は、既定の流れに含めない。人が `revise` と指示したときだけ、検証のあとに行う。

試験ガイドが未取り込みでも事実カードの依頼は出るが、分野の出題範囲が空のまま抽出されるので、試験ガイドの取り込みを先に済ませる。下書きの取り込みが済むまで、検証の依頼は出ない。

## 検証役の評価

検証役の指示かモデルを変えたときは、`eval <資格コード>` で評価を流す(人が `/pipeline-run <資格コード> eval` と指示したときだけ)。手順は検証と同じ形(依頼 → `question-verifier` → 取り込み。再導出のあとに解説の確認)で、
出し直せる回数は設定の `eval.maxAttempts` までで、上限に達した依頼は出し直さず(止めたものとして数える)、「止まる条件」のとおり人に見せる。
レポート(`pipeline-work/eval/<コード>/report.md`)を人に見せ、目標を下回ったときは、変更を取り入れない。測れなかった項目があるときは、評価用のデータを増やすこと(承認した下書きを増やし、`dataset.json` を作り直す)を人に示す([検証役の評価](../../../docs/evaluation.md))。

## 公開している問題の判定

公開している選択式の問題を、資格別の判定の基準に照らして判定するときは、`judge <資格コード>` を回す(人が `/pipeline-run <資格コード> judge` と指示したときだけ)。手順は、依頼 → `question-judge` → 取り込みである(判定の基準と理由コードは [書き方の指針](../../../docs/exam-style/README.md) の「判定の基準」)。

1. `npm run pipeline -- judge <資格コード>` で、問題ごとの判定の依頼を書く。同じ入力は出し直されない。件数の上限(`maxItemsPerRun`)で止まったら、取り込みのあとに続きを書く。
2. 依頼のファイルごとに、別の `question-judge` を起動する(同時は 4 まで。依頼のファイルの場所だけを渡す)。
3. `npm run pipeline -- judge <資格コード> --import` で取り込む。停止(`output-invalid`、`location-unknown`、`publish-with-findings` など)は、同じ依頼を出し直させる(出し直せる回数は `judge.maxAttempts` まで)。
4. 判定の結果(`pipeline-work/judge/<コード>/results.json`)と、要約(判定ごとの件数、理由コードごとの問数)を人に見せる。非公開へ移すのは、結果を人が読んだあとの `unpublish <資格コード>`(人が指示したときだけ。`data/` を変える)で、この手順の外である。

判定役の指示かモデル、判定の基準を変えたときは、`judge-eval <資格コード>` で評価を流す(人が `/pipeline-run <資格コード> judge-eval` と指示したときだけ。手順は `judge` と同じ形で、取り込みは `judge-eval <資格コード> --import`)。
レポート(`pipeline-work/judge-eval/<コード>/report.md`)を人に見せ、目標を下回ったときは、変更を取り入れない([判定役の評価](../../../docs/evaluation.md))。

## 止まる条件

次のいずれかで、その段階を止め、`status` の表示を人に見せる。

- 再試行の上限(`再試行の上限`)、件数の上限(`件数の上限`)。件数の上限は、もう一度実行すると続きから進む。
- 出題計画の「事実カードの未処理」(終了コード 1)。事実カードを抽出していない出典が残っている。facts を、件数の上限が出なくなるまで依頼・抽出・取り込みで回し直してから、plan を実行し直す。facts が「事実カードの本文なし」を出す出典は、回し直しても減らないので、収集をやり直してから回す。
- 入力の誤り(終了コード 2)、内部の誤り(終了コード 3)。
- 検査の失敗(終了コード 1)で、人が直すもの(台帳の誤り、節を取り出せない `検証の節なし`、来歴の誤りなど)。

**保留や、再試行の上限に達した依頼があるときは、ほかの依頼を進めてから止める。** 上限に達した依頼は、出し直さない(人が原因を直す)。ほかの依頼は、止めずに最後まで回す。
入力の誤り(2)と内部の誤り(3)は、すぐ止める(続けても意味がない)。

## 人の確認で止まる

検証まで済んだら、人の確認で止まる。

1. `npm run pipeline -- draft <資格コード> --review` を呼び、確認用の表(`pipeline-work/draft/<コード>/review.md`)と、判断を書き込むシート(`review-sheet.json`)の場所を示す。
2. 人に、通過・保留の下書きの判断(`approve` / `release` / `reject`)をシートに書き、`draft <資格コード> --decide` で取り込むよう求める。保留の理由コード(`verify:*`・`review:*`・`ambiguous:*`)と、検証の指摘の場所、検証役が読む根拠の節の場所は、表に載る。保留の下書きは承認だけで保留も解けること(解除を別に書かなくてよい)、判断の前に直しの依頼(`draft <資格コード> --revise`)で直させられることも伝える。抜き取りに切り替えているときは、通過の下書きのうち選んだものだけが載る(手順書の「8.1」)。
3. 判断が記録されたら(`--review` の「未済」が 0 件になったら)、書き出しへ進む: `npm run pipeline -- export <資格コード>`。作業ツリーの `data/` に追加の分だけを書く(ADR 0020)。出典には、台帳に題がある出典だけ、その公式ページの題が付く(台帳に題がない出典は、題なしで書き出して報告する)。そのため、`collect <資格コード> --titles` で台帳に題を足し、`export <資格コード> --titles` で問題の出典に足す。コミットはしない。
4. 書き出したら、`data/` の差分と、差分レポートの場所(`pipeline-work/export/<コード>/report.md`)を示して終わる。

## 再開

再開は、同じ手順の繰り返しである。依頼の鍵と、取り込み済みの記録(各段階の状態のファイルと、出典の台帳の `guide`、事実カードの台帳の `extracted`、下書きの `verification`)で、**済んだ依頼は出し直されない**。
途中で止まったら、`status` を見て、Step 2 を続ける。エージェントの定義を変えたときは、依頼の鍵が変わるので、記録のあるものは出し直される。

## 手作業で残る部分

- 出典の候補の一覧(`pipeline-work/candidates/<コード>/` の下)を見て、使う URL を収集の計画の `sources` と `scope.prefixes` に足すこと。候補は計画に自動では入らない。
- 資格マスタ・収集の計画・許可ドメインの追加と直し(通常の PR)。
- 事実カードの抜き取りと、保留の判断。人の確認の判断(承認・解除・却下)。
- 台帳・来歴・判断の記録のコミットと PR(`/dev-commit`、`/dev-pr`)。
