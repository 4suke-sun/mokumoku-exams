# 事実カードの作法と運用手順

作問パイプラインの 2 つ目の段階(事実カード)の手順です。収集した公式の一次情報から、問題の根拠になる主張を 1 件ずつ取り出し、
本文と機械的に照合して、先の段階へ進めてよいものだけを残します。
判断の理由は ADR 0006〜0009 にあり、出典の扱いは[出典と権利の方針](./source-policy.md)、収集の手順は[一次情報の収集と台帳の運用](./source-collection.md)にあります。

## 1. 事実カードとは

出典の本文から取り出した、**主張 1 件**を持つカードです。資格ごとに 1 つの JSON(`packages/pipeline/facts/<コード>.json`)をコミットします。
`<コード>` は、試験コードを英小文字にしたものです。

| 項目 | 内容 |
| --- | --- |
| `id` | カードの ID。出典・見出し・主張・分野から決まるので、同じ抽出なら同じ ID になる(CLI が付ける) |
| `claim` | 主張。言い換えた短い記述(日本語で 200 文字以内、英語で 35 語以内) |
| `sources` | 根拠。出典の URL(許可したドメインの https)、節の名前、アンカー、本文のハッシュ。重複をまとめると増える(10 件まで) |
| `scope` | 適用範囲。対象の版(`edition`)とリージョン(`region`)。どちらも任意 |
| `confidence` | 確度。`high`・`medium`・`low` |
| `domain` | 資格マスタの分野のコード。マスタにない分野は不採用になる |
| `scopeItems` | 試験ガイドの出題範囲の項目の添字(0 から)。カバレッジの集計に使う |
| `status` | `passed`(先の段階へ進める)・`held`(人の確認待ち)・`rejected`(不採用) |
| `reasons` | 保留・不採用の理由コード |

台帳の末尾の `extracted` には、抽出を済ませた出典と本文のハッシュが入ります。同じ入力では、抽出を依頼し直しません。

**本文は持ちません。** 持つのは、リンク、言い換えた主張、見出し、30 文字以内の短い引用、本文のハッシュだけです。
本文の写しとして不採用にしたカードも、主張の文は保存せず、固定の文に置き換えます。

## 2. 作法

- **主張の粒度**: 1 件の主張に、1 つの事実だけを入れます。「A は X で、B は Y」は 2 件に分けます。数値や条件が主張の一部なら、一緒に書きます。
- **言い換え**: 本文を写さず、自分の言葉で短く言い換えます。語順や言い回しをなぞりません。サービス名・機能名・API 名・設定値は、本文の表記のまま書きます。
  本文と 30 文字を超えて連続して一致すると、写しとして不採用になります(全角半角・大文字小文字・空白の違いはそろえて比べます)。
  英語の本文を日本語に言い換えても、数値とラテン文字の語(大文字・数字を含まない一般語も数えます)が 8 個以上(異なる語が 4 個以上)あり、本文の中で、その語数の 4 倍以内の範囲に同じ順で並ぶ主張も、写しとみなします。
  この検査は、試験ガイドの言い換え、事実カードの主張、問題の下書きで同じ関数(`packages/pipeline/src/shared/copy.ts` の `detectCopy`)を使います。
- **数値と固有名詞**: 主張に書く数値と、サービス名のような固有名詞(ラテン文字で、大文字か数字を含む語)は、アンカーの節に実際にあるものだけにします。
  なければ、不採用になります。「1 つの」「2 つ」のような数えことばの数は照合しません。
- **適用範囲**: 本文が特定の版やリージョンに限ると述べているときだけ、`edition`・`region` を書きます。書かなければ、出典の対象(台帳の `target`)が入ります。
  版が違うだけの食い違いは、矛盾ではなく、適用範囲の違いとして両方を残します。
- **確度**: `high` は本文が明言している事実、`medium` は複数の記述や条件から読み取ったもの、`low` は本文の記述があいまいなものです。
  まとめた重複のカードは、低いほうの確度になります。
- **アンカー**: 見出しと短い引用の組です。`heading` は節の見出しの `id`(なければ見出しの文)、`quote` はその節にそのまま出てくる 30 文字以内(英語は 10 語以内)の引用です。
  節は、その見出しから、同じか上の深さの次の見出しの手前までです。下の深さの見出しの内容は、上の節に含まれます。

## 3. 運用手順

コマンドは、リポジトリのルートから実行します。`<試験コード>` は、例えば `AWS-AIB-C01` です。前提は、収集が済んで、台帳に active な出典があることです。

1. **抽出の依頼を書く。** 通信も、モデルの呼び出しもしません。

   ```sh
   npm run pipeline -- facts <試験コード>
   ```

   active な出典ごとに(試験ガイドの出典 `exam-guide` を除く。分野・出題範囲の材料で、事実の根拠にしないため)、`pipeline-work/facts/<コード>/requests/<鍵>.json` に依頼が書かれます。抽出を済ませた出典と、本文がキャッシュにない出典(収集をやり直す)は飛ばします。本文がない出典があると、ほかの出典の依頼は書いたうえで、終了コード 1 で終わります(報告は URL だけで、本文は出しません)。
   1 回に依頼する数は、設定の `maxItemsPerRun` までです。
2. **抽出する。** Claude Code で、エージェント `fact-extractor` に、依頼のファイルを 1 つずつ渡します(出典ごとに別の起動にします)。
   エージェントは、依頼の `outputPath` に候補を書きます。
3. **取り込む。**

   ```sh
   npm run pipeline -- facts <試験コード> --import
   ```

   書かれた候補を、次の順に検査します。通ったものだけが `passed` になり、事実カードの台帳に入ります。
   1. 出力の形、依頼との一致(資格・出典・本文のハッシュ)
   2. 分野が資格マスタにあるか、試験ガイドの項目の添字が範囲内か
   3. 本文の長い写しでないか
   4. 本文との照合(出典が active か、本文のハッシュが台帳の最新と同じか、見出し・引用・数値・固有名詞が節にあるか)
   5. 同じ主張の重複をまとめる
   6. 同じ適用範囲で食い違うカードを、保留にする

   出力の形が違うなど、取り込めなかったときは、理由コードを出して終了コード 1 で終わります。その出典の依頼はそのまま残るので、理由を添えて、同じエージェントにやり直させます。
   やり直せる回数は、設定の `facts.maxAttempts` までです。超えると「再試行の上限」を出し、依頼を出さなくなります。
4. **カバレッジを見る。**

   ```sh
   npm run pipeline -- facts <試験コード> --coverage
   ```

   分野ごとの通過・保留・不採用の件数と、試験ガイドの範囲に対してカードがない項目を報告します。報告は、分野のコードと件数、項目の番号だけで、本文は含みません。
   `data/` は読み取りだけで、変更しません。
5. **レビューレポートを作り、人が抜き取りで確かめる。**

   ```sh
   npm run pipeline -- facts <試験コード> --report
   ```

   `pipeline-work/facts/<コード>/review.md`(と `review.json`)に、件数、分野別の件数、理由の種類ごとの件数、抜き取りの表が書かれます。本文は含みません。
   抜き取りは、分野ごとに最大 `facts.samplePerDomain` 件で、乱数の種 `facts.sampleSeed` が同じなら、同じ入力から同じカードが選ばれます。
   あわせて、`pipeline-work/facts/<コード>/cards.md` に、通過と保留のカードをすべて載せた表(ID、分野、主張、根拠の節、出典の URL、版、リージョン、確度、状態、理由コード)が書かれます。
   保留を解く・却下するときは、[人の判断の記録](./human-decisions.md)に書きます。
6. **台帳をコミットする。** 事実カードの台帳と、人の判断の記録(`packages/pipeline/decisions/`。書いたときだけ)だけをコミットします(`/dev-commit`)。`pipeline-work/` の中身はコミットしません。

どのコマンドも `--dry-run` を受け付けます。書き込みをせず、検査と報告だけを行います。

## 4. レビューの観点

- **抜き取りの見方**: 表のカードごとに、出典の URL を開き、アンカーの見出しの節で、主張が本文と合っているかを確かめます。見るのは、数値、条件(版・リージョン)、否定や例外の見落としです。
  機械の照合は、数値と固有名詞が節にあることしか確かめません。主張の意味が合っているかは、人が確かめます。
- **保留のカード**: 保留の理由は `conflict` です。同じ適用範囲で、同じ固有名詞を持つ似た主張の数値が食い違っています。出典を読み比べ、
  正しいほうを残すか、適用範囲の違いなら `scope` を直します。自動では白黒をつけません。確かめた結果は、[人の判断の記録](./human-decisions.md)に、
  カードごとに `release`(保留を解く)か `reject`(却下)で書きます。次の `facts <試験コード> --import` で反映され、保留に戻りません。矛盾の判定は、名前・数値・文字の似かたによる単純なものなので、
  取りこぼしがあります(別の言い方で矛盾する主張は検出できません)。
- **不採用の理由の読み方**: レポートの理由コードの件数が偏っているところが、抽出の指示や出典の選び方を直す手がかりです。

| 理由コード | 意味 | 見直すところ |
| --- | --- | --- |
| `long-copy` | 主張が本文の長い写し | 言い換えの指示。エージェントの定義 |
| `number-mismatch` | 主張の数値が、アンカーの節にない | 数値の読み違い、アンカーの節の取り違え |
| `term-not-found` | 主張の固有名詞が、アンカーの節にない | 表記の揺れ、別の節の内容 |
| `anchor-not-found` / `quote-not-found` | 見出し・引用が本文にない | アンカーの書き方 |
| `hash-mismatch` / `body-not-cached` / `source-not-active` | 出典の本文が変わった・キャッシュにない・検査に合格していない | 収集をやり直し、抽出をやり直す |
| `unknown-domain` / `scope-item-out-of-range` | 分野が資格マスタにない・試験ガイドの項目の添字が範囲外 | 依頼の `domains` を確かめる |
| `conflict` | 食い違う主張(保留) | 上の「保留のカード」 |

取り込みを止める理由コード: `extract-invalid`(出力の形が違う)、`request-mismatch`(依頼と違う資格・出典・本文)、
`request-stale`(依頼のあとに本文か、エージェントの定義が変わった。依頼を出し直す)、`request-invalid`(依頼のファイルが壊れている)。

## 5. 出典が変わったとき

収集で出典の本文が変わると、その出典を根拠にした事実カードに「再検証が必要」の印が付きます(台帳の `recheck`)。
印の付いたカードは、下書きの依頼の根拠の候補になりません。印が外れるまで、そのカードを根拠にした下書きは来歴の検査を通りません。

1. 収集が済んだら、`facts <試験コード>` で、新しい本文の抽出を依頼します(本文のハッシュが変わったので、再び依頼されます)。
2. 抽出して `--import` すると、その出典から作った古いカードは、新しい抽出に置き換わり、印が外れます。複数の出典を持つカードは、変わった出典の根拠だけが入れ替わります。
3. 置き換えたあとも、重複のまとめと保留の判定は、台帳のカード全体でやり直します。

## 5.1 抽出をやり直すとき

抽出の指示(`.claude/agents/fact-extractor.md` の本文)かモデルを直すと、依頼の鍵が変わるので、記録のある抽出済みの出典も、次の `facts` で依頼し直されます
(鍵は、出典の URL・本文のハッシュ・エージェントの定義のハッシュで決まります。定義の説明文(`description`)だけを直しても、ハッシュは変わりません)。
依頼のファイルには、役の名前・モデルの ID・定義のハッシュ(`agent`)が書かれ、取り込んだ出典(事実カードの台帳の `extracted`)にも同じ記録が残ります(指示の本文は残しません)。
依頼のあとに定義が変わったときは(出力の形を見る前に判定します)、`--import` は結果を取り込まず `request-stale` で依頼を捨てます(失敗の回数には数えません)。`agent` の記録がない古い依頼も、同じく捨てます。
`agent` の記録がない古い抽出済みの出典は、同じ定義とみなして飛ばします。検査だけを直したときなど、同じ出典を抽出し直すには、次のようにします。

1. 事実カードの台帳(`packages/pipeline/facts/<コード>.json`)の `extracted` から、やり直す出典の URL の項目を消します。カードは消しません。
2. `facts <試験コード>` で、その出典の依頼が出ます。抽出して `--import` すると、その出典から作った古いカード(不採用のものを含む)が、新しい抽出に置き換わります。
3. 置き換えたカードを根拠にした下書きは、来歴の検査で止まることがあります([出題計画と下書きの手順](./drafting.md))。

## 5.2 実データでの注意

- 本文を埋め込みのデータ(スクリプトの中の JSON など)で持つページでは、データの側にも節の識別子がある。アンカーにそれを使うと、
  そのページのカードがまとめて `anchor-not-found` になる。抽出の指示は、見出しを HTML の見出しの要素に限る。
  1 つの出典のカードがまとめて落ちたら、見出しの付け方を確かめ、「5.1」の手順で抽出をやり直す([失敗の記録 0008](./app/lessons/0008-anchor-from-html-headings.md))。
- 見出しの文は、文字参照(`&nbsp;` など)を文字に戻してから比べる。
- 矛盾の判定のしきい値(`packages/pipeline/src/facts/dedupe.ts` の `CONFLICT_MIN_SIMILARITY`)は、見逃しや誤った保留の例が見つかったときに、その例を根拠に見直す。
- 試験ガイドのページ(`exam-guide`)は抽出の対象にしないので、技術の事実の根拠には、サービスの文書を収集の計画に足す([出典の収集](./source-collection.md))。

## 6. 規約

- 環境固有の値、個人情報、機密を、事実カードにも、依頼にも、報告にも書きません。
- 取得した本文をコミットしません。本文は `pipeline-work/` だけに置きます。
- 報告は、種類と場所と理由コードと件数だけです。本文や、一致した文字列は出しません。
