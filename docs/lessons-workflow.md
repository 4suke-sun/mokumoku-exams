# 引っかかりの記録と、再発を止める形への昇格

作業中の手戻り(検査役の指摘、BLOCK・WARN、差し戻し、CI の失敗、サブエージェントの勘違い、その他)は、同じ形で繰り返される。
ルール(`CLAUDE.md`、スキル)へ「〜しないこと」を足し続けると、1 つあたりの効きが薄まる。
この文書は、引っかかりを**記録し、数え、できるだけ機械で止まる形へ昇格させる**手順を定める。

流れは次のとおり。

1. 引っかかった場面で、受け箱へ 1 件足す(記録)。
2. 同じ種類のキーが繰り返されたものを、Issue の候補にする(数える)。
3. 版の締めで、候補を人に見せ、起票するか、昇格するかを決める(提案)。
4. 昇格したら、受け箱の種類を対処済みにする(締め)。

## 受け箱

- 置き場は `.git` の共有領域(`mokumoku-lessons-inbox.jsonl`)。リポジトリには入らず、作業ツリーをまたいで合算される。
  検査の台帳(`scripts/inspection-ledger.ts`)と同じ置き場の流儀に従う。
- 操作は `node scripts/lessons.ts`(`npm run lessons -- …`)で行う。

```sh
node scripts/lessons.ts add --key <キー> --who <誰> --cause <原因> --promote <昇格先> --what <起きたこと> --should <本来どうすべきか>
node scripts/lessons.ts list        # 種類のキーごとの、対処していない件数
node scripts/lessons.ts repeats     # 繰り返しの種類(しきい値以上)
node scripts/lessons.ts draft       # 繰り返しの種類ごとに、Issue の下書きを .drafts/issues/ に作り、一覧(manifest.json)へ項目を足す(投稿はしない)
node scripts/lessons.ts close <キー> <行き先>   # 対処済みにする(これより前の件は数えない)
node scripts/lessons.ts closed      # 対処済みにした種類の、キーと行き先と日付(読み取りだけ)
```

### 1 件に書くこと

| 項目 | 内容 |
| --- | --- |
| `key` | 同じ原因なら同じになる短い名前(英小文字・数字・ハイフン、2〜40 文字)。件数を数える単位。既存のキーを `list` で確かめて、近いものは使い回す |
| `who` | 誰の問題か。`main`(メインのセッション)、`subagent`、`human`(人の指示)、`system`(仕組み) |
| `cause` | 原因の分類(下の表) |
| `promote` | 昇格先の候補(下の「昇格先」) |
| `what` | 何が起きたか。200 文字まで、1 行 |
| `should` | 本来どうすべきだったか。200 文字まで、1 行 |

- `what` と `should` に、値(認証情報、環境固有の値、個人情報、入力の本文)を書かない。種類と場所だけにする。
  受け箱は手元にしか残らないが、繰り返しの下書きは Issue の本文になるので、書く時点で一般的な書き方にしておく。
- 版は、ブランチ名の末尾(`-vX.Y.Z`)から自動で付く。

### いつ足すか

引っかかった場面で、その場で足す。版の締めにまとめて書こうとしない(細部を忘れる)。次のものが対象になる。

- 検査役の `BLOCK`・`WARN`、作成役の案の差し戻し。
- CI の失敗、`verify` の失敗で、原因が作業の進め方にあるもの。
- サブエージェントの勘違いや、やり直し(「置いた前提」のずれを含む)。
- 人の指示で手戻りした作業。

一度きりの偶発(外部サービスの一時的な障害など)は、足さなくてよい。迷ったら足す(一度きりなら、繰り返しにならず流れる)。
サブエージェントの終了時に自動で促すフックは、この版では入れない。足し忘れが目立つ場合に、効果を見て検討する。

## 原因の分類

| `cause` | 意味 | 昇格の向き |
| --- | --- | --- |
| `knowledge` | 知識がなかった | 文書、チェックリスト、エージェントの定義に置く |
| `ignored` | 知っていたが守らなかった | 機械検査・テスト・フックへ寄せる(決定的に確かめられるなら必ず) |
| `ambiguous` | 指示が曖昧だった | 依頼の型、スキルの手順、定義の文言を直す |
| `unchecked` | 確認しなかった | 確認を手順に入れる。確認を機械にできるなら機械にする |

### サブエージェントの勘違いの種類

サブエージェントの勘違いは、種類をキーにそろえて記録する。同じ種類が続くときは、そのエージェントの定義か共通の決まりを直す。

| 種類 | キーの例 |
| --- | --- |
| 古い入力を読んだ | `stale-input` |
| 署名の指示に引きずられた | `signature-leak` |
| 禁止された語・出来事を語る書き方をした | `forbidden-wording` |
| 範囲外を指摘した、範囲外を編集した | `out-of-scope` |
| 検査の報告に、見つけた値を引用した | `value-quoted` |
| 既存の本文を書き換えた(編集の依頼で、追記だけのはずが) | `rewrote-existing` |

## 繰り返しと Issue の候補

- 一度きりは、特定の条件下での偶発であることが多い。**同じキーが 2 回以上**(初期値)に達した種類を「繰り返し」として扱う。
  版をまたいで数える(版が違っても、同じキーなら合算する)。
- 「繰り返し」ごとに、`node scripts/lessons.ts draft` が Issue の下書きを `.drafts/issues/lessons-<キー>.md` に作る。
  下書きは `/dev-pr` の形式(1 行目が `# 題`)で、投稿はしない。すでに同名の下書きがあるときは、人が編集した内容を守るため、上書きしない。
  あわせて、作った下書きの項目(`action: create`、`file`、`labels: ["lessons"]`)を、一覧(`.drafts/issues/manifest.json`。`/dev-pr` の Step 1)へ足す。
  一覧にすでに同じ `file` の項目があるときは、書き換えない。すでにあった下書き(上書きしなかったもの)は、一覧に足し直さない(投稿済みかもしれないため)。
  一覧は、起票するものを選んでから使う(起票しない項目は消す)。マイルストーンは付けないので、起票の場で決めて足す
  (版が決まっていない新規の Issue は、マイルストーンの代わりにラベル `later` を足す。決めるまで、`scripts/post-issues.ts` の検査が止める)。
- 受け箱から起票する Issue には、ラベル `lessons`(説明: 受け箱(lessons)由来の Issue)を付ける。受け箱の種類のキーと Issue を、あとから突き合わせるため。
  `draft` が足す一覧の項目に入っているので、一覧から起票するときは、そのまま付く(一覧の封印にも入る)。
  一覧を使わずに起票するとき(単発の Issue)は、起票する人が付ける。
- **版の締め**(`/dev-release` の Step 4)で、対処していない「繰り返し」(版をまたいで数える)の一覧を人に見せ、「一緒に起票しますか」と提案する。
  起票は `/dev-pr` の検査と承認を経る。エージェントが勝手に投稿しない。
- 起票した、または昇格した種類は、`close` で対処済みにする(行き先に Issue の番号などを書く)。これより前の件は数えない。
  対処済みにした種類のキーと行き先は、`closed` で、あとから引ける(受け箱は変えない)。

## 昇格先

昇格先は、強い順に決める。強いものほど、再発を確実に止める。

1. **機械検査・テスト・フック**(`--promote mechanical`): 決定的に確かめられるものは、ここへ置く。「知っていたが守らなかった」は、ここへ寄せる。
2. **チェックリストと、役ごとの共通の決まり、エージェントの定義**(`--promote rules`。`.claude/skills/dev-commit/checklist.md`、`writer-rules.md`、`inspector-rules.md`、`.claude/agents/`)。
3. **スキルの手順**(`--promote skill`): 特定の作業のときだけ読まれる。順序の入れ替え、確認の追加。
4. **`docs/app/lessons/`**(`--promote lessons`): 上のどれにもできない注意書き。1 件 1 ファイル、一般的な形で書く(書式は `docs/app/lessons/README.md`)。
5. **`CLAUDE.md`**(`--promote claude-md`): どのタスクでも毎回効くことだけを置く。最後の手段とする。

ルールやスキルの書き換えは、エージェントに直接させない。通常の commit と PR の流れで、人の確認を経る。

## サブエージェントへの依頼の型

メインがサブエージェントに投げる依頼は、次の 4 項目を含める。新しく依頼を書くときと、サブエージェントへの依頼文を持つスキル(`dev-commit`・`dev-pr`・`dev-push`)の依頼文を見直すときに、この型に合わせる。
既存のスキルの依頼文のうち、検査役への依頼は、作業ディレクトリ・見る対象と、報告の制約(値を引用しない、判定の返し方)を示す。作成役への依頼は、作業ディレクトリ・やること・書き出し先を示すが、報告の制約を示さない。範囲(触ってよい場所と触ってはいけない場所)と完了の条件は、どちらも明示していないものがある。見直すまでの間は、メインが依頼に足す。

| 項目 | 内容 |
| --- | --- |
| ゴール | 何ができれば終わりか(1〜2 文) |
| 制約 | 守ること(書式、禁止、モデルの前提など) |
| 範囲 | 触ってよいファイルと、触ってはいけないファイル |
| 完了の条件 | 返答に何が含まれていればよいか |

サブエージェントの返答の最後に、**「置いた前提」**の欄を入れさせる(1〜3 行。なければ「なし」)。
依頼に書かれていなくて、自分で決めたこと(読んだ範囲、仮定した事実、確かめていないこと)を書く欄である。
メインは、前提がずれていないかを確かめる。ずれていたら、受け箱へ足す(`who=subagent`、種類のキーは上の表)。

共通の決まりは `.claude/skills/dev-commit/writer-rules.md` と `inspector-rules.md` にある。

## 回帰の確認

ルールやエージェントの定義を変えたら、引っかかった作業を小さな課題として流し、直っているかを確かめる。
課題と確かめ方は [lessons-regression.md](lessons-regression.md)。

## 版の締めの棚卸し

版のリリースのあと(`/dev-release` の Step 4)に行う。

1. `node scripts/lessons.ts list` と `repeats` で、対処していない種類と、繰り返しを確かめる。
2. 似たキーをまとめる(同じ原因に別のキーが付いていれば、片方に寄せて記録し直す)。
3. 「繰り返し」を人に見せ、起票するか、昇格するかを決める。
4. 不要になったルール(機械検査で置き換わったもの、使われないもの)を消す候補を挙げる。
5. 決まったものを `close` する。

## 計測

どこが重いか(時間、トークン、再検査の回数)を、手元で測る。記録は `.git` の共有領域にあり、リポジトリには入らない。

```sh
npm run metrics                                    # 集計を表示する
node scripts/metrics.ts agent <役> <ミリ秒> <トークン>   # サブエージェント 1 回分を足す
npm run agent-cost -- --since <日付>               # セッション記録から、エージェントごとのトークンと費用を集計する(下の節)
```

| 対象 | 記録のしかた |
| --- | --- |
| `npm run verify` の段階ごとの時間 | 実行のたびに自動で記録される |
| サブエージェントの所要時間とトークン | 完了の通知に出る値を、`agent` で足す |
| 検査の台帳の判定の内訳 | 台帳(`.git` の共有領域)から集計する |
| 引っかかりの内訳(誰・原因・昇格先) | 受け箱から集計する |
| メインとサブエージェントごとの、モデル別のトークンと費用(見積もり) | Claude Code のセッション記録から集計する(`npm run agent-cost`) |

OpenTelemetry によるテレメトリの出力は、Claude Code の公式の文書で設定を確かめてから検討する。受け側は、手元の収集(無料)から始め、
課金が要る受け側は、必要になってから決める。

### エージェントごとのトークンと費用(セッション記録から)

メインのセッションと各サブエージェントが、トークンと費用をどこで使っているかを、Claude Code のセッション記録(jsonl)から集計する。
費用を減らす変更の前後を、同じ尺度で比べるために使う。コマンドは `scripts/agent-cost.ts`(集計の関数は `scripts/lib/agent-cost.ts`)。

```sh
npm run agent-cost -- --since 2026-10-01                      # 期間の始まりから
npm run agent-cost -- --since 2026-10-01 --until 2026-10-31   # 期間を区切る(どちらもその日を含む。日付は端末の時刻)
npm run agent-cost -- --dir <記録の置き場>                     # 置き場を指定する(複数可。指定したら既定は使わない)
```

終了コードは、引数の誤りが 2、読み込みの失敗(置き場が見つからない、読めないなど)が 1。

**読むもの**

- 置き場の直下の `<セッション ID>.jsonl`(メイン)。
- `<セッション ID>/subagents/` の下の `agent-<ID>.jsonl`(サブエージェント。`workflows/` の下の入れ子を含む)と、同名の `.meta.json`。
  `.meta.json` からは、エージェント定義の名前(`agentType`)だけを読む。
- 退避された記録(`.orphaned-…`、`.superseded-…`)は読まない。

**既定の置き場**

Claude Code の記録は、`~/.claude/projects/`(環境変数 `CLAUDE_CONFIG_DIR` があれば、その下の `projects/`)の下に、
作業ディレクトリのパスの英数字以外の文字を 1 文字ずつ `-` に置き換えた名前(例: `/a/b.c` は `-a-b-c`)の置き場として置かれる。
既定では、リポジトリのルート(`git worktree list` の最初の、主の作業ツリー)と、そのとき存在する各作業ツリーのパスから作った名前に、
同じか、`-` が続くものだけを読む(作業ツリーや、サブディレクトリで動かしたセッション)。名前が英数字で続く別のプロジェクトは読まない。
片づけて `git worktree list` に出なくなった作業ツリーのセッションは、`--dir` で置き場を指定する。
Claude Code は、`cleanupPeriodDays`(既定 30 日)を過ぎた記録を消す。前後比較の値は、集計した時点で、期間・件数・費用の値だけを Issue のコメントに残す。

**集計の規則**

- 同じ `message.id` の行は、`output_tokens` が最大の行を 1 つだけ数える(最初の行の出力は、仮の値のことがある)。
- メインの記録は、`isSidechain` が真の行を数えない(サブエージェントの分は、サブエージェントの記録で数える)。
- モデルが `<synthetic>` の応答は、数えずに件数だけを出す。読めない行・必要な項目がない行は、飛ばして、件数だけを標準エラーに書く。
- キャッシュ書き込みは、5 分と 1 時間を分ける。内訳がない記録は、5 分として数える。
- 期間は、応答の時刻で絞る。起動は、最初の応答が期間に入るサブエージェントだけを数える。

**出力**

- 対象: 期間、メインのセッションの数、サブエージェントの起動の数。
- 費用の内訳: 合計、メイン、サブエージェント(割合つき)。
- メイン: 1 リクエストあたりの平均の読み込み量(入力・キャッシュ書き込み・キャッシュ読み込みの合計)と、そのうちキャッシュ読み込みの割合。
  セッションごとのリクエスト数と読み込み量の、最小・中央・最大(セッションの長さと読み込み量の関係を見る。セッションの識別子は出さない)。
- エージェント定義ごと・モデルごと: 起動、応答、入力、キャッシュ書き込み(5 分・1 時間)、キャッシュ読み込み、出力のトークンと、費用。
- 起動分: 各サブエージェントの最初の応答で読む入力(入力・キャッシュ書き込み・キャッシュ読み込みの合計)のトークンと費用、役の費用に占める割合。
  最初の応答の出力まで含めた割合も並べる。
- サブエージェントの費用のモデル別。

**費用は見積もり**

費用は、トークン数に API の単価を掛けた見積もりで、請求額ではない(出力の末尾にも書く)。
単価は `scripts/data/model-prices.json` に置き、確かめた文書の名前と日付を添える。有効な期間は持たず、いまの単価で見る
(前後比較は、同じ単価表で、前と後を両方流す)。モデルの世代が変わったら、モデルの ID の項目を足し、確かめた日を更新する。
表にないモデルは、費用を出さず「単価なし」として、トークンと件数だけを出す。

**記録を外に出さない**

セッション記録は、リポジトリの外の、手元にだけある。本文(プロンプト、応答、ツールの入出力)を含み、`.env` の値などが入りうる。
コマンドが読むのは、usage、`message.id`、モデルの ID、時刻、`isSidechain`、`agentType` だけで、
出力とエラーに出すのは、エージェント定義の名前、モデルの ID、件数、トークン、費用だけである。
モデルの ID は、`claude-` で始まる形だけをそのまま出し、ほかの形(クラウドの識別子など、環境固有の値を含みうるもの)は「(その他のモデル)」にまとめる(`scripts/lib/agent-cost.ts` の `OTHER_MODEL`)。
記録の本文、パス、セッションの識別子、`.meta.json` の説明文は、出力にも、エラーにも、テストのデータにも出さない。
結果を Issue のコメントなどに貼るときも、期間・件数・費用の値だけにする。

**手で足す計測との関係**

`agent` で手で足す計測(上の表)とは併用する。`scripts/metrics.ts` と `npm run metrics` は変えない。
`verify` の段階ごとの時間、検査の台帳の内訳、受け箱の内訳は、記録元がセッション記録と別なので、置き換えられない。
版の締めの手順(`/dev-release` の Step 4 の「計測を足す」)も、いまは変えない。
手で足す計測と併用し、数回の版の締めで傾向が合うことを確かめてから、手で足す操作を外すかを別に決める(#417 もそのときに見直す)。

### 測定の例

一度測ったときの値(`npm run metrics` の出力から抜粋。値は環境で変わる)。

```text
## verify の段階ごとの時間(平均 / 最大 / 実行回数 / 失敗)
- test(scripts): 132.8s / 137.1s / 4 / 3
- test(app): 34.7s / 34.7s / 1 / 0
- build(app): 7.8s / 7.8s / 1 / 0
- test(infra): 6.3s / 6.3s / 1 / 0
- typecheck: 3.7s / 4.9s / 4 / 0
- (check:*、lint、validate:data は、いずれも 1 秒前後)

## サブエージェントの役ごとの時間とトークン(平均の時間 / 平均のトークン / 回数)
- inspector: 52.7s / 40852 / 4
- inspector-deep: 25.4s / 38005 / 2
- commit-writer: 16.1s / 24648 / 2
- draft-writer: 20.0s / 18285 / 1

## 検査の台帳の判定の内訳
- inspector: OK 2 / WARN 0 / BLOCK 0
- inspector-deep: OK 1 / WARN 0 / BLOCK 0
- mechanical: OK 2 / WARN 0 / BLOCK 0
```

この測定から読み取れること。

- **重いのは `test(scripts)`**。ほかの段階の合計の数倍かかる。`scripts/` のテストは子プロセスと一時のリポジトリを多く作るので、
  負荷の高い環境では、上限(ルートの `vitest.config.ts` の `SCRIPTS_TEST_TIMEOUT_MS`)に近づく。子プロセスを多く起こすテストは、上限に余裕を持たせるか、起動回数を減らす。
- **役ごとでは、`inspector` が時間もトークンも最も多い**。差分が大きいほど増えるので、検査の入力(`.drafts/inspect/`)を絞ることが効く。
- **再検査の回数**は、台帳の判定の内訳と、受け箱の `unchecked`・`ignored` の件数で見る。
