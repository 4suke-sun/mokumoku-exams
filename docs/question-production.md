# 問題を作る手順書

作問パイプライン(`packages/pipeline`)で、資格に問題を足す手順を、収集から書き出し、PR を出すときの確認まで、1 本にまとめた文書です。
段階ごとの詳しい規則と、判定・理由コードの表は、段階別の文書にあります。この文書は、順序と、人が確かめるところと、各段階の入口だけを示します。

| 段階 | 詳しい手順 |
| --- | --- |
| 収集 | [一次情報の収集と台帳の運用](./source-collection.md) |
| 事実カード | [事実カードの作法と運用手順](./fact-cards.md) |
| 出題計画・下書き・人の確認・書き出し | [出題計画と下書きの手順](./drafting.md)、[作問のスタイルガイド](./question-style.md) |
| 人の判断の記録 | [人の判断の記録](./human-decisions.md) |
| 出典の扱い | [出典と権利の方針](./source-policy.md) |
| 問題データの形と検査 | [問題データの仕様](./data-spec.md) |

パイプラインそのものを開発する手順は[作問パイプラインの進め方](./pipeline-workflow.md)、問題を手で書いて足す手順は[資格を追加する手順](./adding-an-exam.md)にあります。

## 1. 全体の流れ

```text
収集 → 事実カード → 出題計画 → 下書き(解説を含む) → 検証 → 人の確認 → 書き出し → PR
```

- コマンドは、リポジトリのルートから `npm run pipeline -- <段階> <試験コード> [オプション]` で実行します。`<試験コード>` は、例えば `EX-SMP-XX` です。
- モデルを使う段階(試験ガイドの抽出、事実カードの抽出、下書き、検証)は、Claude Code のエージェントが実行します(ADR 0009)。CLI は、依頼の用意と、出力の検査・取り込みだけを行います。
- 収集の取得、事実カードの依頼、下書きの依頼、検証の依頼は、1 回に扱う件数が設定の `maxItemsPerRun` までです。上限に達したら「件数の上限」を出して止まり、もう一度実行すると続きから進みます(収集は、同じ日のうちに再実行したときだけ、取得済みの出典を飛ばします)。取り込み・検査・確認・書き出しには、この上限はありません。
- どのコマンドも `--dry-run` を受け付けます。書き込みをせず、検査と報告だけを行います。
- 終了コードは、0 が成功、1 が止めたもの・検査の失敗、2 が入力の誤り、3 が内部の誤りです。

### 1.1 通して回す: `pipeline-run` スキルと `status`

人が `/pipeline-run <試験コード> [段階]` と指示すると、メインのセッションが、前提の確認、依頼の書き出し、依頼ごとのエージェントの同時起動、取り込み、停止した依頼の出し直しを、段階の順に行います(手順は `.claude/skills/pipeline-run/SKILL.md`)。

- 前提の確認で足りないもの(資格マスタの分野・出題数、収集の計画、許可ドメイン)は、人が足すものとして示して止まります(通常の PR で直します)。
- 同時に起動するエージェントは 4 までです。依頼ごとに別の起動にし、渡すのは依頼のファイルの場所だけです。
- 停止した依頼は、同じ役のエージェントに出し直させます。回数の上限(`facts.maxAttempts`・`draft.maxAttempts`・`verify.maxAttempts`)に達した依頼は、出し直しません。
- 止まる条件は、再試行の上限、件数の上限、入力の誤り(終了コード 2)、内部の誤り(3)、人が直す検査の失敗です。保留や上限に達した依頼があるときは、ほかの依頼を進めてから止め、入力の誤りと内部の誤りは、すぐ止めます。止まるときは、`status` の表示を人に見せます。
- 検証まで済むと、人の確認で止まります。確認用の表を示し、判断の記録(`--decide`)を人に求めます。判断が記録されたら、書き出しへ進みます(作業ツリーの `data/` に書くところまで)。
- コミット・push・PR はしません。台帳などのコミットは、`/dev-commit` 以降の手順に渡します。
- 再開は、同じ手順の繰り返しです。依頼の鍵と取り込み済みの記録で、済んだ依頼は出し直されません。

`npm run pipeline -- status <試験コード>` は、段階ごとの状態を表示します(読むだけで、何も書きません)。

| 表示(`状態: …`) | 内容 |
| --- | --- |
| `収集` / `試験ガイド` / `再検証の印` | 出典の数、試験ガイドの取り込みの有無と依頼待ち・取り込み待ち、再検証の印の件数 |
| `事実カード` / `下書き` / `検証` | 依頼待ち(依頼のファイルがあり、出力がない)、取り込み待ち(出力がある)、通過・保留・不採用の件数。下書きは書き出し済み(来歴に問題 ID がある)、検証は合格・保留・不採用・解説の確認待ち・検証前 |
| `事実カードの理由` / `下書きの理由` / `検証の理由` | 保留・不採用の理由コードごとの件数 |
| `未達` | 計画の項目ごとの、満たせなかった理由(`no-facts`・`max-rounds`・`max-attempts`) |
| `役` / `見積もり` | 役のモデルと定義のハッシュ。依頼待ちの件数 × 役のモデル、1 回の実行の件数の上限(`maxItemsPerRun`) |

予算は、件数と役のモデルの表示にとどめます。モデルを呼ぶのはエージェントで、CLI はトークンも費用も測れません。
読めないファイルがあると、場所だけを報告して、終了コード 1 で終わります。出力に本文は含まれません。

## 2. 資格を足すとき: 手作業とパイプラインの分担

| 部分 | 誰が | 内容 |
| --- | --- | --- |
| 資格コードと資格マスタの 1 件 | 人(手作業) | `data/exams.json` に足します。問題がそろうまでは `status: "coming-soon"`(近日公開)にします。決めることと手順は[資格を追加する手順](./adding-an-exam.md)の「1」と「3」の手順 1 |
| 出典のドメイン | 人(手作業) | `ALLOWED_REFERENCE_HOSTS` と `REFERENCE_HOST_VENDORS` に足します。[出典と権利の方針](./source-policy.md)の「4. 許可するドメインを追加する手順」 |
| 収集の計画 | 人(手作業) | `packages/pipeline/plans/<コード>.json` を書きます。[収集](./source-collection.md)の「2」の手順 2 |
| 収集 → 事実カード → 出題計画 → 下書き → 書き出し | パイプライン(エージェントと CLI) | この文書の「4」〜「9」 |
| 事実カードの抜き取り、保留の判断、通過・保留の下書きの承認(抜き取りのときは、選んだものの承認) | 人 | この文書の「5」「8」 |
| 資格マスタの値(分野・配点・出題数・時間)の直し | 人(手作業) | 収集の試験ガイドの取り込みが差分を報告します。マスタはパイプラインが書き換えないので、人が直します |
| 公開にする | 人(手作業) | 資格マスタを `status: "published"` にし、必要な項目を足します([資格を追加する手順](./adding-an-exam.md)の「3」の手順 4)。近日公開の資格では、順序を下の段落のとおりにします |
| 画面での確認、リリースノート | 人 | [資格を追加する手順](./adding-an-exam.md)の「3」の手順 7 と 9 |

事実カードから先の段階は、資格マスタの分野(`domains`)を使い、出題計画から先は本番の出題数(`officialQuestionCount`)も使います。
近日公開の資格でも、`edition`・`domains`・`officialQuestionCount`・`idPrefix` を持たせれば([問題データの仕様](./data-spec.md)の「2. 資格マスタ」)、公開にする前から、収集・事実カード・出題計画・下書き・検証・人の確認まで進められます。
分野か本番の出題数がない資格は、出題計画・下書き・検証が、足りない項目を示して止まります(分野がない資格の事実カードの依頼は、止まらず、分野がないので 0 件になります)。収集は、準備中の資格でも、資格マスタの版を出典の対象に付けます。

書き出しは、公開中(`published`)の資格にだけ行えます。公開中の資格には、選択式の問題が本番の出題数以上ある問題のファイルが要ります(データの検査)。そのため、近日公開の資格では、次の順にします。

1. 近日公開のまま、事実カードから人の確認までを進め、承認した選択式の下書きを、本番の出題数以上そろえます。
2. 作業ツリーで、資格マスタを公開の形(`status: "published"` にし、足りない項目を足した形)にします。コミットはまだしません。
3. 書き出します。承認した下書き(と、抜き取りで確認しないと記録した、検証が `pass` の下書き)は、1 回の書き出しでまとめて書かれます。選択式が出題数に届かないと、書いたあとのデータの検査に落ちて、書き出しは取り消されます(手順 1 に戻ります)。
4. 公開の形の資格マスタと、書き出した `data/` を、1 つの PR にまとめます(資格マスタの公開だけを先にコミットしません)。

## 3. 実行の前の準備

- 依存を入れます(`npm ci`)。
- 環境値は、`packages/pipeline/.env`(gitignore 済み)にだけ置きます。`packages/pipeline/.env.example` には、プレースホルダーだけを書きます。
  今ある環境値は、作業用の置き場を変える `PIPELINE_WORK_DIR` だけで、省略できます。API キーなどの認証情報は扱いません(モデルは Claude Code のエージェントが呼びます)。
- 設定は `packages/pipeline/pipeline.config.json` です(コミットします。環境値は入れません)。
- 作業用の置き場(既定は `pipeline-work/`)は gitignore 済みです。取得した本文、依頼、エージェントの出力、レポートは、ここにだけ置きます。

## 4. 収集

| | |
| --- | --- |
| コマンド | `collect <試験コード> --dry-run`(計画の検査)→ `collect <試験コード>` → `collect <試験コード> --import-guide`(試験ガイドの取り込み) |
| 入力 | 収集の計画、許可ドメインの一覧、資格マスタ |
| 出力 | 出典の台帳 `packages/pipeline/ledger/<コード>.json`(コミットする)、本文のキャッシュ `pipeline-work/cache/`(コミットしない) |
| エージェント | `guide-extractor`(`pipeline-work/guide/<コード>.request.json` を渡す)。任意で、出典の候補を挙げる `source-scout`(`collect <試験コード> --candidates` と `--import-candidates`。[収集の手順](./source-collection.md)の「2」の手順 5 に続く「出典の候補を挙げる(任意)」) |
| 関門 | https で許可ドメインの URL か、取得できたか、日付・版・リージョンの検査に合格したか(合格した出典だけが `active`) |
| 止まったとき | 表示の種類と理由コードで、[収集](./source-collection.md)の「6. 止まったときの対処」を引きます |

試験ガイドの取り込みは、資格マスタとの差分(分野・配点と、本番の値)を報告します。マスタを直すかは、人が判断します。
日付が古いだけで止まった出典を使うときは、人が確かめて[人の判断の記録](./human-decisions.md)に `accept` を書きます。

## 5. 事実カード

| | |
| --- | --- |
| コマンド | `facts <試験コード>`(依頼)→ エージェント → `facts <試験コード> --import` → `--coverage` → `--report` |
| 入力 | 台帳の `active` な出典(試験ガイドを除く)と、その本文のキャッシュ |
| 出力 | 事実カードの台帳 `packages/pipeline/facts/<コード>.json`(コミットする)、レビューレポートと、通過・保留のカードの表 `pipeline-work/facts/<コード>/`(コミットしない) |
| エージェント | `fact-extractor`(依頼のファイルを 1 つずつ、別の起動で渡す) |
| 関門 | 出力の形、本文の長い写しでないこと、見出し・引用・数値・固有名詞が出典の節にあること。食い違うカードは保留(`conflict`) |
| 止まったとき | 理由コードで、[事実カード](./fact-cards.md)の「4. レビューの観点」の表を引きます。やり直しは設定の `facts.maxAttempts` 回まで |

人は、`--report` の抜き取りの表で、主張が出典の本文と合っているかを確かめます。保留のカードは、出典を読み比べ、カードごとに `release` か `reject` を判断の記録に書きます。

## 6. 出題計画

| | |
| --- | --- |
| コマンド | `plan <試験コード>` |
| 入力 | 資格マスタ(本番の出題数、分野の重み)、公開済みの問題、設定の `plan` |
| 出力 | `pipeline-work/plan/<コード>/plan.json`(分野・難易度・種別ごとの不足の数。コミットしない) |
| 関門 | なし(計画をスキーマで検査するだけ) |

公開済みの問題に足す数を決めます(置き換えません。ADR 0012)。目標と配分は[出題計画と下書きの手順](./drafting.md)の「2」です。

## 7. 下書き(解説を含む)

| | |
| --- | --- |
| コマンド | `draft <試験コード>`(依頼。`--domain=<分野のコード>` で分野を絞れる)→ エージェント → `draft <試験コード> --import` → `draft <試験コード> --check` |
| 入力 | 出題計画、通過した事実カード(再検証の印がなく、出典が `active` のもの) |
| 出力 | 下書き `pipeline-work/draft/<コード>/drafts.json`(コミットしない)、来歴 `packages/pipeline/provenance/<コード>.json`(コミットする) |
| エージェント | `question-drafter`(依頼のファイルを 1 つずつ、別の起動で渡す) |
| 関門 | スタイル規則(解説の見出しと選択肢の解説を含む)、誤答の検査、データの契約、出典の本文の写し、来歴、重複。正解の偏りは報告だけ |
| 止まったとき | 理由コードで、[出題計画と下書きの手順](./drafting.md)の「4. 判定と理由コード」を引きます。やり直しは `draft.maxAttempts`、出し直しは `draft.maxRounds` まで |

解説と選択肢ごとの解説は、この段階で書きます(誤答の設計の理由が、その選択肢の解説になります)。書き方は[作問のスタイルガイド](./question-style.md)の「解説の書き方」です。
`--check` は、来歴の事実カードと出典を確かめ、再検証が要るものを止めます。来歴のない下書きは先へ進めません。

### 7.1 検証

| | |
| --- | --- |
| コマンド | `verify <試験コード>`(依頼)→ エージェント → `verify <試験コード> --import`。解説の確認が続くので、再導出の取り込みのあと、もう一度 `verify` を実行して、解説の確認の依頼を出す |
| 入力 | 来歴のある下書き(通過と保留)、根拠の事実カードの出典の節(キャッシュの本文) |
| 出力 | 下書きの状態(`pipeline-work/draft/<コード>/drafts.json`)の `verification`(判定、理由コード、指摘の場所、検査ごとの結果) |
| エージェント | `question-verifier`(依頼のファイルを 1 つずつ、別の起動で渡す。下書きの役とは別のモデル) |
| 関門 | 根拠の節だけからの再導出が宣言した正解と一致し、解説に指摘がないこと。食い違いは保留、節の本文の写しは不採用。節を取り出せないときは、依頼を出さず止まる |
| 止まったとき | 理由コードで、[出題計画と下書きの手順](./drafting.md)の「4. 判定と理由コード」を引きます。やり直しは `verify.maxAttempts` まで |

保留の下書きは、人の確認(次の節)で、理由コード(`verify:*`)と指摘の場所を見て、承認・却下を判断します。検証で保留になった下書きは、人が承認すれば書き出せます(人の判断を優先します)。検証をしていない下書きは、承認があっても書き出せません。
詳しい動きは、[出題計画と下書きの手順](./drafting.md)の「検証」です。

### 7.2 理由の集計

| | |
| --- | --- |
| コマンド | `reasons <試験コード>`(`--dry-run` で書き込まない) |
| 入力 | 事実カードの台帳、下書きの置き場、人の判断の記録 |
| 出力 | `pipeline-work/reasons/<コード>/summary.json` と `summary.md`(コミットしない)。理由コード・論点・段階ごとの件数と割合、意味、よくある型、指示に足すとよい制約の候補。本文は含まない |
| いつ使うか | 下書きの取り込みや検証のあと、不採用や保留が多いとき。作る側(下書きの役)の指示を直す材料にする |

指示の書き換えは、通常の PR で、人の確認を経ます。集計は、元の記録も指示も書き換えません。

### 7.3 検証役の評価

| | |
| --- | --- |
| コマンド | `eval <試験コード>`(依頼)→ エージェント `question-verifier` → `eval <試験コード> --import`。解説の確認が続くので、もう一度 `eval` で依頼を書く |
| 入力 | 人が承認した選択式の下書き(人の判断の記録)、根拠の節 |
| 出力 | 評価用のデータ(`pipeline-work/eval/<コード>/dataset.json`、コミットしない)、レポート(`report.json` と `report.md`) |
| いつ使うか | 検証役の指示かモデルを変えたとき。人の確認を抜き取りに切り替える前 |

評価用のデータは、承認した下書きに誤りを仕込んで作ります。指標の定義、目標、下回ったときの扱いは、[検証役の評価](./evaluation.md)です。

## 8. 人の確認

```sh
npm run pipeline -- draft <試験コード> --review
npm run pipeline -- draft <試験コード> --decide
```

1. `--review` で、作業用の置き場に確認用の表(`review.md`)と判断のシート(`review-sheet.json`)を書きます。対象は、通過と保留の下書きのすべてと、人が却下した下書きです(却下したものは、確認済みとして載ります)。抜き取りに切り替えているときは、通過の下書きのうち選んだものだけが載ります(「8.1」)。
2. 表を、下書きごとに読みます。載っているのは、状態と人の判断、分野・難易度・種別、設問文、選択肢と正答(自由記述は観点と合格点)、解説、根拠の事実カードの主張と節、出典の URL、保留・不採用の理由コード、警告です。取得した本文は載りません。出典の URL を開いて、本文と照らします。
3. 判断をシートの行に書きます。`decision` は次のどれかで、`reason` には理由コード(英小文字・数字・ハイフン)を書きます。自由な文や個人の情報は書きません。

   | 判断 | 書くとき |
   | --- | --- |
   | `approve`(承認) | 設問文と正答が根拠の主張だけで言え、誤答が設問の条件のもとで確かに誤りで、解説が正答と誤答の理由を説明し、適用範囲(版・リージョン)が合っている。保留の下書きを承認すると、保留も解けます |
   | `reject`(却下) | 根拠にないことを足している、誤答が条件によって正しくなる、公開済みの問題やほかの下書きと同じ論点を問う、など。直すより作り直すほうが早いもの |
   | `release`(保留の解除) | 保留の理由を確かめ、問題がなかったもの(承認は別に要ります)。保留でない下書きには書けません |

4. `--decide` で、シートを[人の判断の記録](./human-decisions.md)(`packages/pipeline/decisions/<コード>.json`。コミットする)に取り込みます。理由のない判断、知らない下書き、保留でない下書きの解除があると、行の番号と種類を出して、何も取り込みません。
5. 確認の済み・未済の件数は、`--review`・`--decide`・`--check` が報告します。**表に載る下書きがすべて承認か却下になるまで**、PR を出しません。

保留の理由ごとの扱いは次のとおりです。観点の詳細は[出題計画と下書きの手順](./drafting.md)の「5. レビューの観点」です。

| 保留の理由 | 解く条件 | 解けないとき |
| --- | --- | --- |
| `ambiguous:*`(正答が複数になりうる) | 検証の再導出が宣言した正解と一致し、解説の確認にも合格した(保留が自動で解ける)。または、誤答が設問の条件のもとで確かに誤りだと、人が出典で確かめた | 却下する(下の「却下したあとの作り直し」) |
| `verify:*`(検証の保留) | 理由コードと指摘の場所を、出典の節と照らして確かめ、下書きが正しいと確かめた(承認すると、書き出せる) | 却下する、または下書きを作り直す |
| `review:similar-*`・`review:topic-*`(既存や下書きに近い) | 相手の問題と論点が違うと確かめられた | 却下する(下の「却下したあとの作り直し」) |
| `review:copy-unchecked`(写しを確かめられない) | 人が出典の本文と照らして、写しでないと確かめた | 機械の検査をやり直すときは、収集をやり直して本文をキャッシュに戻してから、[出題計画と下書きの手順](./drafting.md)の「下書きをやり直すとき」の手順で、下書きを作り直す(再作成) |

**却下したあとの作り直し**: 却下した下書きは、計画の項目の数に数えなくなります。次に `draft <試験コード>` を実行すると、足りない分の依頼が出ます。ただし、依頼の鍵(計画の項目、書かせる数、出し直しの回数、事実カード、エージェントの定義のハッシュ)が取り込み済みの依頼と同じになると、依頼は出ず、「取り込み済みの入力で飛ばした」に数えられます。そのときは、[出題計画と下書きの手順](./drafting.md)の「下書きをやり直すとき」の手順で作り直します。

事実カードの保留(`conflict`)と、日付の古い出典の受け入れも、同じ判断の記録に書きます(「4」「5」)。判断は次にその段階を実行したときに反映されます。
対象がなくなった判断は、`判断の対象なし` として報告されるので、新しい対象を確かめ直して書き直すか、消します。

### 8.1 抜き取りで確認する

人の確認は、既定では全件です。検証役の評価が目標を満たしたときだけ、リスクの高いものを優先した抜き取りに切り替えられます。

```json
"review": { "mode": "sample", "rate": 0.3, "seed": 1, "nearHoldMargin": 0.15, "highRiskScore": 2, "maxRejectRate": 0.2, "minDecisions": 5 }
```

- **切り替えの条件**: `review.mode` が `sample` で、`pipeline-work/eval/<コード>/report.json` があり、`meetsTargets` が真で、レポートの検証役の定義のハッシュが今の検証役と同じであること。ひとつでも欠けると全件の確認のままで、理由(`eval-missing`・`eval-not-met`・`eval-stale`)を報告します。
- **対象**: 検証を通った(通過の)下書きと事実カード。保留と不採用は対象にならず、人が解くまで先へ進みません。
- **選び方**: 件数は `max(⌈件数 × review.rate⌉, 点数が `review.highRiskScore` 以上のもの)`。点数の高い順に選び、同点は `review.seed` で決めます(同じ入力・率・種なら、同じものが選ばれます)。
- **リスクの点数**(該当ごとに 1 点): 下書きは、スタイル規則の警告がある・設問文の類似度が `draft.similarity.hold` から `review.nearHoldMargin` 以内・新しい論点・来歴の出典が 1 件だけ(来歴がない場合も含む)。事実カードは、確度が `high` でない・新しい論点・根拠が 1 件以下。新しい論点は、出題範囲の項目(`scopeItems`)のうち、人が承認した下書きが、まだないもの。
- **類似度**: 下書きを取り込むとき、公開済みの問題やほかの下書きとの最大の類似度を、下書きの記録(`similarity`)に残します。
- **却下の割合が高いとき**: 前回確認すると記録した下書きのうち、人の判断が `review.minDecisions` 件以上あり、却下の割合が `review.maxRejectRate` を超えたら、全件の確認へ戻します(`reject-rate-high`)。
- **記録**: `draft --review` が、率・種・確認する件数・しない件数・理由を `packages/pipeline/decisions/<コード>.sampling.json` に残します(ID と件数だけで、本文は含みません。コミットする)。記録があれば、`--decide`・`--check`・`export` は記録のとおりに動きます。確認用の表とシートには、選ばれたものだけが載ります。
- **書き出し**: 確認しないと記録した下書きは、検証が `pass` で、記録の時点と同じ検証役の定義なら、承認なしで書き出せます。検証が保留・未検証のものは、これまでどおり人の承認が要ります。
- 事実カードの確認用の表(`cards.md`)も、確認しない通過のカードを載せません(保留のカードは全件載せます)。

## 9. 書き出し

| | |
| --- | --- |
| コマンド | `export <試験コード>`(`--dry-run` で件数だけ) |
| 入力 | 承認され(抜き取りで確認しないと記録したものを除く)、検証を通った下書き、来歴、資格マスタ(`idPrefix`・`retiredQuestionIds`)、公開済みの問題 |
| 出力 | 作業ツリーの `data/questions.<コード>.json`(追加の分だけ)、来歴の `questionId`、差分レポート `pipeline-work/export/<コード>/report.md`(件数と種類だけ。コミットしない) |
| 関門 | 承認(抜き取りで確認しないと記録したものを除く)があり、検証を通り、来歴の検査を通ったものだけを書き出します。書いたあとにデータの検査を通し、落ちたら元に戻します(`データの検査の失敗`) |

問題の ID は、退役した ID と書き出し済みの ID を含めた最大の番号の次から採番します(ADR 0014)。書き出し済みの下書きは、再び書き出しません。

## 10. コミットと PR

コミットするのは、資格マスタと `data/` の差分、台帳(`ledger/`・`facts/`)、来歴(`provenance/`)、判断の記録(`decisions/`)、収集の計画(`plans/`)です。
`pipeline-work/` の中身は、コミットしません。コミット・push・PR は、`CLAUDE.md` の「検査と承認の流れ」に従います(`/dev-commit`・`/dev-pr`)。

PR を出す前に、次を確かめます。

- [ ] **機密・個人情報・環境情報**: 差分に、認証情報、個人の情報、環境固有の値(アカウント ID、独自ドメイン、個人の環境のパスなど)がない。例はプレースホルダー(`example.com`・`<資格コード>` など)だけ
- [ ] **権利**: 出典の本文をコミットしていない。台帳にあるのは、URL・取得日・ハッシュ・検査の結果・短い言い換えだけ([出典と権利の方針](./source-policy.md))
- [ ] **出典**: `references` は、許可ドメインの https の URL で、公式のもの、対象の版に該当するもの、リンクが生きているもの(人が開いて確かめる)
- [ ] **差分レポート**: `pipeline-work/export/<コード>/report.md` の件数(追加、分野別、出典のドメイン別、保留・不採用の理由の種類)を、PR の本文に書き写す。本文は載せない
- [ ] **人の確認**: 書き出した全件に、判断の記録の承認がある(`draft <試験コード> --check` の未済が 0 件)。抜き取りのときは、確認しないと記録した下書きを除く(「8.1」)
- [ ] **データの検査**: `npm run validate:data` と `npm run check:retired-ids` が通る

## 11. 作業用の置き場の掃除

- 取得した本文のキャッシュ(`pipeline-work/cache/`)は、収集のたびに、保持日数(`cache.retentionDays`)を過ぎたものと、容量の上限(`cache.maxBytes`)を超えた古いものが消えます。
- 下書きをやり直すときは、[出題計画と下書きの手順](./drafting.md)の「下書きをやり直すとき」の手順で、作業用の置き場と来歴の項目を消します。
- 事実カードの抽出をやり直すときは、[事実カード](./fact-cards.md)の「5.1 抽出をやり直すとき」の手順です。
- 作業用の置き場を丸ごと消しても、コミットした台帳・来歴・判断の記録は残ります。本文のキャッシュがないと検査できない段階は、収集からやり直します。

## 12. ログと報告に載せてよいもの

| 載せてよいもの | 載せてはいけないもの |
| --- | --- |
| 表示の種類、場所(ファイル、項目、行の番号)、理由コード、件数、ID、出典の URL | API キーなどの認証情報、取得した本文、設問文などの下書きの本文、環境固有の値、個人の情報 |

CLI の報告とレポートは、この形で出ます。PR・Issue・コミットメッセージに結果を書くときも、同じ範囲にとどめます。

## 13. テスト

パイプラインのテストは fixture だけを使い、外部へ通信しません。ネットワークを使うテストは、CI に入れません([作問パイプラインの進め方](./pipeline-workflow.md)の「5」)。
収集から書き出しまでを通す結合テストは、`packages/pipeline/src/e2e/` にあります。
