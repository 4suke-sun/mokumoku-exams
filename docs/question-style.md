# 作問のスタイルガイド

作問パイプラインの下書きの段階で、設問文・選択肢・誤答・自由記述の採点基準を、どう作るかの決まりです。
決まりの多くは、機械で検査できる規則(`packages/pipeline/src/draft/style.ts` と `distractors.ts`)になっていて、下書きを取り込むときに適用されます。
この文書の規則の名前は、検査の報告に出る名前と同じです。手順は[出題計画と下書きの手順](./drafting.md)、データの形は[問題データの仕様](./data-spec.md)にあります。

## 1. 規則の重さ

- **止める**(`block`): 違反した下書きは、不採用になります。理由コードは `style:<規則の名前>` です。
- **警告**(`warn`): 違反しても通ります。下書きの記録に、規則の名前と場所が残り、レビューで見ます。

報告は、規則の名前と場所(`questionText`、`choices.2.text` など)だけです。設問文や選択肢の本文は出しません。

## 2. 設問文

| 規則 | 重さ | 内容 |
| --- | --- | --- |
| `stem-question-form` | 止める | 問いの形(「〜でしょうか。」「〜ですか。」「〜してください。」「〜か。」など)で終える。末尾に選ぶ数の注記(「(2 つ選択)」)を添えるときは、注記を除いた末尾で見る。語尾は「です・ます」が望ましい(書き方の点数票が、敬体でない末尾を減点する) |
| `multi-select-count` | 止める | 複数選択の設問文には、選ぶ数(「2 つ選択」など)を書く |
| `multi-select-count-mismatch` | 止める | 複数選択の設問文に書いた数は、正答の数と一致させる |
| `stem-negation` | 警告 | 否定を含む設問は避ける。使うなら否定の語を 1 つだけにし、強調する |
| `stem-double-negation` | 止める | 設問文に否定の表現を 2 つ以上入れない(二重否定) |

規則ではありませんが、難易度が `medium` と `hard` の設問文は、状況を設定する形にします。誰が何をしようとしていて、どんな要件や制約があるかを 2〜4 文で書き(資格ごとの文の数や長さの目安がある資格は、[資格ごとの出題スタイル](./exam-style/README.md)の目安を優先します)、
その要件を満たすもの(または、取るべき手順の組み合わせ)を問います。正答を決める要件と制約は、依頼の事実カードの主張で根拠を示せるものだけにします(状況を成り立たせる架空の設定の数値は、資格別の指針が許すときだけ、根拠を求めません)。
`easy` は、事実を 1 つ問う短い形でかまいません。

### 主語の書き方

設問文の状況の文と、解説の文は、何が何をするのかを読んで分かるように、主語を書きます。知識として覚えるときに、動作の主が読み取れないと、何が成り立つのかを覚えにくいためです。
これは書き方の指針です。機械の規則ではなく、取り込みでは止めません(日本語の主語の省略は、機械では見分けられないため)。判定の基準(判定役が読む「判定の基準」の節)にも入れていません。作問役と書き直し役が、この文書を読んで従い、人のレビューで見ます。

主語を書く範囲:

- 設問文の状況の文(「ある企業は」「開発者が」「あなたの会社が」など)。
- 解説(総合解説、選択肢ごとの解説、補足)の文。「何が」「誰が」を名指しします(「Amazon S3 は」「Lambda 関数が」「利用者が」)。段落の最初の文では、前の段落と同じ主語でも書きます。

省いてよい範囲:

- 同じ段落の中で、前の文と同じ主語が続く文。
- 選択肢。サービス名・語句・短い文の形は、資格別の指針の選択肢の形に従います([AWS 共通](./exam-style/aws-common.md)の「3. 選択肢」の「形」の行)。
- 事実を直接問う設問文の、問いの形の文(「Amazon S3 の特徴として正しいものはどれですか。」のように、サービス名や概念が主語の形)。ベンダー共通の指針の「主体」の行に従います。
- 問いの形の「〜してください」の聞き手(「あなた」)。

試験の言い回しに寄せる指針とぶつかるときは、設問文の書き出しと構成(状況の文の数、問いの形)と選択肢の形は、試験の言い回し(資格別の指針)を優先します。ただし、状況の文の中で動作の主を書くことは、これと矛盾しません。解説は学習用なので、主語を書くほうを優先します。

体系ノートの規則 `missing-subject`([体系ノートの文体の規則](./notebook-style.md)の「4.3 文」)との関係: 体系ノートの規則は、体系ノートの本文だけにかかります(同文書の「1. かける範囲」)。
問題データの設問文・解説は、この文書の決まりに従い、体系ノートの規則は使いません。

既存の問題には、一括では当てません。書き直し(`draft --rewrite`。[出題計画と下書きの手順](./drafting.md)の「書き直し(非公開の問題)」)で問題を直すときに、書き直し役がこの指針に合わせます。判定(`judge`)は、この指針を見ません。

資格ごとの長さの目安、状況の文の数、選択肢の形、語尾などは、[資格ごとの出題スタイル](./exam-style/README.md)にあります。
採点は、[書き方の点数票](./exam-style/scorecard.md)(`npm run pipeline -- score <資格コード>`)です。点数票は警告で、取り込みは止めません。

## 3. 選択肢

| 規則 | 重さ | 内容 |
| --- | --- | --- |
| `choice-count` | 警告 | 選択肢は 4 つ以上にする |
| `choice-length-balance` | 警告 | 選択肢の長さをそろえる(最も長いものが 30 文字以上のとき、最も短いものの 3 倍を超えない) |
| `correct-length-bias` | 警告 | 正答だけが長い(短い)といった偏りを作らない |
| `choice-similar-pair` | 警告 | ほぼ同じ文言の選択肢を並べない。紛らわしさは、内容の違いで作る |
| `choice-catch-all` | 止める | 「すべて正しい」「いずれでもない」のような、選択肢をまとめる選択肢を置かない |

## 4. 誤答

誤答(正答でない選択肢)には、1 つずつ設計を付けます(下書きの `distractors`)。

| 項目 | 内容 |
| --- | --- |
| `key` | 誤答の選択肢の `key` |
| `type` | 誤答の型。`similar-service`(似た別のサービス)、`scope-difference`(適用範囲や条件の違い)、`misconception`(よくある誤解)、`numeric-difference`(数値や上限の違い)、`condition-reversal`(条件の逆) |
| `reason` | 誤りである理由。10 文字以上で具体的に書く |
| `basis` | 誤りの根拠。事実カードの主張(`factId`。依頼にあるものだけ)か、適用範囲の違い(`scope`。型が `scope-difference` のときだけ) |

誤答の検査は、モデルを呼ばずに行います。理由コードは `distractor:<コード>` か、保留の `ambiguous:<コード>` です。

| コード | 結果 | 内容 |
| --- | --- | --- |
| `distractor-missing` | 止める | 誤答に設計がない |
| `distractor-unknown-key` | 止める | 正答の選択肢や、存在しない選択肢に設計がある |
| `distractor-duplicate` | 止める | 同じ選択肢に設計が重複している |
| `distractor-reason-short` | 止める | 理由が短すぎる |
| `distractor-basis-not-in-request` | 止める | 根拠の事実カードが、依頼にない |
| `distractor-basis-scope-type` | 止める | 適用範囲の違いを根拠にできるのは、`scope-difference` の型だけ |
| `distractor-forbidden-text` | 止める | 理由や適用範囲の言い表しに、URL や環境固有の値がある |
| `distractor-type-bias` | 警告 | 誤答が 3 つ以上で、型が 1 種類に偏っている |
| `similar-to-correct` | 保留 | 誤答が正答とほぼ同じ文言(15 文字以上の選択肢だけ比べる) |
| `supported-by-fact` | 保留 | 誤答の語(数値とラテン文字の語)が、根拠の主張にそのまま含まれる |

保留は、**設問文の条件のもとで誤答が正しくなりうる(正答が複数になる)候補**です。機械の検査は候補を出すだけで、白黒はつけません。
候補は、モデルによる検査(検証の段階。[出題計画と下書きの手順](./drafting.md)の「検証」)で、再導出が宣言した正解と一致するまで、先へ進めません。

## 5. 自由記述の採点基準

形は[問題データの仕様](./data-spec.md)の「自由記述」に従います。観点名とキーワードの長さが上限を超える出力は、出力の形の誤り(`output-invalid`)として取り込みを止めます。
そのほかのデータの検査規則(配点と合格点の関係、観点名の重複など)に合わない採点基準は、その下書きだけを `data-invalid` で不採用にします([出題計画と下書きの手順](./drafting.md))。
次の規則は、データの検査規則に加える、作り方の決まりです。

| 規則 | 重さ | 内容 |
| --- | --- | --- |
| `rubric-criteria-count` | 警告 | 観点は 2 つ以上にする。1 つだけでは、部分的な理解を測れない |
| `rubric-keyword-short` | 警告 | キーワードは 2 文字以上にする。1 文字では、無関係な回答にも当たる |
| `rubric-keyword-shared` | 警告 | 同じキーワードを、複数の観点に入れない |
| `rubric-pass-ratio` | 警告 | 合格点は、配点の合計の 5 割以上 9 割以下にする |

観点とキーワードは、根拠の事実カードの主張だけを根拠にします。選択肢と誤答の規則は、自由記述には適用しません。

## 6. 禁止事項と、そのほかの決まり

| 規則 | 重さ | 内容 |
| --- | --- | --- |
| `no-url` | 止める | 設問文・選択肢・解説・観点名・キーワードに URL を書かない。出典は来歴に記録する |
| `no-env-value` | 止める | 環境固有の値(12 桁のアカウント ID、ARN、アクセスキー、メールアドレス、ローカルのパス)を書かない |
| `overclaim-term` | 警告 | 「必ず」「絶対」「常に」など、断定しすぎる語を使わない |
| `explanation-length` | 警告 | 総合解説は、正答の理由が分かる長さ(30 文字以上)で書く |
| `explanation-heading` | 止める | 解説の見出し(`## ` の行)は、決まった名前だけを使う([問題データの仕様](./data-spec.md)の「6.1 解説の見出し」の表。表の別名も通るが、正式名にそろえる) |
| `explanation-wrong-pairs` | 止める | 解説の「他の選択肢が誤りである理由」の節は、誤答の選択肢の本文と同じ段落の次に、その理由の段落を置く組だけで書く。組にならない段落を置かない(本文の比べ方は、空白と読点・句点を除く。アプリが選択肢ごとの小カードにする判定と同じ) |
| `explanation-key-reference` | 止める | 解説で選択肢を記号で指すときは、その問題の記号だけを使う。選択肢ではない大文字 1 文字を、前後に英数字なしで書かない(「X-Ray」のように、ハイフンで語につながるものは除く) |
| `choice-explanation-missing` | 止める | 誤答のすべてに、誤りである理由を書く(誤答の設計の理由が、その選択肢の解説になる) |
| `choice-explanation-markup` | 止める | 選択肢ごとの解説に、見出し(行の先頭の、1〜6 個の `#` に半角の空白かタブが続くもの)と箇条書き(行の先頭の `-`・`*`・`+`・`1.` などに半角の空白かタブが続くもの。どちらも、前の字下げは問わない)を使わない。使える記法は、太字・コード・改行([問題データの仕様](./data-spec.md)の 3) |

### 解説の書き方

アプリは、解説を見出しごとのカードで表示し、選択肢ごとの解説を選択肢の下に表示します([問題データの仕様](./data-spec.md)の 3・6・6.1)。

- 見出しは、6.1 の表にある名前を、`## ` の行か、名前だけの段落で書きます。見出しの名前の一覧は、データの契約(`packages/data-schema/src/exam-data/explanation.ts`)にあり、アプリと作問パイプラインが同じ一覧を読みます。
- 「他の選択肢が誤りである理由」の節では、選択肢の本文と同じ段落の次に、その理由の段落を置きます。組にならない段落(節の前置きや補足など)は置きません。取り込みの規則 `explanation-wrong-pairs` が止めます。
  組の判定(段落の分け方、選択肢の本文の比べ方)は、データの契約(`packages/data-schema/src/exam-data/explanation.ts` の `pairChoices`)にあり、アプリの表示と作問パイプラインの検査が同じものを使います。書き出しは、解説を書き換えません。
- 誤答の設計の理由(`distractors[].reason`)は、問題の形に組み立てるとき、その選択肢の解説(`choices[].explanation`)になります。選択肢に解説を書いたときは、そちらを使います。正答の選択肢の解説は任意です。

加えて、次の決まりがあります(規則ではなく、取り込みの関門です)。

- 設問文と正答は、依頼の事実カードの主張だけを根拠にします。主張にないことは書きません。
- 公式の文書の本文を、思い出して書き写しません。自分の言葉で書きます。
- 下書きの種別と難易度は、依頼のとおりにします。種別が違う下書きは、不採用になります(`kind-mismatch`)。

## 7. 規則を足す・変えるとき

1. `packages/pipeline/src/draft/style.ts`(または `distractors.ts`)に規則を足し、通る例と落ちる例のテストを書きます。
2. この文書の表に、同じ名前の行を足します。表の名前と実装の名前が食い違うと、テストが失敗します。
3. 規則の集合を変えたら、`STYLE_VERSION` を上げます。依頼の鍵が変わり、規則が変わったあとの依頼は、取り込み済みの入力とは別に扱われます。
