# セルフサインアップの仕様

利用者が、自分でメールアドレスとパスワードを登録して使い始められるようにします。
あわせて、自分で退会してデータを消す操作と、集める情報と使い道を示すページ(`/privacy`)を足し、管理者の画面から招待を外します。

認証の全体の作り(トークン、ログイン必須化、管理者の判定)は [認証の仕組み](../auth.md) のとおりで、この仕様では変えません。

## ユーザーの流れ

### 登録

1. ログインの画面(`/login`)の「新規登録」から、登録の画面(`/signup`)を開く。
2. メールアドレス、パスワード、パスワードの確認を入れ、`/privacy` を読んだうえで「登録する」を押す。
3. 確認コードの入力に切り替わる(同じ画面のまま)。メールに届いたコードを入れ、「確認する」を押す。
4. 確認が通ると、そのままログインした状態になり、ホームへ移る。

### 確認コードが届かないとき

1. 確認コードの入力の画面で「コードを送り直す」を押すと、同じメールアドレスにコードを送り直す。
2. 送信の上限に当たったときは、上限の文言(下の「必要なデータ」の「送信の上限に当たったことは、必ず利用者に伝える」の文言)を出す。
3. 上限が戻ったあと(日本時間の 18 時以降)は、ログインの画面から、登録したメールアドレスとパスワードでログインを試すと、確認がまだのときは確認コードの入力へ移る(「コードを送り直す」が使える)。
   `/signup` から同じメールアドレスとパスワードでもう一度登録しても、同じく確認コードの入力へ移る(下の「登録し直し」)。

### 登録し直し(確認がまだのアカウントがあるとき)

1. 同じメールアドレスで、確認がまだのアカウントがある状態で、`/signup` から登録する。
2. パスワードが前の登録と同じなら、確認コードを送り直し、確認コードの入力へ移る。
3. パスワードが違い、前の登録から 24 時間たっているときは、前の登録を消して、新しく登録し直す(打ち間違いで他人のメールアドレスが押さえられたままにならないようにする)。
4. パスワードが違い、前の登録から 24 時間たっていないときは、「このメールアドレスでは登録できません」と出す(下の「必要なデータ」の文言)。

### 退会

1. アカウントの画面(`/account`)の末尾の「退会する…」を押す。
2. 消えるもの(アカウント、サーバーの学習の記録、通知の購読、この端末の学習の記録)と、元に戻せないことを示し、パスワードの入力を求める。
3. パスワードを入れて「退会する」を押すと、データを消し、ログアウトしてログインの画面へ移る。「退会しました」と出す。

## 画面の構成とメニューの階層

- **`/signup`(新規)**: ログインなしで開ける。
  - 登録の入力: メールアドレス、パスワード、パスワードの確認、パスワードの規則の説明、「登録する」。
  - 注意書き(入力の上): 「確認コードのメールは、サービス全体で 1 日 50 通までしか送れません(日本時間の 18 時に数え直します)。届かないときは、18 時を過ぎてからもう一度お試しください。」
  - `/privacy` へのリンク(「登録すると、プライバシーと利用条件に同意したものとします」)。同意のチェックボックスは置かない。
  - 確認コードの入力: コード、「確認する」、「コードを送り直す」。
  - 「ログインへ戻る」のリンク。
- **`/privacy`(新規)**: ログインなしで開ける読み物の 1 ページ。見出しは次のとおり。
  - 集める情報: メールアドレス、学習の記録(結果、ブックマーク、復習、表示の設定など。[データの設計](../data.md) の項目)、通知を購読したときの購読の情報。接続元の IP アドレスなどのアクセスのログは集めていないこと(配信のアクセスのログは設定していない)。サーバーの動作の記録(エラーの内容など)は、不具合を調べるために 30 日のあいだ残し、そのあと消えること(`packages/infra/lib/web-stack.ts` のログの保存期間)。
  - 使い道: ログインと、学習の記録の保存と表示、通知の送信だけ。広告に使わない。第三者に渡さない。ただし、通知を購読したときは、通知を届けるために、ブラウザの提供元のプッシュの仕組みへ、購読の情報と通知の本文を渡す([データの設計](../data.md) の「通知の購読」)。
  - 退会のあとに残るもの: 管理者が利用者を無効にした操作の記録には、利用者を見分ける識別子(メールアドレスではない)が残る。
  - 消し方: アカウントの画面の「退会する」で、アカウントと学習の記録と通知の購読を消せる。
  - 利用条件: 問題・解説の正しさと、サービスの継続を保証しない。利用によって生じた損害の責任を負わない。悪用が疑われるアカウントは、予告なく無効にすることがある。
  - 問い合わせ: リポジトリの Issue(下の「未決の点」の 2)。Issue は公開の場なので、メールアドレスなどを書かないよう、ページに注意書きを置く。
- **`/login`(変更)**: 「招待されたメールアドレスで、ログインしてください。」を「メールアドレスとパスワードで、ログインしてください。」に変える。「新規登録」のリンクを足す。確認がまだの利用者がログインしたときは、確認コードの入力へ移す。招待の仮パスワードからの新しいパスワードの入力は、すでに招待済みで未使用の利用者のために残す。
- **`/account`(変更)**: 末尾に「退会」の節を足す。
- **`/admin`(変更)**: 招待の入力を外す。一覧と無効化は残す。一覧の状態に「確認待ち」(確認コードの入力がまだ)を足す。
- フッター(または、ログインの画面と登録の画面の下)に `/privacy` へのリンクを置く。

## 必要なデータ

### Cognito

- UserPool: セルフサインアップを許す(`selfSignUpEnabled: true`)。メールの自動の確認(`autoVerify: { email: true }`)とパスワードの規則は今のまま。送信元は Cognito の既定のまま。
- 確認のメール(`userVerification`)は、登録の確認とパスワードの再設定の両方で同じ文面が使われるため、どちらにも合う件名と本文にする(例: 件名「【もくもく問題集】確認コード」)。
- 招待のメール(`userInvitation`)の設定は消す。
- 送信の上限: Cognito の既定のメールの送信は、AWS アカウントごとに 1 日 50 通までで、上げられない。数は毎日 UTC の 9 時(日本時間の 18 時)に戻る(AWS の文書「Quotas in Amazon Cognito」の、ユーザープールの資源の上限)。同じアカウントのほかのユーザープールの送信とも、数を分け合う。画面の文言の「サービス全体で 1 日 50 通」と「日本時間の 18 時」は、この上限に合わせている。
- アプリのクライアントの `preventUserExistenceErrors: true` は残す。この設定は、存在しない利用者への認証・確認コードの送り直し・パスワードの再設定の応答を、存在する利用者と見分けられない形にするだけで、`SignUp` の `UsernameExistsException` は変えない。そのため、確認コードの送り直し(`POST /api/auth/resend-code`)は、登録のないメールアドレスにも成功の応答を返す(画面は、送り直したと出す)。
- ログインのエラーの変換(`packages/app/src/lib/auth/cognito.ts` の `ERROR_CODES`)で、`UserNotConfirmedException` を `invalid-credentials` から新しい種類 `not-confirmed` に分ける。ログインの画面は `not-confirmed` を受けたら、確認コードの入力へ移す。登録の API は、この種類で登録し直しを見分ける(下の「登録済みのメールアドレスでの登録」)。種類を列挙する型(`packages/app/src/lib/auth/types.ts`)、種類から応答の状態への対応表(`packages/app/src/lib/auth/handlers.ts`。`not-confirmed` は 403)、`messages.ts` の文言に足し、変換のテストも合わせる。ログインの API(`POST /api/auth/login`)は、確認がまだのとき `{ "error": "not-confirmed" }`(403)を返す。
- 認証の API(`packages/app/src/lib/auth/cognito.ts`。認証情報のいらない操作)に、`SignUp`・`ConfirmSignUp`・`ResendConfirmationCode`・`DeleteUser`(アクセストークンで本人が消す)を足す。
- 管理 API(`lib/auth/user-admin.ts`)から招待(`AdminCreateUser`)を外し、Lambda の権限からも外す。
- 登録し直しのために、Lambda の権限に `AdminGetUser`(状態と作成日時を読む)と `AdminDeleteUser`(確認がまだで 24 時間たったアカウントだけを消す)を足す。対象は、このユーザープールだけ(今の権限と同じ絞り方。`packages/infra/lib/auth-stack.ts`)。`AdminDeleteUser` を呼ぶ前に、状態が未確認(`UNCONFIRMED`)であることを必ず確かめ、確認済みのアカウントは消さない。テストで、確認済みのアカウントには呼ばないことを確かめる。

### アプリの API

| メソッドと経路 | 内容 | ログイン |
| --- | --- | --- |
| `POST /api/auth/sign-up` | 本文は `{ email, password }`。確認コードを送る | 不要 |
| `POST /api/auth/confirm-sign-up` | 本文は `{ email, code, password }`。確認が通ったらログインし、Cookie を付ける | 不要 |
| `POST /api/auth/resend-code` | 本文は `{ email }`。確認コードを送り直す | 不要 |
| `POST /api/auth/delete-account` | 本文は `{ password }`。パスワードを確かめてから、データとアカウントを消す | 要 |

- ログインなしで開ける API の一覧(`guard.ts` の `PUBLIC_AUTH_API_PATHS`)に、上の 3 つを足す。画面の一覧(`PUBLIC_PAGE_PATHS`)に `/signup` と `/privacy` を足す。経路の一覧のテスト(`authorization.test.ts`)も合わせる。
- `PUBLIC_PAGE_PATHS` は、robots の許可と sitemap(`packages/app/src/lib/site.ts`)にも使われる。`/signup` と `/privacy` は、検索エンジンに載せてよい(公開してよい画面のため)。`site.ts` のテストの期待値も合わせる。
- `POST` の決まり(JSON だけ、別サイトからの送信を断る、本文の大きさの上限)は、既存の認証の API と同じ。
- エラー応答は `{ "error": "<種類>" }` の形。
- 送信の上限: メールを送る 3 つの API(登録、送り直し、パスワードの再設定)では、`CodeDeliveryFailureException` と `LimitExceededException` を、新しい種類 `send-limit`(429)にまとめる。`LimitExceededException` は、同じメールアドレスへの試行の回数の上限でも返り、AWS の文書からはどちらか見分けられないため、文言は両方を含める。ログインなど、ほかの API の `limit-exceeded`(試行の回数が多すぎる)は今のまま変えない。
- **送信の上限に当たったことは、必ず利用者に伝える。** 3 つの画面のどれでも、`send-limit` を受けたら、上限の文言(「確認コードを送れませんでした。メールの送信は、サービス全体で 1 日 50 通までで、日本時間の 18 時に数え直します。同じメールアドレスへの送信の回数の上限に達した場合もあります。時間をおいてから、もう一度お試しください」)を、入力の近くの目立つ位置に出し、読み上げにも届くようにする(`role="alert"`)。ほかのエラーと同じ汎用の文言にまとめない。テストで、3 つの画面それぞれに上限の文言が出ることを確かめる。
- 登録済みのメールアドレスでの登録(`UsernameExistsException`)は、次の順に扱う。
  1. `AdminGetUser` で状態を読む。未確認(`UNCONFIRMED`)でなければ、パスワードを試さずに 4 へ進む(確認済みのアカウントについて、登録の API がパスワードを試す経路にならないようにする)。
  2. 未確認なら、受け取ったパスワードでログインを試す(`InitiateAuth`)。`UserNotConfirmedException` が返れば、本人の登録し直しとみなし、確認コードを送り直して、確認コードの入力へ進める(応答は登録が通ったときと同じ)。トークンは返らない(未確認のアカウントはログインできない)が、万一返っても、捨てて Cookie を付けない。
  3. それ以外で、作成から 24 時間たっているときは、`AdminDeleteUser` で消してから、もう一度 `SignUp` する。
  4. どれでもないときは、「このメールアドレスでは登録できません。登録済みなら、ログインかパスワードの再設定をお使いください」と出す(登録の有無が分かることは受け入れる)。応答は `{ "error": "already-exists" }`(409)。
  - 2 でログインを試して、パスワードが違うとき(`invalid-credentials`)だけ 3 へ進む。回数の制限や接続の失敗は、そのままエラーとして返し、消す方へは進まない。
- 確認が通ったのにログインできなかったとき(接続の失敗など): 確認の API は Cookie を付けずに `{ "status": "confirmed" }` を返し、画面は「メールアドレスを確認しました」とログインへのリンクを出す。
- 退会が通ったあとは、`/login?deleted=1` へ移し、ログインの画面に「退会しました」と出す。
- 送信の上限で `SignUp` が失敗したときに、未確認のアカウントが残るかは、AWS の文書に書かれていない。どちらでも、上の順で、上限が戻ったあとに、同じメールアドレスとパスワードで登録し直せる。
- 退会の順: パスワードで認証し直す → DynamoDB の `PK=USER#{sub}` の項目を `Query` で集めて `DeleteItem` で消す → Cognito の `DeleteUser` → Cookie を破棄。途中で失敗したら `503` を返し、もう一度押せば続きから消せる(消し済みの項目は、もう一度消しても結果が変わらない)。今の権限(`Query`・`DeleteItem`)で足りる。
- 画面は、退会が通ったら、この端末の学習の記録(持ち主の印で分けたキー。[データの設計](../data.md) の「端末の結果(localStorage)との関係」)を消す。

### DynamoDB

- データの契約の変更はない。
- 管理者の操作の記録(`PK=ADMIN`)は、退会しても残す。記録にはメールアドレスが入っていないため(Cognito のユーザー名だけ。このユーザープールでは `sub` と同じ値)。残ることは `/privacy` の「退会のあとに残るもの」に書く。

### 費用と悪用への備え

- 登録の回数の上限は付けない。送信の上限に当たったときは、上の文言で利用者に伝える。
- WAF と Cognito の有料の保護の機能は使わない。
- **共通のタグ**: CDK のアプリ全体(`packages/infra/bin/app.ts`)に `Tags.of(app).add("Service", "mokumoku-exams")` を付け、すべてのスタックとリソースに同じタグを付ける。値は固定で、環境ごとの接頭辞は入れない。
  請求の設定で、このタグをコスト配分タグとして一度だけ有効にすると、Cost Explorer でサービス全体の費用をタグで絞って見られる(有効にする手順は `docs/app/infra.md` に書く。有効にする前の費用は、タグでは絞れない)。
- **AWS Budgets**: 月の費用の予算を作り、上のタグで絞って、実績と予測が予算を超えそうなときにメールで知らせる(`packages/infra`)。金額と宛先は `.env` で渡し、リポジトリには書かない。`.env.example` にはプレースホルダーだけを書く。

### 手元の開発とテストの代替の認証

- `lib/auth/fake.ts` に、登録・確認・送り直し・退会を足す。確認コードは固定の値(`FAKE_SIGNUP_CODE`)。送信の上限を再現する宛先(例: `limit@example.com`)を用意する。

## 前提

- 認証: `/signup` と `/privacy` は、ログインなしで開ける。退会はログインが要る。管理者の画面は、今までどおり管理者だけ。
- 画面スタイル(リッチ / シンプル)、ライト / ダーク、動きを減らす設定: ログインの画面と同じ扱い。
- すでにいる利用者: そのまま使える。移行はない。

## 未決の点

なし。決めたことは次のとおり。

1. 確認がまだのまま残るアカウント(ボットや放置、打ち間違い): 定期の掃除はしない。登録し直しのときだけ、同じパスワードなら確認へ進め、違うパスワードで 24 時間たっていれば置き換える(上の「登録し直し」)。管理者の画面の一覧に「確認待ち」と出す。未確認のアカウントはログインできず、学習の記録を持たないため、消してもデータは失われない。
2. `/privacy` の問い合わせ先: リポジトリの Issue にし、メールアドレスなどの個人情報を書かないよう注意書きを置く。データを消す求めは、退会の操作で本人が行えるため、問い合わせを経ずに済む。
3. 画面の文言の「サービス全体で 1 日 50 通」: このままにする。上限は AWS アカウントの単位だが、利用者から見て「この問題集の全体」の意味で通じ、アカウントの内訳は利用者に関係しないため。
