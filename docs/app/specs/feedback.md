# 送信フォーム(お問い合わせ・問題の誤りの報告)の仕様

ログインした利用者が、開発者へ一方向で送るフォームを 2 つ置きます。送った内容は、サーバーが、このリポジトリ専用の GitHub App として、このリポジトリの Issue に起票します。
受け付けは一方向にとどめます。開発者からの返信、やりとりの往復、メールの通知は作りません。

## ユーザーの流れ

### お問い合わせ

1. 画面の下の注記(フッター)の「お問い合わせ」を押す。ログインしていなければ、ログインの画面へ移り、ログインのあとに戻る。
2. `/contact` で、種類を 1 つ選ぶ(「不具合」「機能改善の要望」「機能追加の要望」「その他」)。
3. 内容を書く。送信のボタンの上に、次の注意を出す。
   - 返信はしない。
   - 送った内容は、GitHub の Issue として起票され、公開されることがある。メールアドレスなどの個人情報や、公開されて困ること・人を傷つけることを書かない。
4. 「送る」を押す。送れたら、同じ画面に「送りました。返信はしません。」と出し、フォームを空にする。

### 問題の誤りの報告

1. 問題の下にある「この問題の誤りを報告」を押す。リンクは、問題を出す画面のすべてで、常に問題の下に出す(解いている途中も、解いたあとの解説、結果、ブックマークの見直し、学習モードの演習も)。
2. `/contact/question?exam=<資格コード>&id=<問題 ID>` で、対象の問題(資格の名前、問題の ID、問題文の冒頭)を確かめる。資格コードと問題 ID は、利用者が書き換えられない表示にする。
3. 種類を 1 つ選ぶ(「正解が違う」「解説が違う」「問題文・選択肢が分かりにくい」「その他」)。
4. 補足を書く(空でもよい)。注意の表示は、お問い合わせと同じ。
5. 「送る」を押す。送れたら「送りました。返信はしません。」と出し、元の画面へ戻るボタン(ブラウザの履歴を 1 つ戻る)を出す。

### 断られるとき

- 上限を超えた: 「今日はこれ以上送れません。明日またお試しください。」
- GitHub の API が失敗した、または受け付けを止めている(App の設定がない): 「いまは送れません。時間をおいてお試しください。」入力は消さない。
- 存在しない資格コード・問題 ID: 誤りの報告の画面に「対象の問題が見つかりません。」と出し、送信のボタンを出さない。

## 画面の構成とメニューの階層

- **`/contact`(新規)**: 見出し「お問い合わせ」、種類の選択(4 つのボタンから 1 つ。ラジオの役割)、内容の欄(複数行)、注意、送信のボタン、結果の表示。
- **`/contact/question`(新規)**: 見出し「問題の誤りを報告」、対象の問題の表示、種類の選択(4 つ)、補足の欄、注意、送信のボタン、結果の表示。
- **フッター(変更)**: 「利用規約とプライバシーポリシー」の隣に「お問い合わせ」のリンクを足す。
- **問題を出す画面(変更)**: 問題の下に、「この問題の誤りを報告」のリンクを常に出す(解いている途中、解いたあとの解説、結果、ブックマークの見直し、学習モードの演習。管理者のプレビューには出さない)。
- メニュー(サイドバーと下のドック)には足さない。本文の幅は、既定(`study`)にする。

## 再利用する既存の部品とレイアウト

- フォーム: `packages/app/src/components/form-parts.tsx` の `FormError`・`SubmitButton`。`Field` は 1 行の入力欄だけを描くので、複数行の欄(内容・補足)は、`feedback-form.tsx` に書く。
- 結果の表示: `packages/app/src/components/notice.tsx`。
- フッター: `packages/app/src/components/page-main.tsx` の `PageFooter`(中身は `packages/app/src/app/layout.tsx`)。
- 問題を出す画面: 問題を出す部品(`packages/app/src/components/player.tsx`(解いている途中と解説)、`result-view.tsx`(結果)、`bookmark-check.tsx`(ブックマークの見直し)、`unit-practice.tsx`(学習モードの演習))に、報告のリンクを置く。リンクは小さな部品(`packages/app/src/components/report-link.tsx`)にして、資格コードと問題 ID を受け取る。
  復習の一覧(`review-view.tsx`)は、問題文の冒頭だけを並べる一覧で、選択肢・正解・解説を出さないので置かない(誤りに気づくのは、問題を解く・見直す画面のため)。コードドリルは、問題データ(`Question`)ではないので対象外。
- 新しく作る部品: 種類の選択(4 つのボタンから 1 つを選ぶ)。既存に同じ形の部品がないため、`packages/app/src/components/feedback-form.tsx` に、2 つのフォームが共有する形で作る。

## 必要なデータ

### 送信の API

`POST /api/feedback`(ログインが要る。JSON だけを受け付け、別サイトからの送信を断る。本文の未知の項目は `400`)。

| 項目 | 内容 |
| --- | --- |
| `form` | `contact` か `question` |
| `category` | お問い合わせは `bug`・`improvement`・`feature`・`other`。誤りの報告は `answer`・`explanation`・`unclear`・`other` |
| `text` | 自由記述。お問い合わせは 1〜2000 文字(前後の空白を除いて数える)。誤りの報告は 0〜2000 文字 |
| `examCode`・`questionId` | 誤りの報告だけ。公開している問題に実在すること(サーバーで確かめる) |

応答: 成功は `201`、上限は `429`、受け付けを止めている・GitHub の API の失敗は `503`。応答に Issue の番号や URL は入れない。

### 起票する Issue

- 題(固定の形。利用者の入力を使わない): `お問い合わせ: <種類の日本語名>`、`問題の誤り: <資格コード> <問題 ID>(<種類の日本語名>)`。
- 本文: フォームの名前、種類、(誤りの報告は)資格コードと問題 ID、アプリの版(リリースノートの先頭の版)、利用者の書いた内容。
  利用者の識別子、メールアドレス、送信の時刻以外の利用者の情報は入れない。
- 無害化: 利用者の書いた内容は、コードブロック(` ``` ` で囲む)に入れて載せる。コードブロックの中では、`@名前` のメンション、`#番号` の参照、リンク、HTML が働かない。
  内容に含まれるバッククォートの連続より長い囲みを使い、囲みを内容で閉じられないようにする。
- ラベル: お問い合わせの `bug` は `user`・`bug`、`improvement` と `feature` は `user`・`feat`、`other` は `user`。誤りの報告は、どの種類も `user`・`data`。

### 送信の回数

- 1 人あたり、1 日(日本時間の日付)に 10 件まで。2 つのフォームを合わせて数える。
- `PK=USER#{sub}`、`SK=FEEDBACK#{YYYY-MM-DD}` の項目の `count` を、`UpdateItem`(`ADD`。`count < 10` を条件にする)で増やしてから、GitHub の API を呼ぶ。
  API が失敗したら、増やした 1 を戻す。条件に合わないときは `429`。
- 利用者の区画にあるので、退会で消える(`deleteUserData`)。古い日付の項目は消さない(1 日 1 項目で、小さい)。
- `docs/app/data.md` の「テーブル」「アクセスパターン」「API」に足す。

- 上限の 10 件は、GitHub の API の枠に収まる。内容を作る操作(Issue の起票を含む)は、1 分に 80 回、1 時間に 500 回まで(Web の画面の操作も同じ枠)、
  インストールのトークンの回数の上限は、1 時間あたり 5,000 回以上。1 件の送信で、起票の 1 回(トークンを発行し直すときは、発行の 1 回を足す)を使う。
  全利用者の合計がこの枠を超えたときは、GitHub の API の失敗として `503` を返し、増やした 1 を戻す。値と、公式の文書の節の名前は、`docs/app/infra.md` の「GitHub App の秘密鍵」に書く。

### GitHub App(起票の主体)

- 起票は、このリポジトリ専用の GitHub App で行う。個人のアクセストークンは使わない。起票した Issue の作成者は `<App の名前>[bot]` になり、フォームから来た Issue を、作成者の欄で見分けられる(ラベルだけに頼らない)。
- App は、このリポジトリだけにインストールする(「Only select repositories」)。権限は、Issues の書き込みと Metadata の読み取りだけ。Webhook は無効にする。App の作成とインストールは、人が GitHub の画面で行う。
- 起票先のリポジトリ(持ち主と名前)は、`packages/app/src/lib/site.ts` の `REPOSITORY_URL` から取る。
- アプリの Lambda に渡す環境変数は、次の 3 つ。3 つそろえて渡すか、どれも渡さない(一部だけ渡したときは、`packages/infra/lib/config.ts` の設定の検査で断る。VAPID の 3 つの変数と同じ形)。
  App の ID とインストールの ID は、秘密ではないが環境固有の値なので、`.env` から渡し、リポジトリに書かない。SSM には置かない。

| 変数 | 内容 | 形の検査 |
| --- | --- | --- |
| `FEEDBACK_GITHUB_APP_ID` | App の ID | 数字だけ |
| `FEEDBACK_GITHUB_INSTALLATION_ID` | インストールの ID | 数字だけ |
| `FEEDBACK_GITHUB_PRIVATE_KEY_PARAMETER` | App の秘密鍵(PEM)を置いた SSM のパラメーターの名前 | `SSM_PARAMETER_NAME` と同じ |

- 秘密鍵(PEM)は、SSM Parameter Store の SecureString に置く。扱いは `docs/app/infra.md` の「VAPID の秘密鍵」と同じ(環境変数にもテンプレートにも値を入れず、名前だけを渡す。
  この秘密鍵について、アプリの Lambda に許すのは、このパラメーター 1 つの `ssm:GetParameter` だけで、ARN にワイルドカードを使わない。
  アプリの Lambda が読むパラメーターは、VAPID の秘密鍵と合わせて 2 つになる。3 つの変数を渡さないときは、読む権限を付けない)。ブラウザには渡さない。
- 起票の手順(サーバー側だけで行う):
  1. 秘密鍵を、最初に送るときに 1 度だけ読み(`WithDecryption`)、そのプロセスの間は覚えておく。
  2. RS256 の JWT を作る。`iat` は今より 60 秒前、`exp` は今から 10 分以内、`iss` は App の ID。署名は Node の標準の `crypto` で行い、新しい依存を足さない。
  3. インストールのアクセストークンを発行する。発行のときに、リポジトリを起票先の 1 つに、権限を Issues の書き込みに絞る。
     トークンは 1 時間で切れるので、切れる 5 分前まではプロセスの間で使い回す。
  4. Issue を起票する(題・本文・ラベル)。ラベルが付くことは、デプロイ後の確認(`docs/post-deploy-smoke.md` の「送信フォーム」)で確かめる。
- 権限の名前と API の経路は、GitHub の公式の文書で確かめたものを、`docs/app/infra.md` の「GitHub App の秘密鍵」に書く。
- 3 つの変数を渡していない環境(手元の開発、テスト)では、GitHub の API を呼ばず、`503` を返す。フォームの画面は出す。テストは、GitHub の API の呼び出しを差し替えて確かめる。
- 秘密鍵の値、JWT、インストールのトークンの値と、読めない原因は、ログとエラー応答に出さない。

### 公開の扱い

- 送った内容は、そのままこのリポジトリに起票する(非公開の受け箱を経ない)。リポジトリは公開されうるので、利用者の文章は、起票と同時に公開されうる。
- 個人情報の書き込み、荒らし、宣伝は、人が見つけて Issue を消す。抑えるのは、ログインの必須、1 日 10 件の上限、コードブロックでの無害化、送信の画面と `/privacy` の注意。

## 前提

- 認証: 2 つの画面と API は、ログインが要る(`PROTECTED_PAGES`・`PROTECTED_APIS` に足す)。管理者に限らない。ゲストのお試しの利用者は対象外。
- 画面スタイル(リッチ / シンプル)、ライト / ダーク、動きを減らす設定に、既存のフォームと同じく対応する。新しい動きは足さない。
- `/privacy` を、次のとおり直す。
  - 「1. 取得する情報」: フォームで送った内容を足す。
  - 「6. 外部のサービスの利用」: GitHub(送った内容を Issue として保存する)を足す。
  - 「7. 保存期間」「8. 削除」: 送った内容は、退会しても消えないことを書く。
  - 「10. 問い合わせ」: このフォームを案内する(リンクを置く)。返信しないことを書く。
- 送った内容が公開されうることは、送信の画面と `/privacy` の両方に書く。

## 未決の点

なし。

決めたこと: 起票の主体は、このリポジトリ専用の GitHub App(JWT の署名は Node の標準の `crypto`)。公開の扱いは、非公開の受け箱を経ず、そのまま起票する。上限は 1 日 10 件(連続した送信の間隔の制限は設けない)。文字数(お問い合わせは 1〜2000 文字、誤りの報告の補足は 0〜2000 文字)。報告のリンクは、問題の下に常に出す。Issue の本文に、利用者の端末の種類を入れない。退会しても消えないことは `/privacy` にだけ書く。
