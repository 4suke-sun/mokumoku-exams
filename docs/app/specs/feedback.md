# 送信フォーム(お問い合わせ・問題の誤りの報告)の仕様

ログインした利用者が、開発者へ一方向で送るフォームを 2 つ置きます。お問い合わせの画面はログインなしでも開けますが、送るにはログインが要ります。送った内容は、サーバーが、このリポジトリ専用の GitHub App として、このリポジトリの Issue に起票します。
受け付けは一方向にとどめます。開発者からの返信、やりとりの往復、メールの通知は作りません。

## ユーザーの流れ

### お問い合わせ

1. 画面の下の注記(フッター)の「お問い合わせ」を押す。`/contact` は、ログインなしで開ける。
   ログインしていなければ、種類の選択・内容の欄・送信のボタンの代わりに、「投稿はログインユーザーのみ受け付けております。」と、「ログインする」(ログインのあとにこの画面へ戻る)・「アカウントを作成する」(新規登録の画面へ)のボタンを出す。
2. `/contact` で、画面の上(見出しの上)に「元の画面へ戻る」ボタン(ブラウザの履歴を 1 つ戻る)を出す。種類を 1 つ選ぶ(「不具合」「機能改善の要望」「機能追加の要望」「その他」)。
3. 内容を書く。送信のボタンの上に、次の注意を出す。
   - 返信はしない。
   - 送った内容は、GitHub の Issue として起票され、公開されることがある。メールアドレスなどの個人情報や、公開されて困ること・人を傷つけることを書かない。
4. 「送る」を押す。送れたら、同じ画面に「お問い合わせを受け付けました。ありがとうございます。いただいた内容は、今後の改善の参考にさせていただきます。」と出し、フォームを空にする(返信しないことは、送る前の注意で伝える)。
   お礼の言葉のあとにも、「元の画面へ戻る」ボタンを出す(画面の上のボタンと同じ働き)。

### 試験についてのお問い合わせ

1. 試験の画面(`/exams/<資格コード>` とその下のすべての画面)で、フッターの「お問い合わせ」を押す。フッターのお問い合わせのリンクは、どの画面でも 1 つで、文言も同じ。
   試験の画面では、そのリンクが `/contact?exam=<資格コード>` を指す。
2. `/contact?exam=<資格コード>` で、種類の選択の上に、対象の選択(ラジオ。種類の選択と同じ見た目)を出す: 「この試験について(<資格の名前>)」と「全般」。既定は「この試験について」。
   「この試験について」を選んでいる間は、対象の選択の下に、対象の試験(資格の名前と資格コード)を出す。資格コードは、利用者が書き換えられない表示にする。「全般」を選んだら、対象の試験の表示を消す。
3. 種類・内容・注意・「送る」と、送れたときの表示(「元の画面へ戻る」ボタンを含む)は、試験なしのお問い合わせと同じ。「この試験について」を選んで送ったときだけ資格コードを添え、「全般」を選んで送ったときは、試験なしのお問い合わせと同じく資格コードを添えない。
   送れたあとも、対象の選択と対象の試験の表示は残す(続けて送るときも、同じ対象について送る)。
4. 試験の画面以外(フッターの「お問い合わせ」、`/privacy` の本文のリンク)から開いたときは、`exam` を付けずに開き、対象の選択を出さず、従来どおり試験なしで送る。

### 問題の誤りの報告

1. 問題の下にある「この問題の誤りを報告」を押す。リンクは、問題を出す画面のすべてで、常に問題の下に出す(解いている途中も、解いたあとの解説、結果、ブックマークの見直し、学習モードの演習も)。
2. `/contact/question?exam=<資格コード>&id=<問題 ID>` で、画面の上(見出しの上)に「元の画面へ戻る」ボタン(ブラウザの履歴を 1 つ戻る)を出し、対象の問題(資格の名前、問題の ID、問題文の冒頭)を確かめる。資格コードと問題 ID は、利用者が書き換えられない表示にする。
3. 種類を 1 つ選ぶ(「正解が違う」「解説が違う」「問題文・選択肢が分かりにくい」「その他」)。
4. 補足を書く(空でもよい)。注意の表示は、お問い合わせと同じ。
5. 「送る」を押す。送れたら「ご報告ありがとうございます。いただいた内容をもとに、問題を確認します。」と出し、そのあとにも「元の画面へ戻る」ボタン(画面の上のボタンと同じ働き)を出す。

### 断られるとき

- 上限を超えた: 「今日はこれ以上送れません。明日またお試しください。」
- GitHub の API が失敗した、または受け付けを止めている(App の設定がない): 「いまは送れません。時間をおいてお試しください。」入力は消さない。
- 存在しない資格コード・問題 ID: 誤りの報告の画面に「対象の問題が見つかりません。」と出し、送信のボタンを出さない(画面の上の「元の画面へ戻る」ボタンは出す)。
- 試験についてのお問い合わせで、`exam` が公開中の資格に一致しない(手で書き換えた URL、存在しない試験の画面のフッターから開いたなど): 「対象の試験が見つかりません。」と出し、フォームを出さない。
  代わりに、試験なしのお問い合わせ(`/contact`)へのリンクを出す(画面の上の「元の画面へ戻る」ボタンは出す)。`exam` が空・形の外れ・複数あるときも、一致しないものとして扱う。`exam` が無いときだけ、従来どおり試験なしのフォームを出す。

## 画面の構成とメニューの階層

- **`/contact`(新規)**: 画面の上の「元の画面へ戻る」ボタン、見出し「お問い合わせ」、種類の選択(4 つのボタンから 1 つ。ラジオの役割)、内容の欄(複数行)、注意、送信のボタン、結果の表示(送れたときは、そのあとに「元の画面へ戻る」ボタン)。
  ログインなしで開ける(変更)。ログインしていなければ、見出しまでは同じで、フォームの代わりにログインへの案内(お知らせの通知と、「ログインする」「アカウントを作成する」のボタンの見た目のリンク)を出す。
  ログイン状態を確かめている間は、フォームも案内も出さない。`?exam=<資格コード>` が公開中の資格に一致しないときは、ログイン状態によらず「対象の試験が見つかりません。」を出す。
  `?exam=<資格コード>` が付いたとき(変更)は、種類の選択の上に、対象の選択(「この試験について(<資格の名前>)」と「全般」)と、
  「この試験について」を選んでいる間は対象の試験の表示(資格の名前と資格コード。誤りの報告の、対象の問題の表示と同じ形のカード)を足す。見出しは変えない。
- **`/contact/question`(新規)**: 画面の上の「元の画面へ戻る」ボタン、見出し「問題の誤りを報告」、対象の問題の表示、種類の選択(4 つ)、補足の欄、注意、送信のボタン、
  結果の表示(送れたときは、そのあとに「元の画面へ戻る」ボタン)。
- **フッター(変更)**: 「利用規約とプライバシーポリシー」の隣に「お問い合わせ」のリンクを 1 つ足す。文言は、どの画面でも「お問い合わせ」。
  試験の画面(`packages/app/src/lib/nav.ts` の `examCodeOf` が資格コードを返す画面)では、リンクの行き先を `/contact?exam=<資格コード>` にする。それ以外の画面では `/contact`。
  `isInExam` が真でも、URL から資格コードを取り出せない(区切りを元の文字に戻せない)ときは、`/contact` を指す。
- **問題を出す画面(変更)**: 問題の下に、「この問題の誤りを報告」のリンクを常に出す(解いている途中、解いたあとの解説、結果、ブックマークの見直し、学習モードの演習。管理者のプレビューには出さない)。
- メニュー(サイドバーと下のドック)には足さない。本文の幅は、既定(`study`)にする。

## 必要なデータ

### 送信の API

`POST /api/feedback`(ログインが要る。JSON だけを受け付け、別サイトからの送信を断る。本文の未知の項目は `400`)。

| 項目 | 内容 |
| --- | --- |
| `form` | `contact` か `question` |
| `category` | お問い合わせは `bug`・`improvement`・`feature`・`other`。誤りの報告は `answer`・`explanation`・`unclear`・`other` |
| `text` | 自由記述。お問い合わせは 1〜2000 文字(前後の空白を除いて数える)。誤りの報告は 0〜2000 文字 |
| `examCode`・`questionId` | 誤りの報告だけ。公開している問題に実在すること(サーバーで確かめる) |
| `examCode`(お問い合わせ) | 任意。試験の画面から開き、対象に「この試験について」を選んだときだけ送る。資格コードの形(`EXAM_CODE`)で、公開している資格に実在すること(サーバーで確かめる)。無いときは従来どおり |

- `FeedbackRequestSchema` のお問い合わせの側(`z.strictObject`)に、任意の `examCode`(`z.string().regex(EXAM_CODE).optional()`)を足す。ほかの未知の項目は、従来どおり `400`。
- お問い合わせの `examCode` が公開している資格に無いときは `400`(誤りの報告で、存在しない問題を `400` にするのと同じ)。確かめるのは、上限の回数を増やす前(回数を使わない)。
  確かめる関数は、`questionExists` と同じく依存として渡す(`examExists`)。
- 回数の数え方は変えない(試験の有無にかかわらず、2 つのフォームと合わせて 1 日 10 件)。

応答: 成功は `201`、上限は `429`、受け付けを止めている・問題や資格の有無を確かめられない・GitHub の API の失敗は `503`。応答に Issue の番号や URL は入れない。

### 起票する Issue

- 題(固定の形。利用者の自由記述を使わない。資格コード・問題 ID は、サーバーで公開中のデータと照合した値だけを使う): `お問い合わせ: <種類の日本語名>`、
  試験についてのお問い合わせは `お問い合わせ: <種類の日本語名>(<資格コード>)`、`問題の誤り: <資格コード> <問題 ID>(<種類の日本語名>)`。
- 本文: フォームの名前、種類、(試験についてのお問い合わせは)資格コード、(誤りの報告は)資格コードと問題 ID、アプリの版(リリースノートの先頭の版)、利用者の書いた内容。
  試験についてのお問い合わせの本文は、「種類」の行の次に「資格コード: <資格コード>」の行を足す(誤りの報告と同じ書き方)。試験なしのお問い合わせの題と本文は、従来と同じ。
  利用者の識別子、メールアドレス、送信の時刻以外の利用者の情報は入れない。
- 無害化: 利用者の書いた内容は、コードブロック(` ``` ` で囲む)に入れて載せる。コードブロックの中では、`@名前` のメンション、`#番号` の参照、リンク、HTML が働かない。
  内容に含まれるバッククォートの連続より長い囲みを使い、囲みを内容で閉じられないようにする。
- ラベル: お問い合わせの `bug` は `user`・`bug`、`improvement` と `feature` は `user`・`feat`、`other` は `user`。誤りの報告は、どの種類も `user`・`data`。
  試験についてのお問い合わせも、種類で決める(試験の有無でラベルを変えない)。
- 資格コードは個人情報ではない。資格コードを足しても、利用者の識別子とメールアドレスは、従来どおり Issue に載せない(`buildFeedbackIssue` は、それらを受け取らない)。

### 送信の回数

- 1 人あたり、1 日(日本時間の日付)に 10 件まで。2 つのフォームを合わせて数える。
- `PK=USER#{sub}`、`SK=FEEDBACK#{YYYY-MM-DD}` の項目の `count` を、`UpdateItem`(`ADD`。`count < 10` を条件にする)で増やしてから、GitHub の API を呼ぶ。
  API が失敗したら、増やした 1 を戻す。条件に合わないときは `429`。
- 利用者の区画にあるので、退会で消える(`deleteUserData`)。古い日付の項目は消さない(1 日 1 項目で、小さい)。
- `docs/app/data.md` の「テーブル」「アクセスパターン」「API」に足す。

- 上限の 10 件は、GitHub の API の枠に収まる。内容を作る操作(Issue の起票を含む)は、1 分に 80 回、1 時間に 500 回まで(Web の画面の操作も同じ枠)、
  インストールのトークンの回数の上限は、1 時間あたり 5,000 回以上。1 件の送信で、起票の 1 回(トークンを発行し直すときは、発行の 1 回を足す)を使う。
  全利用者の合計がこの枠を超えたときは、GitHub の API の失敗として `503` を返し、増やした 1 を戻す。値と、公式の文書の節の名前は、`docs/app/infra.md` の「GitHub App の秘密鍵」に書く。

### GitHub App(起票の主体)

- 起票は、このリポジトリ専用の GitHub App で行う。個人のアクセストークンは使わない。起票した Issue の作成者は `<App の名前>[bot]` になり、フォームから来た Issue を、作成者の欄で見分けられる(ラベルだけに頼らない)。
- App は、このリポジトリだけにインストールする(「Only select repositories」)。権限は、Issues の書き込みと Metadata の読み取りだけ。Webhook は無効にする。App の作成とインストールは、人が GitHub の画面で行う。
- 起票先のリポジトリ(持ち主と名前)は、`packages/app/src/lib/site.ts` の `REPOSITORY_URL` から取る。
- アプリの Lambda に渡す環境変数は、次の 3 つ。3 つそろえて渡すか、どれも渡さない(一部だけ渡したときは、`packages/infra/lib/config.ts` の設定の検査で断る。VAPID の 3 つの変数と同じ形)。
  App の ID とインストールの ID は、秘密ではないが環境固有の値なので、`.env` から渡し、リポジトリに書かない。SSM には置かない。

| 変数 | 内容 | 形の検査 |
| --- | --- | --- |
| `FEEDBACK_GITHUB_APP_ID` | App の ID | 数字だけ |
| `FEEDBACK_GITHUB_INSTALLATION_ID` | インストールの ID | 数字だけ |
| `FEEDBACK_GITHUB_PRIVATE_KEY_PARAMETER` | App の秘密鍵(PEM)を置いた SSM のパラメーターの名前 | `SSM_PARAMETER_NAME` と同じ |

- 秘密鍵(PEM)は、SSM Parameter Store の SecureString に置く。扱いは `docs/app/infra.md` の「VAPID の秘密鍵」と同じ(環境変数にもテンプレートにも値を入れず、名前だけを渡す。
  この秘密鍵について、アプリの Lambda に許すのは、このパラメーター 1 つの `ssm:GetParameter` だけで、ARN にワイルドカードを使わない。
  アプリの Lambda が読むパラメーターは、VAPID の秘密鍵と合わせて 2 つになる。3 つの変数を渡さないときは、読む権限を付けない)。ブラウザには渡さない。
- 起票の手順(サーバー側だけで行う):
  1. 秘密鍵を、最初に送るときに 1 度だけ読み(`WithDecryption`)、そのプロセスの間は覚えておく。
  2. RS256 の JWT を作る。`iat` は今より 60 秒前、`exp` は今から 10 分以内、`iss` は App の ID。署名は Node の標準の `crypto` で行い、新しい依存を足さない。
  3. インストールのアクセストークンを発行する。発行のときに、リポジトリを起票先の 1 つに、権限を Issues の書き込みに絞る。
     トークンは 1 時間で切れるので、切れる 5 分前まではプロセスの間で使い回す。
  4. Issue を起票する(題・本文・ラベル)。ラベルが付くことは、デプロイ後の確認(`docs/post-deploy-smoke.md` の「送信フォーム」)で確かめる。
- 権限の名前と API の経路は、GitHub の公式の文書で確かめたものを、`docs/app/infra.md` の「GitHub App の秘密鍵」に書く。
- 3 つの変数を渡していない環境(手元の開発、テスト)では、GitHub の API を呼ばず、`503` を返す。フォームの画面は出す。テストは、GitHub の API の呼び出しを差し替えて確かめる。
- 秘密鍵の値、JWT、インストールのトークンの値と、読めない原因は、ログとエラー応答に出さない。

### 公開の扱い

- 送った内容は、そのままこのリポジトリに起票する(非公開の受け箱を経ない)。リポジトリは公開されうるので、利用者の文章は、起票と同時に公開されうる。
- 個人情報の書き込み、荒らし、宣伝は、人が見つけて Issue を消す。抑えるのは、ログインの必須、1 日 10 件の上限、コードブロックでの無害化、送信の画面と `/privacy` の注意。

## 前提

- 認証: 問題の誤りの報告の画面と API は、ログインが要る(`PROTECTED_PAGES`・`PROTECTED_APIS` に足す)。お問い合わせの画面(`/contact`)は、ログインなしで開ける(`PUBLIC_PAGES`。変更)が、送信の API は同じくログインが要る。管理者に限らない。ゲストのお試しの利用者は対象外。
- 画面スタイル(リッチ / シンプル)、ライト / ダーク、動きを減らす設定に、既存のフォームと同じく対応する。新しい動きは足さない。
- `/privacy` を、次のとおり直す。
  - 「1. 取得する情報」: フォームで送った内容を足す。
  - 「6. 外部のサービスの利用」: GitHub(送った内容を Issue として保存する)を足す。
  - 「7. 保存期間」「8. 削除」: 送った内容は、退会しても消えないことを書く。
  - 「10. 問い合わせ」: このフォームを案内する(リンクを置く)。返信しないことを書く。
- 送った内容が公開されうることは、送信の画面と `/privacy` の両方に書く。
- 試験についてのお問い合わせで資格コードを送ることについて、`/privacy` は直さない。「1. 取得する情報」の「フォームで送った内容」に含まれ、
  「6. 外部のサービスの利用」の、Issue として保存し、メールアドレスと識別子を書かないという記載とも食い違わない。資格コードは、送る前にフォームに表示するので、利用者が確かめてから送れる。
- 試験についてのお問い合わせの API の形は `docs/app/data.md` の `POST /api/feedback` に、確かめ方は `docs/post-deploy-smoke.md` の「送信フォーム」に書く。

## 未決の点

なし。

決めたこと: 起票の主体は、このリポジトリ専用の GitHub App(JWT の署名は Node の標準の `crypto`)。公開の扱いは、非公開の受け箱を経ず、そのまま起票する。上限は 1 日 10 件(連続した送信の間隔の制限は設けない)。文字数(お問い合わせは 1〜2000 文字、誤りの報告の補足は 0〜2000 文字)。報告のリンクは、問題の下に常に出す。Issue の本文に、利用者の端末の種類を入れない。退会しても消えないことは `/privacy` にだけ書く。
試験についてのお問い合わせ: 入口は、フッターの「お問い合わせ」の 1 つだけで、試験の画面では資格コードを付けて開く(画面ごとに置かない)。開いた先で、対象(この試験について・全般。既定はこの試験について)を選ぶ。資格コードは、題と本文の両方に載せる。存在しない資格コードは、画面ではフォームを出さず試験なしの画面へのリンクを出し、API は `400`。API は、お問い合わせの側に任意の `examCode` を足す。回数とラベルは試験の有無で変えない。`/privacy` は直さない。
