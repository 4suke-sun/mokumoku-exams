# 送信フォーム(お問い合わせ・問題の誤りの報告)の仕様

ログインした利用者が、開発者へ一方向で送るフォームを 2 つ置きます。送った内容は、サーバーがこのリポジトリの Issue として起票します。
受け付けは一方向にとどめます。開発者からの返信、やりとりの往復、メールの通知は作りません。

## ユーザーの流れ

### お問い合わせ

1. 画面の下の注記(フッター)の「お問い合わせ」を押す。ログインしていなければ、ログインの画面へ移り、ログインのあとに戻る。
2. `/contact` で、種類を 1 つ選ぶ(「不具合」「機能改善の要望」「機能追加の要望」「その他」)。
3. 内容を書く。送信のボタンの上に、次の注意を出す。
   - 返信はしない。
   - 送った内容は、GitHub の Issue として起票され、公開されることがある。メールアドレスなどの個人情報や、公開されて困ること・人を傷つけることを書かない。
4. 「送る」を押す。送れたら、同じ画面に「送りました。返信はしません。」と出し、フォームを空にする。

### 問題の誤りの報告

1. 問題の下にある「この問題の誤りを報告」を押す。リンクは、問題を出す画面のすべてで、常に問題の下に出す(解いている途中も、解いたあとの解説、結果、復習も)。
2. `/contact/question?exam=<資格コード>&id=<問題 ID>` で、対象の問題(資格の名前、問題の ID、問題文の冒頭)を確かめる。資格コードと問題 ID は、利用者が書き換えられない表示にする。
3. 種類を 1 つ選ぶ(「正解が違う」「解説が違う」「問題文・選択肢が分かりにくい」「その他」)。
4. 補足を書く(空でもよい)。注意の表示は、お問い合わせと同じ。
5. 「送る」を押す。送れたら「送りました。返信はしません。」と出し、元の画面へ戻るリンクを出す。

### 断られるとき

- 上限を超えた: 「今日はこれ以上送れません。明日またお試しください。」
- GitHub の API が失敗した、または受け付けを止めている(トークンがない): 「いまは送れません。時間をおいてお試しください。」入力は消さない。
- 存在しない資格コード・問題 ID: 誤りの報告の画面に「対象の問題が見つかりません。」と出し、送信のボタンを出さない。

## 画面の構成とメニューの階層

- **`/contact`(新規)**: 見出し「お問い合わせ」、種類の選択(4 つのボタンから 1 つ。ラジオの役割)、内容の欄(複数行)、注意、送信のボタン、結果の表示。
- **`/contact/question`(新規)**: 見出し「問題の誤りを報告」、対象の問題の表示、種類の選択(4 つ)、補足の欄、注意、送信のボタン、結果の表示。
- **フッター(変更)**: 「利用規約とプライバシーポリシー」の隣に「お問い合わせ」のリンクを足す。
- **問題を出す画面(変更)**: 問題の下に、「この問題の誤りを報告」のリンクを常に出す(解いている途中、解いたあとの解説、結果、復習。管理者のプレビューには出さない)。
- メニュー(サイドバーと下のドック)には足さない。本文の幅は、既定(`study`)にする。

## 再利用する既存の部品とレイアウト

- フォーム: `packages/app/src/components/form-parts.tsx` の `Field`・`FormError`・`SubmitButton`。
- 結果の表示: `packages/app/src/components/notice.tsx`。
- フッター: `packages/app/src/components/page-main.tsx` の `PageFooter`(中身は `packages/app/src/app/layout.tsx`)。
- 問題を出す画面: `packages/app/src/components/player.tsx`、`result-view.tsx`、`review-view.tsx` など、問題を出す部品に、報告のリンクを置く。リンクは小さな部品(`packages/app/src/components/report-link.tsx`)にして、資格コードと問題 ID を受け取る。置く部品の一覧は、実装のときに `Question` を表示する箇所を検索して洗い出す。
- 新しく作る部品: 種類の選択(4 つのボタンから 1 つを選ぶ)。既存に同じ形の部品がないため、`packages/app/src/components/feedback-form.tsx` に、2 つのフォームが共有する形で作る。

## 必要なデータ

### 送信の API

`POST /api/feedback`(ログインが要る。JSON だけを受け付け、別サイトからの送信を断る。本文の未知の項目は `400`)。

| 項目 | 内容 |
| --- | --- |
| `form` | `contact` か `question` |
| `category` | お問い合わせは `bug`・`improvement`・`feature`・`other`。誤りの報告は `answer`・`explanation`・`unclear`・`other` |
| `text` | 自由記述。お問い合わせは 1〜2000 文字(前後の空白を除いて数える)。誤りの報告は 0〜2000 文字 |
| `examCode`・`questionId` | 誤りの報告だけ。公開している問題に実在すること(サーバーで確かめる) |

応答: 成功は `201`、上限は `429`、受け付けを止めている・GitHub の API の失敗は `503`。応答に Issue の番号や URL は入れない。

### 起票する Issue

- 題(固定の形。利用者の入力を使わない): `お問い合わせ: <種類の日本語名>`、`問題の誤り: <資格コード> <問題 ID>(<種類の日本語名>)`。
- 本文: フォームの名前、種類、(誤りの報告は)資格コードと問題 ID、アプリの版(リリースノートの先頭の版)、利用者の書いた内容。
  利用者の識別子、メールアドレス、送信の時刻以外の利用者の情報は入れない。
- 無害化: 利用者の書いた内容は、コードブロック(` ``` ` で囲む)に入れて載せる。コードブロックの中では、`@名前` のメンション、`#番号` の参照、リンク、HTML が働かない。
  内容に含まれるバッククォートの連続より長い囲みを使い、囲みを内容で閉じられないようにする。
- ラベル: お問い合わせの `bug` は `user`・`bug`、`improvement` と `feature` は `user`・`feat`、`other` は `user`。誤りの報告は、どの種類も `user`・`data`。

### 送信の回数

- 1 人あたり、1 日(日本時間の日付)に 10 件まで。2 つのフォームを合わせて数える。
- `PK=USER#{sub}`、`SK=FEEDBACK#{YYYY-MM-DD}` の項目の `count` を、`UpdateItem`(`ADD`。`count < 10` を条件にする)で増やしてから、GitHub の API を呼ぶ。
  API が失敗したら、増やした 1 を戻す。条件に合わないときは `429`。
- 利用者の区画にあるので、退会で消える(`deleteUserData`)。古い日付の項目は消さない(1 日 1 項目で、小さい)。
- `docs/app/data.md` の「テーブル」「アクセスパターン」「API」に足す。

### トークン

- GitHub の API を呼ぶトークンは、Issue の書き込みだけの権限で、このリポジトリだけに限る。SSM Parameter Store の SecureString に置き、アプリの Lambda にはパラメーターの名前だけを環境変数で渡す(扱いは `docs/app/infra.md` の「VAPID の秘密鍵」と同じ)。
- 名前を渡していない環境(手元の開発、テスト)では、GitHub の API を呼ばず、`503` を返す。フォームの画面は出す。テストは、GitHub の API の呼び出しを差し替えて確かめる。
- トークンの値と、読めない原因は、ログとエラー応答に出さない。

## 前提

- 認証: 2 つの画面と API は、ログインが要る(`PROTECTED_PAGES`・`PROTECTED_APIS` に足す)。管理者に限らない。ゲストのお試しの利用者は対象外。
- 画面スタイル(リッチ / シンプル)、ライト / ダーク、動きを減らす設定に、既存のフォームと同じく対応する。新しい動きは足さない。
- `/privacy` を、次のとおり直す。
  - 「1. 取得する情報」: フォームで送った内容を足す。
  - 「6. 外部のサービスの利用」: GitHub(送った内容を Issue として保存する)を足す。
  - 「7. 保存期間」「8. 削除」: 送った内容は、退会しても消えないことを書く。
  - 「10. 問い合わせ」: このフォームを案内する(リンクを置く)。返信しないことを書く。
- 送った内容が公開されうることは、送信の画面と `/privacy` の両方に書く。

## 未決の点

なし。

決めたこと: 上限は 1 日 10 件(連続した送信の間隔の制限は設けない)。文字数(お問い合わせは 1〜2000 文字、誤りの報告の補足は 0〜2000 文字)。報告のリンクは、問題の下に常に出す。Issue の本文に、利用者の端末の種類を入れない。退会しても消えないことは `/privacy` にだけ書く。
