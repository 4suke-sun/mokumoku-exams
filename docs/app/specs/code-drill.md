# コードドリルの仕様

コード(Spark SQL・PySpark)の問題を、穴埋めと全文入力で解くモードです。コードは実行しません。
答えたあとに、正解のコードを実行するとどうなるか、誤りを入れるとどうなるか(エラー、結果の変化)を、文章と図で示します。
最初は Data Engineer Associate(`DBX-DEA-2605`)で作ります。

## ユーザーの流れ

1. モード選択(`/exams/<コード>`)で「コードドリル」を選ぶ。
2. 一覧(`/exams/<コード>/code-drill`)で、分野ごとに並んだ問題(題・言語)から 1 問を選ぶ。
3. 問題の画面(`/exams/<コード>/code-drill/<問題 ID>`)で、問いと要件を読み、解き方(穴埋め / 全文入力)を選ぶ。既定は穴埋め。
4. 穴埋め: 断片を押すと、先頭の空いた穴に入る。埋めた穴を押すと外れる。「すべてクリア」で、ヒントで埋めた穴を除く全部の穴が空に戻る。全部の穴が埋まると「回答する」が押せる。
5. 全文入力: コード全体を入力し、「回答する」を押す(空のときは押せない)。
   - 迷ったら、どちらの解き方でも「ヒント」を押すと、1 か所ずつ正解が明らかになる(何度でも押せる)。
6. 「回答する」を押すと確定し、正誤、正解のコード、解説、「実行するとどうなるか」(文章と、あれば図)、出典が出る。
   - 不正解のときは、誤りの箇所に応じた「実行するとどうなるか」を先に出す(「必要なデータ」の「実行するとどうなるか」)。
7. 「もう一度」で同じ問題を未回答に戻す。「次の問題」で一覧の次の問題へ移る(最後の問題では「一覧へ戻る」)。結果は保存しない。

## 画面の構成とメニューの階層

- **一覧** `/exams/<コード>/code-drill`: 分野ごとの見出しの下に、問題の行(題・言語のラベル「SQL」「PySpark」)。言語での絞り込み(すべて / SQL / PySpark)。
- **問題の画面** `/exams/<コード>/code-drill/<問題 ID>`:
  - パンくず(コードドリル › 分野)、題、言語のラベル、問いと要件。
  - 解き方の切り替え(タブ: 穴埋め / 全文入力)。切り替えても、それぞれの入力は別々に保つ。どちらも「回答する」を押すまで回答にしない。確定後は切り替えられない(「もう一度」で戻る)。
  - **穴埋め**: 穴のあるコード(等幅。穴はボタンで、「穴 1」のように番号と状態(空 / 入れた断片)を文字で示す)。その下に、断片のボタンの並び(使った断片は薄くなり、押せない。同じ語が 2 つの穴に入るときは、同じ断片を 2 つ置く)。「すべてクリア」。
  - **全文入力**: 等幅の入力欄(改行・空白をそのまま保つ。Tab キーはフォーカスの移動のまま使い、インデントは空白で入れる)。入力は空で始める。ヒントの欄は、入力欄の下に出す。
  - 「ヒント」(穴埋め・全文入力の両方。「ヒント」の節)と「回答する」。
  - **確定後**: 正誤(文字と記号。色だけに頼らない)、穴ごとの正誤(穴埋め)、正解のコード、「実行するとどうなるか」、解説、出典、「もう一度」「次の問題」。
- 入口: モード選択に「コードドリル」のカードを足す。コードドリルのデータがない資格、検証済みの問題が 1 つもない資格では出さない。データがない資格の画面は 404 にする。
- **管理者のプレビュー** `/admin/preview/<コード>/code-drill`(と、その下の問題の画面): 利用者の画面と同じ構成で、未検証の問題も出す。入口は、全問のプレビューの資格の一覧(`/admin/preview`)。

## 必要なデータ

- 読む: `data/code-drill.<コード>.json`(静的なファイル。ビルド時に読む)。問題の選択式のモード(通常出題・本番・セクション・復習)には混ざらない。
- データの契約: `packages/data-schema/src/code-drill-data/` にスキーマと検査を置き、`npm run validate:data` に足す(`scripts/` に検査のスクリプト、`package.json` の `validate:data`、`packages/data-schema/package.json` の `exports`)。`docs/data-spec.md` に「15. コードドリルのデータ」を足し、`docs/adding-an-exam.md` の「2. ファイルの命名と配置」の表に足す。
- 形(案):

  ```text
  { examCode, problems: [ {
      id,            // <問題 ID の接頭辞>-CD-<4 桁>(例: DEA-CD-0001)。問題データの ID と重ならない
      domain,        // 分野のコード
      language,      // "sql" | "pyspark"
      title,         // 一覧に出す題(60 文字以内)
      prompt,        // 問いと要件(本文の記法)
      template,      // 穴のあるコード。穴は {{1}}, {{2}} … の形
      blanks: [ { answer } ],                // 穴ごとの正解の断片(穴の番号の順)
      distractors: [ { text, blank, outcome } ],
                     // 誤りの断片。blank は、取り違えを狙う穴の番号。outcome は「実行するとどうなるか」
      solutions: [ … ],                      // 全文入力で正解にするコード。先頭は template に blanks を入れたもの。2 つ目以降は別解
      mistakes: [ { code, outcome } ],       // 全文入力のよくある誤り(任意)
      result,        // 正解のコードを実行した結果: { text, diagram? }
      explanation,   // 解説
      references,    // 出典(問題の references と同じ形と規則)
      status         // "verified" | "unverified"
  } ] }
  ```

  - `outcome` は `{ kind, text, diagram? }`。`kind` は `error`(エラーになる)/ `different-result`(結果が変わる)/ `same-result`(結果は同じだが要件を満たさない。例: 重複を防げない)。
- 検査:
  - `template` の穴の番号が 1 から連番で、`blanks` の数と同じ。`template` に `blanks` を入れると `solutions` の先頭になる。
  - 誤りの断片の `blank` が、ある穴の番号を指す。誤りの断片の `text` が、その穴の正解と同じでない。断片(正解と誤り)の数は、1 問あたり穴の数 + 2 以上、12 以下。
  - `solutions` に重複がない(判定の正規化をかけたあとで比べる)。`mistakes[].code` が、正規化のあとで `solutions` のどれとも一致しない。
  - 図は `DiagramSchema`(`packages/data-schema/src/curriculum-data/schema.ts`)で検査する。
  - 出典のドメインが許可の一覧(`ALLOWED_REFERENCE_HOSTS`)にある。文字の項目に URL を書けない決まり(`docs/data-spec.md` の「4. 機械検査する規則」の 20)を、コード以外の文字の項目に適用する。
  - ID が一意で、形に合う。分野のコードが資格マスタにある。
- **全文入力の判定**:
  - 正規化した入力が、正規化した `solutions` のどれかと完全一致すれば正解。
  - 正規化(両方の言語): 行末の空白と空行を除き、改行の形(CRLF / LF)をそろえ、前後の空白を除く。文字列リテラル(`'…'`・`"…"`)の中は変えない。
  - SQL: 文字列リテラルの外の、連続する空白・改行・インデントを 1 つの空白にし、記号(括弧・カンマ・`;`・演算子・`.` など)の前後の空白を除く。末尾の `;` を 1 つまで無視する。キーワード(`SELECT`・`MERGE`・`FILEFORMAT` など。一覧は `packages/data-schema/src/code-drill-data/normalize.ts` の `SQL_KEYWORDS`)は、大文字小文字を区別しない。一覧の語は、識別子として使っていても区別しない。型・形式の名前(`STRING`・`JSON` など)は、キーワードに含めず、区別する。
  - PySpark: 括弧の中の改行とインデントは無視する(1 つの空白にする)。括弧の外の行頭のインデントは、深さの相対を保つ(Python では意味を持つため)。記号の前後の空白は、SQL と同じく除く。
  - 識別子・文字列リテラル・PySpark の名前の大文字小文字と、引用符の種類は、そろえない。
  - 判定の結果は、正誤と、一致した `mistakes` があればその番号だけ。入力したコードの実行結果は断定しない。
- **実行するとどうなるか**:
  - 穴埋めの不正解: 誤りの断片を、その断片の `blank` の穴に入れたときは、その `outcome` を出す。正解の断片を別の穴に入れたとき(入れ替え)や、`blank` と違う穴に入れたときは、「この位置には入りません」と、その穴の正解だけを示す(結果は断定しない)。
  - 全文入力の不正解: `mistakes` と一致したときは、その `outcome` を出す。一致しないときは、正解のコードを実行した結果(`result`)と、正解のコードを並べて示し、入力したコードの結果は断定しない。
  - 正解のとき: 正解のコードを実行した結果(`result`)を出す。
  - エラーの文言: 公式の文書にあるものだけを書く。引用は、エラーの名前・コードなど表記を正しく示す短い部分だけにし(`docs/source-policy.md` の「2. 言い換えと引用」の上限の中)、意味は自分の言葉で書く。上限に収まらない文言は書かず、出典の文書で示す。
- **問題の数と内訳(DEA)**: 20 問。`docs/exam-style/dbx-dea.md` の「2. 設問の構成」の、コードを含む問の分野ごとの割合(変換とモデリング約 3 分の 2、取り込み・ガバナンス約 4 割)に配点を掛けて目安にし、SQL・PySpark で書けない CI/CD(CLI のコマンドとバンドルの構成)は除く。
  - 変換とモデリング(`domain3`)10 問(SQL 5、PySpark 5)、取り込み(`domain2`)6 問(SQL 2、PySpark 4)、ガバナンス(`domain7`)4 問(SQL 4)。合計 SQL 11、PySpark 9。
  - テーブルの操作(`MERGE INTO`、行の更新と削除、スキーマの進化など)の問題には、`result` と `outcome` に図(表の変化)を付ける。
- **作り方**: 手作業で作り、別のサブエージェントの検証役で、出典の節だけを根拠に検証してから `verified` にする(作問の検証 `.claude/agents/question-verifier.md` と同じ見方。記憶や推測を根拠にしない)。確かめること: 正解のコードが要件を満たす、誤りの断片がその穴では誤りである、別解が正解と同じ結果になる、`outcome`(エラーを含む)と `result` の文章と図が出典と食い違わない。根拠のないものは出さない。文章は出典の文を写さず、自分の言葉で書く。種は、体系ノートの解説のコードのブロック(SQL 63、Python 28)と、演習の問題。
- 正規化の関数(`packages/data-schema/src/code-drill-data/normalize.ts` の `normalizeCode`)は、データの検査(別解の重なり)と、画面の判定(`packages/app/src/lib/code-drill.ts` の `judgeCode`)で共有する。
- 書く: なし(結果は、履歴・統計・復習・端末のいずれにも保存しない)。

## 前提

- 認証: 問題演習と同じ(ログインが要る)。管理者のプレビューは、管理者だけが開ける(`/admin` 以下の確認を通る)。新しい経路を `packages/app/src/authorization.test.ts` の経路の一覧に、保護する経路として足す。
- 公開の絞り込み: 利用者の画面には、検証済みの問題だけを出す。一覧・モード選択の数も、検証済みだけで数える。未検証の問題は、管理者のプレビューにだけ出す。
- コードは実行しない。入力したコードは文字として表示するだけにし、HTML として解釈しない(本文の記法の処理にも通さない)。
- 操作: 穴・断片・タブは、キーボードだけで操作できる(ボタンとタブの役割)。穴の状態と正誤は、色だけでなく文字で示し、読み上げにも伝える(`aria-live`。断片を入れた・外したときに「穴 2 に distinct を入れました」のように伝える)。
- 画面スタイル: リッチでは、断片が穴に入る動きと、図の動きを、1 回ずつ短く出す。シンプルと、動きを減らす設定では止めて、最終の状態を出す。
- ライト / ダーク: 両方に対応する(色はテーマの役割の色だけ)。
- 画面の幅: 等倍で横にはみ出さない。長いコードは、欄の中で横にスクロールする(コードの行を折り返すと、インデントの意味が読み取りにくいため)。断片のボタンは折り返して並べる。図は狭い画面で上下に積む。
- 見た目の方針は、[デザイン方針](../design-tone.md) に「コードドリルの画面」の節を足して書く。

## 決定事項

1. 問題は手作業で作り、別のサブエージェントの検証役で検証してから公開する。作問パイプラインの段階にするのは、形が固まってから別の Issue で扱う。
2. データは新しいファイル(`data/code-drill.<コード>.json`)に置き、選択式のモードに混ぜない。
3. 結果は、履歴・統計・復習に記録しない。記録は、モードの形が固まってから別の Issue で扱う。
4. 穴埋めの断片は、1 回ずつ使える。穴を押すと外れ、「すべてクリア」で全部外れる(ヒントで埋めた穴は外れない)。全部の穴が埋まる前は「回答する」を押せない。
5. 全文入力は、正規化したうえで正解か別解と完全一致したときだけ正解にする。キーワードを含むかの判定は使わない。
6. 図は、この版で種類を足さず、体系ノートの図を増やす版(v0.73.0)の部品を使う。足りない図は、図の版の側に足す。
7. データは資格ごとのファイルにし、言語は項目で持つ(資格に依らない形)。ほかの資格は、資格ごとに別の Issue で足す。
8. モードの名前は「コードドリル」(経路 `code-drill`、ファイル `code-drill.<コード>.json`)。「コード」だけだと、試験コードと紛れるため。
9. SQL のキーワード(`SELECT`・`MERGE INTO` など)の大文字小文字は、全文入力の判定で同一視する。根拠は、公式の文書(SQL リファレンスの使い方のページ)の、キーワードは大文字で書くが大文字小文字を区別しない、という記述。識別子・文字列リテラル・PySpark の名前は同一視しない。
10. 全文入力の欄は空で始める。
11. 一覧に、言語での絞り込み(すべて / SQL / PySpark)を入れる。
12. 管理者のプレビューを、この版で入れる。
13. 穴埋めと全文入力の両方に「ヒント」を置く。押すごとに 1 か所ずつ正解が埋まり、回数の上限はない(「ヒント」を参照)。

## ヒント

- 「回答する」の前だけ押せる。押すたびに 1 か所(穴 1 つ)ずつ正解を明かす。回数の上限はなく、すべての穴が明らかになると押せなくなる。
- **穴埋め**: 先頭から見て、まだヒントで明かしていない穴のうち最初の穴に、正解の断片を入れる(入っていた断片は外れて、断片の並びに戻る。すでに正解の断片が入っていれば、そのまま明かした印を付ける)。押せるかどうかで、入れた断片の正誤が分からないようにする。ヒントで埋めた穴は「ヒント」と文字で示し、外せない。
- **全文入力**: 入力欄は書き換えない。入力欄の下に「ヒント」の欄を出し、1 回目で穴のあるコード(穴は伏せ字)を、2 回目からは押すごとに穴を 1 つずつ正解の断片で埋めて見せる。
- 正誤の判定は、ヒントの有無で変えない。確定後に「ヒントを 2 回使いました」のように、使った回数を出す(保存はしない)。
- 読み上げでも、明かした内容を伝える(例: 「穴 2 に distinct を入れました(ヒント)」)。
