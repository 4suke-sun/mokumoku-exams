# 0026. 動的なページと API は、当面 Lambda Web Adapter の構成のままにする

- 状態: 採用
- 日付: 2026-11-21

## 背景

動的なページと API は、Lambda Web Adapter 上の Next.js を、CloudFront の背後の Function URL(`authType: NONE` + 合言葉のヘッダー)で動かしている。
AWS Lambda Web Functions は、ポートで待ち受ける HTTP サーバーを、アダプターなしで載せる Lambda の形式で、専用のエンドポイント、変更できないリビジョン、
1 つの実行環境での同時処理を持つ。移せるかを調べた結果は [Lambda Web Functions の調査](../lambda-web-functions.md) にある。

## 決定

- 当面は移さず、今の構成(Lambda Web Adapter + Function URL + 合言葉のヘッダー)を続ける。
- 次のどれかがそろったときに、移すかを見直す。
  - デプロイの道具(`cdkd`、または v1.0.0 以降に選ぶ道具)で、`AWS::Lambda::WebFunction` 本体を含む 3 つのリソースを作れることを、検証用の環境で確かめられた。
  - 東京の単価と無料利用枠が分かり、今の利用の規模で、費用が今の構成と同じか下がる見込みが立った。
  - 通信が増え、1 つの実行環境での同時処理や、重みでの切り戻しの利点が、費用の差を上回る。
- 移すと決めたときは、移行の計画(順序、切り戻し、文書の更新)を別の Issue にする。

## 理由

- **デプロイの道具が追いついていない**: 固定している `cdkd` は、リビジョンとエンドポイントに専用の処理を持つが、本体(`AWS::Lambda::WebFunction`)にはない。
  Cloud Control API の対応の一覧にも載っておらず、本体を作れるかが分からない。CDK にも L2 の構成がなく、L1 と、CloudFront の OAC の差し込みを自前で書くことになる。
- **費用が増える見込みが高い**: 実行環境は 2 GB に固定で、生きている間のメモリが待ち時間も含めて課金される。
  今の規模では、従来の関数は無料利用枠に収まる見込みが高い。東京の単価と、Web Functions の無料利用枠は確かめられていない。
- **今の構成で困っていない**: 画面と API は今の構成で動いており、移して得られるもの(アダプターが不要、重みでの切り戻し、同時処理)は、今の規模では小さい。
- **移せないわけではない**: OAC の形で、同じ配信元の構成と、Cookie でトークンを持つ認証は保てる。Next.js の standalone も、入口の `index.js` を足せば動かせる見込みである。
  見直すときに、ここから始められる。

## 採用しなかった選択肢

- すぐに移す: デプロイの道具が本体を作れるか分からず、費用も増える見込みが高い。得られるものが小さい。
- 本体だけを AWS CLI(`aws lambda-web`)で作り、残りを `cdkd` で作る: 構成の一部が IaC の外に出て、`cdkd` と素の操作が混ざる。
  デプロイの手順と切り戻しが 2 つの道具にまたがる。
- 本体をカスタムリソースで作る: カスタムリソースの Lambda を保守することになる。デプロイの道具の対応を待つほうが、手間が少ない。
- 移さないと決めて、見直さない: 新しい形式で、道具と料金の情報がまだそろっていない。そろった時点で判断し直す余地を残す。

## 影響

- `docs/app/infra.md`、`docs/app/architecture-plan.md`、`CLAUDE.md` の構成の記述は変えない。
- 合言葉のヘッダー(`ORIGIN_VERIFY_VALUE`)と、Lambda Web Adapter のレイヤー(`WEB_ADAPTER_LAYER_ARN`)の設定は、引き続き必要である。
- 見直すときは、[Lambda Web Functions の調査](../lambda-web-functions.md) の「まだ確かめていないこと」から始める。
