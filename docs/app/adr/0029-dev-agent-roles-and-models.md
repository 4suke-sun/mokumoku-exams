# 0029. 開発のサブエージェントの役の割り当てと、モデルの使い分け

- 状態: 採用
- 日付: 2026-11-23
- 置き換える ADR: 0003

## 背景

commit・push・PR・Issue の前に、文面を書く側と、確かめる側を分けます。分ける目的は、確かめる側が、書いた側の文脈を引き継がない目で見ることです。
サブエージェントは、起動のたびに、最初の応答で入力を読みます(起動分。`npm run agent-cost` で集計できます。1 回あたり約 1 万トークンです)。起動が多い役は、費用のうち起動分が大きくなります。
書く側の定義(コミットメッセージの作成役、PR・Issue の作成役)は、手順と書式を書いただけで、独立した目として働くことに意味がありません。文脈を引き継がない目が要るのは、確かめる側です。
定義を持たないサブエージェント(`general-purpose`)は、メインのセッションと同じモデルで動くので、用途ごとに専用の定義へ回すと、費用を抑えられます。

## 決定

エージェントの定義を `.claude/agents/` に置き、役ごとにモデルを完全な ID で固定します。

| 役 | エージェント | モデル | 使う場面 |
| --- | --- | --- | --- |
| 文面の作成(コミットメッセージ案、PR・Issue の下書き) | メインのセッション | Sonnet 5.5 または Opus 5.5 | commit・pr(書き方は `.claude/skills/dev-commit/writer-rules.md`) |
| 検査役 | `inspector` | Haiku 5.5 | commit・push・PR・Issue の全般 |
| 検査役(深め) | `inspector-deep` | Sonnet 5.5 | 差分に `scripts/`、`.githooks/`、`.github/workflows/`、`.claude/` を含むとき、`inspector` と併せて使い、最も重い判定を採用する |
| バッチでの生成 | `batch-generator` | Sonnet 5.5 | 体系ノートの書き直し、図の下書き、問題データのタグ付け、出題の傾向の蒸留など(割り当ては `docs/subagent-usage.md`) |
| 体系ノートの文体の直し | `notebook-reviser` | Sonnet 5.5 | 体系ノートの本文を、文体の規則に沿って直す |
| 版ごとの実装・リベース、保留の再判定、生成物の検証、レビュー | 定義を持たない(`general-purpose`) | メインのセッションと同じ | 用途ごとの割り当ては `docs/subagent-usage.md`。保留の再判定と生成物の検証は、Sonnet に下げられるかを、同じ入力の突き合わせで確かめてから決める |
| 開発本体 | メインのセッション | Sonnet 5.5 または Opus 5.5 | 実装・設計 |

作問パイプラインの役のモデルは、ADR 0015 と ADR 0021 が決めます。

- 書く側と確かめる側は、別にします。書くのはメインのセッション、確かめるのは検査役のサブエージェントです。検査役に書かせて確かめさせません。
  書く側が文脈から持ち込みやすい語(外部の事情や経緯)は、検査役のチェックリスト(`.claude/skills/dev-commit/checklist.md`)が見ます。
- 書いてよい場所は、`.drafts/` の下だけです(コミットメッセージ案は `.drafts/commit-msg.txt`)。
- 検査役の道具は、Read / Grep / Glob だけにします(Bash は持たせません)。検査役が読む入力(差分・コミットのログ・ブランチ名・拒否リストの置き場)は、
  メインのセッションが `.drafts/inspect/` に書き出します(`scripts/prepare-inspection.ts`)。検査役の報告のスタンプをいまの入力と照合してから消します。
- `inspector-deep` は、畳みません。検査の仕組みを変える差分では、2 つの検査役の指摘が補い合い、どちらか一方だけが見つける指摘があります。
- 定義のある用途は、その定義を使います。定義を持たないサブエージェントは、合う定義がない用途だけに使います(`CONTRIBUTING.md` の「サブエージェントの使い分け」)。
- 権限の設定(`.claude/settings.json`)で、次を決めます。
  - 禁止(deny): `--force` 系と `--no-verify` を付けた git の操作。
  - 確認必須(ask): 外に出す操作と、環境やリポジトリのデータを消す・移す操作だけにします。形はすべて先頭に `*` を付け、`env` や `bash -c` の後ろの呼び出しも拾います。
    対象と照合の書き方は、`CONTRIBUTING.md` の「権限の確認(ask)の範囲」にあります。
  - 禁止にした操作を、例外として行うときは、人が自分で実行します(理由を説明して承認を待つ)。
- 権限の設定の効き方は、次のとおりです。
  - deny は、メインのセッションからも、サブエージェントからも、権限で拒否されます。
  - ask は、権限の確認を省く動作モードでは、確認になりません。確認なしで実行されます。ask は「確認を求める設定」であって、強制ではありません。
    確実に止めたい操作は、deny にして人が実行するか、フックで止める必要があります。
  - push と、PR・Issue の作成、題・本文の編集は、PreToolUse のフック(`scripts/approval-hook.ts`)で止めます。人の承認の印(`.git` の下。有効 60 分)がないと、終了コード 2 で止めます。
    サブエージェントからの呼び出しは、印があっても止めます。仕組みの全体(印が覆う範囲、見分けられない形、止めすぎる形)は、`CONTRIBUTING.md` の「承認の印」にあります。
  - 読み取り役(`Explore`・`Plan`)の Bash は、フックが、読み取りのコマンドだけを許可リストで通します。
  - スキルが求める承認(本文と検査の結果を見せて待つ)と、ask の確認は、別のものです。ask は機械的な最後の関門で、二重になるのを許容します。
- モデルの選定は、新しい仕組みやワークフローを組むときに行います。都度の判断では変えません。
- メインのセッションが Agent ツールの引数でモデルを指すときは、別名しか使えません。定義のあるエージェントを使うことで、完全な ID を固定します。

## 理由

検査役を Haiku 5.5 と Sonnet 5.5 で比べると、次の傾向があります。

- 文書に仕込んだ漏えいを見つける力は、同等です。問題のない文書では、Sonnet のほうが軽微な注記を多く出します。
- コードを読む場合、取りこぼしが役ごとに別々です。1 つだけに頼ると穴が残るので、検査の仕組みを変える差分では 2 つを併せます。
- 速度は同程度で、コードを読む場合は Haiku のほうが遅くなることがあります。単価は Sonnet より大幅に低く、検査の費用を抑えられます。

この比較は、事例が少なく、ばらつきを含みます。

書く側を別のサブエージェントにする利点は、確かめる側が書いた側と別であれば、すでに得られます。書く側の起動は、コミットと PR・Issue のたびに起きるので、起動分の費用が大きくなります。
書く側をメインのセッションに戻すと、起動分は減ります。一方で、メインのセッションが、書くための手順を読み込むので、メインの 1 リクエストあたりの読み込みが増えます。
どちらが大きいかは、費用の集計(`npm run agent-cost`)の前後比較で確かめます。

## 採用しなかった選択肢

- 書く側を別のサブエージェントのままにする: 起動分の費用が残ります。書く側の範囲(`.drafts/` の下だけ、git の書き込みとネットワーク操作をしない)を、定義の道具と本文の指示で担保できる利点がありますが、メインのセッションは、承認の印のフックなど、別の仕組みで守られます。
- `inspector-deep` を畳み、検査役を 1 つにする: 検査の仕組みを変える差分で、取りこぼしが残ります。
- すべての役を Sonnet にする: 結果は同等でも、費用が大きいままです。
- すべての検査を Haiku だけにする: 検査の仕組みを変える差分で、取りこぼしが残ります。
- モデルの別名(`haiku` など)で指定する: 別名の指す先が変わると、検査の水準が気づかないうちに変わります。エージェントの定義では、完全な ID で固定します。

## 影響

- commit・push・PR の起動分の費用が下がります。メインのセッションの読み込みが増えます。前後の比較で、メインの増加が起動分の減少を上回るときは、この決定を見直します。
- 書く側の質は、検査役のチェックリストと、書く側の決まり(`writer-rules.md`)で担保します。書く側が文脈から持ち込みやすい語は、検査役が見続けます。
- フックの判定(`scripts/lib/subagent-command.ts`)は、読み取り役だけを対象にします。
- 書く側の回帰の課題(`docs/lessons-regression.md` の書く側の課題)は、書く工程を担う実行者を替えて流し、前の定義の結果と比べます。
- モデルの世代が変わるときは、新しい ADR で置き換え、比較をやり直します。
- 定義を変えたら、`inspector` と `inspector-deep` の両方で検査します。
- 検査役の読み取り専用は、道具の絞り込み(Bash を持たせない)で担保します。書き込みになるコマンドを、本文の指示で禁じる形はやめました。
  代わりに、検査役が必要とする情報は、メインのセッションが先に書き出します。書き出しにない情報は、検査役は読めません。
