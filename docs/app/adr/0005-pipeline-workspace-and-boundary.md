# 0005. 作問パイプラインを同じリポジトリの 3 つ目のワークスペースに置き、境界を守る

- 状態: 採用
- 日付: 2026-10-13

## 背景

問題を、品質と費用を管理しながら作る仕組み(収集、事実カード、出題計画、下書き、検証、解説・出典、書き出し)を持ちます。
この仕組みの置き場を、アプリと同じリポジトリにするか、別にするかを決める必要があります。

## 決定

- `packages/pipeline` を、`packages/app`・`packages/infra` と並ぶ 3 つ目のワークスペースとして置きます。
- pipeline は、app の内部(`packages/app/src` 以下)を import しません。逆も同じです。
- 共有するのは**契約**だけです。データの仕様、スキーマと検査、出典に許すドメインの一覧が該当します。
  契約は共有パッケージに置きます。共有パッケージは `packages/data-schema` で、ADR 0011 が ADR 0004 を置き換えます。
- 境界は、CI の検査で守ります(import の向きを機械で確かめる)。
- Git のサブモジュールは使いません。

## 理由

- 公開する問題の正は `data/` で、pipeline はその仕様に従います。同じリポジトリなら、仕様と pipeline を 1 つの PR で一緒に直せ、
  食い違いが残りません。
- 管理する場所が 1 つで済みます。Issue、版、CI、規約(検査の流れ)を二重に持たなくて済みます。
- 境界を検査で守れば、同居していても、あとで切り出せます。

## 採用しなかった選択肢

- 別の非公開リポジトリに置く: 権利の問題は台帳の方針(ADR 0006)で解けるため、分ける理由になりません。
  仕様の変更が 2 つのリポジトリにまたがり、管理が二重になります。
- サブモジュールにする: 参照の更新と履歴の管理が複雑になり、利点より手間が大きくなります。
- app の中に置く: 実行時のバンドルや依存に作問の道具が混ざります。

## 影響

- ルートの `lint` / `build` / `test` は、pipeline も対象にします。
- CI は、変更したパスごとに分け、pipeline のテストは通信なしで動かします。
- 切り出しの条件は、ADR 0010 に書きます。
