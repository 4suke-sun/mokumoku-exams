# 0022. 非公開の問題は、アプリが読まない別のファイルに持つ

- 状態: 採用
- 日付: 2026-10-27

## 背景

公開している問題を外す手段は、削除と、資格マスタの `retiredQuestionIds` への ID の追加だけだった。この状態では、あとから公開に戻せない。
基準を満たさない問題を、削除せずに残して、書き直してから公開に戻せるようにしたい(質を上げる機構。判定の仕組みは ADR 0021)。
アプリには、非公開の問題を載せない。画面で隠すのではなく、配信の対象から外す。

アプリは、ビルド時に `data/questions.<資格コード>.json` を読み込む(`loadQuestions` の動的な `import`)。バンドラは、この形の `import` を、`data/` の `questions.*.json` すべてを対象にする読み込みとして扱う。
問題データの検査(`validate:data`)と、削除した ID の検査(`check:retired-ids`)も、公開の問題のファイルとして `questions.*.json` の名前を対象にする(非公開のファイルの扱いは、次の「決定」)。

## 決定

- 非公開の問題は、`data/unpublished.<資格コードの英小文字>.json` に持つ。ファイル名を `questions.` で始めない。
  - アプリの読み込み(`questions.<コード>.json`)とバンドラの対象に入らない。配信に載らないことが、名前の形で守られる。
  - 公開の問題の検査の対象(`questions.*.json`)は変えない。非公開の問題は、`validate:data` と `check:retired-ids` が、非公開のファイルを別に読んで検査する。
- 1 件の形は、`{ verdict, reasons, question }` とする。`question` は、公開の問題と同じ形で、本文を変えずに持つ。`verdict` は `rewritable`(書き直して戻せる)か `unpublish`(同じ内容では直らない)、`reasons` は非公開にした理由(判定の段階の理由コード)。
  公開に戻すときは、`question` をそのまま公開のファイルへ移す。ID は変わらない。
- 非公開は、削除 + 退役とは別の状態にする。退役した ID は復帰しない。非公開の ID は復帰できる。
- データの検査(`validate:data`)は、非公開の ID が、退役した ID・公開の問題・非公開の中の別の問題と重ならないことと、分野・接頭辞が資格マスタと合うことを確かめる。本番モードの出題数(選択式の問題数)は、公開の問題だけで数える。
- `check:retired-ids` は、公開と非公開のあいだの移動を、削除とみなさない(同じ資格の公開と非公開の ID を合わせて数える)。非公開のファイルから消えた ID は、削除として、`retiredQuestionIds` に求める。
- 作問パイプラインの書き出し(`export`)は、非公開の ID も使用済みとして採番する。
- 移す作業は、パイプラインの `unpublish` コマンドで行う。判定の結果(`judge`)から、公開のファイルから非公開のファイルへ移す。
  - 判定が古い問題(判定のあとに、問題の内容・判定の基準・判定役の定義のどれかが変わったもの)は移さない。判定の機構(`judge`)が「判定済み」とみなす条件と同じにする。
  - カリキュラムの単元・段階(`units[].questionIds` と `units[].stages[].questionIds`)か、要約カードから参照されている問題は移さない(参照が切れるため。先に参照を直す)。
  - 公開の選択式が、本番モードの出題数を下回る移し方は、何も書かずに止める。
  - 書く前に、移したあとのデータ全体の検査を通し、失敗したら何も書かない。書く順序は、非公開のファイル、公開のファイルで、書き込みが途中で失敗したときは、2 つのファイルを元に戻す。
    プロセスが書き込みの途中で止まった場合は、同じ ID が両方のファイルに残り、`validate:data` が重なりで止める。直すには、非公開のファイルから該当の件を消す(その件だけだったときは、ファイルごと消す)。または、この作業の移動をまだコミットしていないなら、`data/unpublished.<コード>.json`(新しく作られて追跡されていなければ、消す)と `data/questions.<コード>.json` を `git checkout` で戻して、やり直す(この 2 つのファイルの、同じ作業の未コミットの変更も戻るので、差分を確かめてから行う)。
  - 移した結果は、作業ツリーの `data/` の差分として、PR で人が確かめる。
- 配信に含まれないことは、2 つで守る。(1)上の名前の形。(2)CI の `check:unpublished-bundle` が、アプリのビルド成果物(`.next`)から、非公開の問題の設問文と ID を探し、見つかれば失敗にする(設問文が 12 文字未満の問題は、設問文を探さず、ID だけを探す(偶然の一致を避けるため))。
- 履歴・復習・ブックマークは、問題の ID だけを持つ。非公開の問題は、いまのデータにない問題と同じ扱いにする(一覧にも、数にも、ID にも出さない)。非公開から公開に戻せば、同じ ID で再び出る。
  結果の数(解いた数・正答率)は、いまの公開の問題だけで数え直す。非公開の期間は、その問題の分が数に入らない。

## 理由

- 問題ごとのフィールド(例: 状態を表す印)で持つ案は、データが 1 か所にまとまるが、アプリの読み込みが問題ファイルをそのまま取り込むので、ビルドの前に取り除く処理が要る。取り除き忘れると、非公開の問題が配信に載る。
  別のファイルなら、取り除く処理がなく、載らないことが構造で守られる。
- 名前を `questions.` で始めないのは、バンドラが、動的な `import` の対象を、名前の形(`questions.*.json`)で決めるため。`questions.<コード>.unpublished.json` のような名前は、この対象に入り、ビルドに取り込まれる。
- 履歴の数を、非公開の問題を含めて保つには、結果に、問題ごとの採点の情報(正解)を残す必要がある。正解は問題データにあり、非公開の問題の正解は、配信に載せない。結果の保存の形を変えずに、いまの扱い(いまのデータにない問題は数えない)にそろえる。

## 採用しなかった選択肢

- 問題ごとのフィールドで持つ: 上の理由のとおり、取り除き忘れの危険がある。スキーマの変更も大きい。
- `questions.<コード>.unpublished.json` の名前: バンドラの対象に入る。
- 画面で隠す(CSS や、出題の条件で除く): 配信に載るので、方針(配信しない)に反する。
- 削除 + 退役のまま、別の場所に写しを残す: 退役した ID は復帰しない決まりと、食い違う。写しと本体の同期も要る。
- 結果の数に、非公開の問題を含める: 結果の保存の形の変更(問題ごとの採点の記録)が要り、この版の範囲を超える。

## 影響

- 非公開へ移した問題の出典・題の補完(`export --titles` など)は、公開のファイルだけを対象にする。公開に戻すときに、題がない出典は、戻したあとに補う。
- 書き直しの段階(公開への復帰)は、別の版で作る。書き直した問題が、元の ID で公開に戻ることは、この決定の形(`question` を移す)で足りる。
- 新しい下書きの重複の検出は、公開の問題だけを比べる相手にする(ADR 0012)。非公開の問題と同じ論点の下書きは、重複として落ちない。必要なら、非公開の問題も比べる相手に足す。
