# 0003. 作成役と検査役のモデルを使い分ける

- 状態: 採用
- 日付: 2026-10-09

## 背景

commit・push・PR・Issue の前に、文面を書く作成役と、確かめる検査役を、別々のサブエージェントで動かしています。
どの役にも同じ高性能モデルを使うと、固定の形式の文章作りや、文書の確認でも費用がかさみます。
役ごとに必要な水準のモデルを割り当てると、費用を抑えられます。Haiku 5.5 と Sonnet 5.5 の検査の結果を比べて、割り当てを決めます。

## 決定

エージェントの定義を `.claude/agents/` に置き、役ごとにモデルを固定します。

| 役 | エージェント | モデル | 使う場面 |
| --- | --- | --- | --- |
| コミットメッセージの作成役 | `commit-writer` | Haiku 5.5 | commit |
| 検査役 | `inspector` | Haiku 5.5 | commit・push・PR・Issue の全般 |
| 検査役(深め) | `inspector-deep` | Sonnet 5.5 | 差分に `scripts/`、`.githooks/`、`.github/workflows/`、`.claude/` を含むとき、`inspector` と併せて使い、最も重い判定を採用する |
| PR・Issue の作成役 | `draft-writer` | Sonnet 5.5 | dev-pr |
| 開発本体 | メインのセッション | Sonnet 5.5 または Opus 5.5 | 実装・設計 |

- 検査役の道具は、Read / Grep / Glob だけにします(Bash は持たせません)。検査役が読む入力(差分・コミットのログ・ブランチ名・拒否リストの置き場)は、
  メインのセッションが `.drafts/inspect/` に書き出します(`scripts/prepare-inspection.ts`)。検査が終わったら消します。
- 作成役が書いてよいのは `.drafts/` の下だけです(`commit-writer` は `.drafts/commit-msg.txt` だけ)。
- モデルの選定は、新しい仕組みやワークフローを組むときに行います。都度の判断では変えません。

## 理由

検査役を Haiku 5.5 と Sonnet 5.5 で比べると(検査フックのコード、CI とリリース本文、問題のない README、漏えいを仕込んだ文書の 4 事例を各 1 回)、次の傾向があります。

- 見つける力は同等です。文書に仕込んだ 8 項目は、どちらも全部見つかります。問題のない README では、Haiku は指摘なし、Sonnet は軽微な注記 3 件です。
- コードを読む場合、取りこぼしが役ごとに別々です。1 つだけに頼ると穴が残るので、検査の仕組みを変える差分では 2 つを併せます。
- 速度は同程度で、コードを読む場合は Haiku のほうが遅くなることがあります。単価は Sonnet より大幅に低く、検査の費用を抑えられます。
- 固定の形式の文章(コミットメッセージ)は、間違いを検査役が止めるので、Haiku で足ります。

この比較は各事例 1 回で、ばらつきを含みます。

## 採用しなかった選択肢

- すべての役を Sonnet にする: 結果は同等でも、費用が大きいままです。
- すべての検査を Haiku だけにする: 検査の仕組みを変える差分で、取りこぼしが残ります。
- モデルの別名(`haiku` など)で指定する: 別名の指す先が変わると、検査の水準が気づかないうちに変わります。エージェントの定義では、完全な ID で固定します。

## 影響

- commit・push・PR の検査の費用が下がります。
- モデルの世代が変わるときは、新しい ADR で置き換え、比較をやり直します。
- 定義を変えたら、`inspector` と `inspector-deep` の両方で検査します。
- 検査役の読み取り専用は、道具の絞り込み(Bash を持たせない)で担保します。書き込みになるコマンドを、本文の指示で禁じる形はやめました。
  代わりに、検査役が必要とする情報は、メインのセッションが先に書き出します。書き出しにない情報は、検査役は読めません。
- 権限の設定(`.claude/settings.json`)で、次を決めます。
  - 禁止(deny): `--force` 系と `--no-verify` を付けた git の操作。
  - 確認必須(ask): `git push`(タグを含む)、`gh` の PR の作成・編集・マージ・クローズと、Issue の作成・編集・クローズ、`gh api`。コメントとラベルは対象にしません。
  - 禁止にした操作を、例外として行うときは、人が自分で実行します(理由を説明して承認を待つ)。
- 権限の設定の効き方は、次のとおりです。
  - deny は、メインのセッションからも、サブエージェントからも、権限で拒否されます。
  - 検査役(`inspector`、`inspector-deep`)の道具は、どちらも Read / Grep / Glob だけです。`.drafts/inspect/` のファイルを読み、拒否リストの語と照合できます。
  - ask は、権限の確認を省く動作モードでは、確認になりません。確認なしで実行されます。ask は「確認を求める設定」であって、強制ではありません。
    確実に止めたい操作は、deny にして人が実行するか、フックで止める必要があります。
  - スキルが求める承認(本文と検査の結果を見せて待つ)と、ask の確認は、別のものです。ask は機械的な最後の関門で、二重になるのを許容します。
- メインのセッションが Agent ツールの引数でモデルを指すときは、別名しか使えません。定義のあるエージェントを使うことで、完全な ID を固定します。
