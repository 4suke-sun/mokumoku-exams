# 0007. 作問を段階に分け、段階ごとに関門を置く

- 状態: 置き換え済み(置き換えた ADR: 0013)
- 日付: 2026-10-13

## 背景

問題は、出典の収集から公開データへの書き出しまで、多くの作業を経ます。1 つのモデルに一括で任せると、
誤りの原因をたどれず、費用も読めません。

## 決定

- 作業を次の段階に分けます。収集、事実カード、出題計画、下書き、検証、解説・出典、書き出し。
- 段階ごとに、入力と出力の形(スキーマ)と、**関門**(次へ進める条件)を定めます。関門を通らないものは、先へ進めません。
- 安い機械検査(スキーマ、重複、出典の有無、長さ)を先に、高いモデルによる検証をあとに置きます。
- **作る役と検証する役を分けます**。同じエージェントに、書かせて確かめさせません。
- 各段階の成果物は、作業用の置き場(gitignore 済み)にファイルで残し、段階の間はファイルで受け渡します。
- 公開するデータに入るのは、書き出しの段階を通ったものだけです。

## 理由

- 段階ごとに確かめれば、誤りを早く見つけ、直す範囲が小さくなります。
- 機械検査で先に落とすと、高いモデルを呼ぶ回数が減り、費用を抑えられます。
- 作る役と確かめる役を分けると、同じ思い込みを通してしまうことを防げます。

## 採用しなかった選択肢

- 一括で生成して、最後に人が確かめる: 誤りの発見が遅く、人の負担が大きくなります。
- すべての段階を同じモデルで行う: 費用が大きくなり、検証の独立性もありません(ADR 0003 の使い分けに従います)。

## 影響

- 関門の基準は、段階ごとの Issue で決め、検査の失敗は理由コードで報告します(本文は引用しません)。
- 段階を足すときは、入力・出力・関門を定義してから実装します。
