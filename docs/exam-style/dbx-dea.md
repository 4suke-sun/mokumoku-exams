# Databricks Certified Data Engineer Associate(DBX-DEA-2605)の書き方

[Databricks の資格に共通の書き方](./dbx-common.md)に加わる、この資格の値と言い回しです。採点は [点数票](./scorecard.md) です。

## 1. 要点

**状況の問が約 6 割、1 文か 2 文の知識の問が約 4 割です。** すべて択一です。選択肢は、方式や説明の文が約 3 分の 1、製品名・機能名が約 4 分の 1、コードが約 4 分の 1、短い語句が約 1 割です。コードを含む問は、全体の約 3 分の 1 です。

| 項目 | 目安 |
| --- | --- |
| 設問文の文字数(複数選択の表記を除く) | 30〜320(満点)、20〜420(部分点) |
| 状況の文(問いより前の文)の数 | 0〜5(知識の問は 0) |
| 設問文の段落 | 状況の問は、状況の段落と問いの段落を分ける(機械では見ない) |
| 状況つきの設問の割合(束) | 50% 以上 75% 以下(状況の文が 1 文以上あるもの) |
| 最長の選択肢の文字数 | 100 以内(満点)、150 以内(部分点) |
| 選択肢の最長÷最短 | 3.5 倍以内(満点)、5 倍以内(部分点) |
| 選択肢どうしの類似度(バイグラムの Dice) | 0.9 未満 |
| 複数選択の割合(束) | 0% 以下(すべて択一。複数選択は置かない) |
| 設問文の中央値(束) | 120〜180 字。90 パーセンタイルは 340 字以下 |
| 選択肢の形(束) | 文・名前・コード・語句の混在。文 50% 以下 |
| 設問文の先頭 8 文字が同じものの割合(束) | 40% 以下 |

目安の値は、次の出題の傾向から決めています。

| 項目 | 傾向 |
| --- | --- |
| 設問文の長さ | 中央値は約 150 字(状況の問は約 180 字、知識の問は約 60 字)。90 パーセンタイルは約 310 字 |
| 最長の選択肢 | 中央値は約 40 字。90 パーセンタイルは約 110 字。最長÷最短の中央値は約 1.6 倍 |
| 状況の要件 | 状況の問の半数は、要件を並べず、現状と課題から「何をすべきか」を問う。要件を書く問も、要件は 1 つが主で、3 つ以上はまれ |
| 書き出し | 「データエンジニア」が約 4 割、主体なし(知識の問)が約 3 分の 1、「チーム」が約 1 割半 |
| 解説 | 中央値は約 240 字 |

## 2. 設問の構成

```text
[状況の問]  状況の段落(主体・現状 → 課題。要件は 0〜2 つ。1〜5 文)+ 問いの段落(1 文)
[知識の問]  機能や仕様を直接問う 1〜2 文(30〜120 字)
[コードの問]  状況か問いの文+設問文の中のコード(コードのブロック)+ 問いの段落
```

- 状況の問は、役割の語(「データエンジニア」「ジュニアデータエンジニア」「データエンジニアリングチーム」)から書き出すのが主です。企業から書き出してもよい。
- 状況は、現状の構成(使っている機能・表・パイプライン)と、起きていること(遅い、失敗する、新しい列が届く、別のチームに読ませたい)を書き、問いで「何をすべきか」「どれを使うべきか」を問います。要件の文を並べなくてよい。要件を書くときは、答えを分けるものを 1〜2 つにします。
- 知識の問は、製品名や機能名を主語にして、「〜の説明として正しいものはどれですか」「〜するコマンドはどれですか」「〜に使う機能はどれですか」の形で問います。
- 設問の型の配分の目安は次のとおりです(45 問の束で、どれかに偏らないようにする)。

| 設問の型 | 目安 | 中身 |
| --- | --- | --- |
| 事実を選ぶ | 約 25% | 機能の説明・利点・動作として正しいものを選ぶ |
| 方式を選ぶ | 約 20% | 状況に合う方式・構成・コンピュート・取り込みの方法を選ぶ |
| 正しいコードを選ぶ | 約 15〜20% | 要件を満たす SQL 文・式・PySpark の呼び出し・CLI のコマンドを選ぶ |
| 名前を選ぶ | 約 15% | 機能・コマンド・オプション・権限の名前を選ぶ |
| 穴埋め | 約 10% | 設問文のコードの 1 か所の空欄に入るものを選ぶ |
| 原因と対処 | 約 5〜10% | 遅い・失敗する・結果が違う原因か、その対処を選ぶ |
| 結果の予想 | 約 5% | コードや操作の結果(値、エラー、動作、メダリオンのどの層の処理か)を選ぶ |
| 否定の問 | 5% 以下 | 誤っているもの・できないものを選ぶ。否定の語は 1 つにし、太字で強調する |

- コード(SQL・PySpark・CLI のコマンド・設定ファイル)を含む問は、変換とモデリングの分野でおよそ 3 分の 2、取り込み(Auto Loader やストリーミングの読み書き)、CI/CD(CLI のコマンドとバンドルの構成)、ガバナンス(GRANT・REVOKE や行フィルター・列マスクの定義)の分野でそれぞれ約 4 割です。プラットフォーム、Lakeflow Jobs、障害対応・監視・最適化の分野では、コードの問はほぼ置きません。コードの置き場所は次のとおりです。
  - **正しいコードを選ぶ**: 要件を示し、要件を満たす 1 行の SQL 文・式・コマンドを選ばせる。選択肢は文中のコードで書く。
  - **穴埋め**: 設問文のコードのブロック(数行)の 1 か所を空欄にし、入る関数・オプション名・句を選ばせる。
  - **結果の予想**: 設問文のコードのブロックや式を示し、結果を選ばせる。
  - **複数行のコードを比べる**: 候補を「コード 1」〜「コード 4」として設問文にコードのブロックで並べ、選択肢は「コード 1」のように候補を指す(変換の分野で、PySpark や宣言型パイプラインの定義を比べるときに使う)。

## 3. 選択肢

| 項目 | 決まり |
| --- | --- |
| 数 | 単一 4。複数選択は使わない |
| 長さ | 最長÷最短は 3.5 倍以内。文で書く問は、1〜2 文(100 字以内)。名前の選択肢は 20 字前後 |
| 形 | 1 問の中で形をそろえる(文なら文、名前なら名前、コードならコード) |
| 並行 | 方式やコードを選ぶ設問は、選択肢どうしが書き出しや構成を共有する |
| コード | 選択肢のコードは、文中のコード(`` `…` `` で囲んだ 1 行の SQL 文・式・コマンド)で書く。コードのブロックは置かない。複数行のコードは設問文に置く(「2. 設問の構成」) |
| 正答の手がかり | 正答だけを最長にしない。状況の語を、そのまま正答の語に使わない(状況の語と正答の語の一致で答えが分かる形にしない) |

## 4. 作問の指示に落とすとき

1. 設問は、状況の問を約 6 割、知識の問を約 4 割にする。状況の問は **状況の段落+問いの段落**(空行で分ける)。
2. 設問の型は、「2. 設問の構成」の配分の目安に沿って混ぜる。知識の問(事実・名前を選ぶ)を、状況の問に無理に書き換えない。
3. 選択肢は、1 問の中で形をそろえる。最長の選択肢は 100 字以内にする。コードの問は、「2. 設問の構成」の置き場所のどれかで書き、選択肢のコードは 1 行の文中のコードにする。
4. 誤答は、「5. 誤答の作り方」の型から作り、1 問の中で 2 つ以上の型を混ぜる。どれも、状況でもっともらしく、事実カードの主張で誤りを示せるものにする。
5. 状況の要件・制約は、事実カードで根拠を示せるものだけにする。長くするために、根拠のない要件を足さない。ただし、状況を成り立たせる架空の数値(件数、ファイル数、頻度、時刻、実行時間、レイテンシの目標など、シナリオの設定)は、事実の主張ではないので、事実カードで根拠を示さなくてよい(扱いは [dbx-common.md](./dbx-common.md) の「状況の数値」)。製品の既定値・上限・保持期間・料金を数値で述べるときは、設定にせず、事実カードで根拠を示す。
6. 難易度との対応は拘束しない。この資格は全体が Associate の難しさで、知識の問も `easy` に限らない。
7. 問いは「です・ます」で書く。
8. 作る問題の分野の配分は、公式の配点(資格マスタ `data/exams.json` の `domains` の `weight`)に合わせる。分野の中の論点は、「6. 範囲の注意」の論点の重みに沿って選ぶ。

## 5. 誤答の作り方

出題の傾向で、誤答に使われる型の割合は次のとおりです。下書きの誤答の `type`([作問のスタイルガイド](../question-style.md)の誤答の型)との対応を、右の列に置きます。

| 誤答の型 | 割合 | 中身 | `type` |
| --- | --- | --- | --- |
| 同じ層の別の機能・モード | 約 25% | 正答と同じ分類(同じ用途のコンピュート、取り込み方式、スキーマ進化のモード、トリガーの種類、ビューとテーブルの種類、結合の種類、メダリオンの層、権限の種類)から選ぶ。状況の 1 つの事実だけが、正答とそれを分ける | `similar-service` |
| 機能の誤った説明 | 約 20% | 機能の効果や仕組みを、別の機能のものにすり替えた説明。存在しない動作を述べる説明 | `misconception` |
| 条件の反転・境界のずれ | 約 10% | 以上と超、すべてといずれか、古いと新しい、追加と上書き、ソースとターゲットの逆 | `condition-reversal` |
| 存在しない名前 | 約 10% | 実在の名前に似せた、存在しないコマンド・関数・オプション・権限の名前 | `misconception` |
| 構文の誤り | 約 10% | コードの語順、キーワード、引数の形、オプション名の接頭辞の違い。1 点の違いが主で、2 点の違いも半分近くある | `misconception` |
| 一部だけ満たす | 約 8% | 要件の 1 つを落とす(増分ではあるが重複を防げない、出力に余計な列が残る) | `scope-difference` |
| 手作業・過剰な構成 | 約 3% | 手で実行する、全体を作り直す、別のジョブに分ける。運用の負荷が要件のときだけ使う | `misconception` |
| 権限の過不足 | 約 3% | 親のカタログ・スキーマの USE の欠け、必要以上の権限、付与の効果の言い過ぎ | `scope-difference` |
| 絶対の否定・数値・古い手段 | 合わせて約 3% | 「方法はない」、既定の日数・間隔・上限の違い、古い・非推奨の手段 | `numeric-difference` ほか |

- 1 問の 3 つの誤答は、2 つ以上の型を混ぜる。方式を選ぶ設問は「同じ層の別の機能・モード」が中心になってよいが、3 つすべてをこの型にしない。
- 2 つの軸の組み合わせ(モード × 環境のような 2 × 2)は、4 つの選択肢がそれぞれずれる並行の形として使ってよい。
- 存在しない名前の誤答は、正答の集合が事実カードで閉じているとき(コマンド・オプション・権限の一覧が出典にあるとき)に使う。
- 構文の誤りの誤答は、誤答どうしで、違う点を重ねない。2 点を違えるときも、どちらの点も、解説で示せるものにする。
- 名称が変わった機能の旧称(例: Lakeflow 宣言型パイプラインの旧称、Lakeflow Jobs の旧称、バンドルの旧称)を、誤答の材料にしない。旧称と新称は同じものを指すので、正答が 2 つになる。
- 「方法はない」「不可能」「設定できない」のような絶対の否定を、誤答に多用しない。それだけで誤りと見抜かれやすい。
- 状況と無関係な効果(暗号化する、ネットワークを速くする、可視化の道具である)を並べた、一目で誤りと分かる誤答は置かない。
- 同じ論点の変種(空欄の答えや条件だけを入れ替えたもの)を、続けて作らない。

## 6. 範囲の注意

- 分野は 7 つで、配点は次のとおりです。プラットフォーム 6%、取り込み 21%、変換とモデリング 22%、Lakeflow Jobs 16%、CI/CD 10%、障害対応・監視・最適化 10%、ガバナンス 15%(合計 100%)。値の正は、資格マスタ(`data/exams.json`)の `domains` の `weight` です。
- 設問は、機能の選び分け(コンピュートの種類、取り込み方式、デプロイ方法、トリガーの種類)と、機能の説明、操作や設定の意味、コードの書き方を問います。
- 分野ごとの論点の重みの目安(出題の傾向の多い順。内容の根拠は、これまでどおり出典と事実カードだけです)。
  - プラットフォーム: コンピュートの種類と選び分け(サーバーレス・ジョブ用・汎用・SQL ウェアハウス)、Delta Lake の基本(トランザクションログ、ACID)、クラスターの設定、コントロールプレーンとコンピュートプレーン。事実を選ぶ問が多い。
  - 取り込み: Auto Loader(スキーマの推論と進化、オプション、ファイルの検出方式)が最も多い。次に Structured Streaming(トリガー、チェックポイント)、Lakeflow Connect、スキーマの進化、COPY INTO。穴埋めと方式を選ぶ問が多い。
  - 変換とモデリング: 宣言型パイプライン(期待値、ストリーミングテーブルとマテリアライズドビュー、CDC の適用)、SQL の関数(高階関数、半構造データ、日時)、PySpark の API(結合、集計、重複の排除、ウィンドウ)、メダリオンの層の役割、SQL の DDL・DML。正しいコードを選ぶ問と穴埋めが多い。
  - Lakeflow Jobs: トリガーの種類(定時、ファイル到着、テーブルの更新、連続)、タスクの種類と依存、実行の監視と修復実行、再試行、条件による分岐とループ。方式を選ぶ問が多い。
  - CI/CD: バンドル(構成ファイル、変数とターゲットの上書き、validate・deploy・run)、Git フォルダーの操作、Databricks CLI。コマンドを選ぶ問がある。
  - 障害対応・監視・最適化: 偏り・シャッフル・ディスクへの退避と Spark UI での見分け、Liquid Clustering、OPTIMIZE と予測最適化、クラスターの設定、ノートブックの機能。原因と対処を選ぶ問と名前を選ぶ問が多い。
  - ガバナンス: Unity Catalog の権限(GRANT・REVOKE、USE CATALOG・USE SCHEMA と最小権限)、マネージドと外部テーブル、Delta Sharing、リネージと監査、行フィルター・列マスク、オブジェクトの階層。権限のコードを選ぶ問がある。
- 試験ガイドの出題範囲の要旨に名前がない論点(ノートブックのデバッガーと変数の一覧、Databricks Connect、Lakehouse Federation、インスタンスの種別の細部、クラウド事業者の転送料金)は、試験ガイドの全文で範囲を確かめるまで、主題や正答にしない。

## 7. 判定の基準

公開している問題を、**公開 / 非公開 / 書き直しで復帰できる**のどれにするかを決める基準です。判定と理由コードの共通の決まりは、[README](./README.md) の「判定の基準」にあります。基準は二層で、機械の観点は点数票が測り、LLM の観点は判定役(`question-judge`)が、次の文章に照らして判断します。

### 機械の観点

点数票の項目(A1〜A10、B1〜B7、S1〜S5)と、「1. 要点」の表の帯のとおりです。値は表にだけ置き、ここには重ねて書きません(食い違いを防ぐため)。合格点は、問題 1 問が 80 点、束が 70 点で、変えません。問題 1 問ごとの項目(A と B)で不合格になる問題(合格点に届かない、または止める項目に違反する問題)は、判定の依頼に「候補」として載ります(判定役は全件を判定します。束の項目 S は、候補には使いません)。

### LLM の観点

| ID | 観点 | この資格で見ること | 外れの例 |
| --- | --- | --- | --- |
| J1 | 設問の型 | 状況の問(状況の段落+問いの段落)か、機能や仕様を直接問う 1〜2 文の知識の問である。単一選択で、選択肢が 4 つ。コードの問は、正しいコードを選ぶ・穴埋め・結果の予想・複数行のコードを比べるのどれかで、複数行のコードは設問文の中にコードのブロックで置き、選択肢のコードは 1 行の文中のコードである(複数行のコードを比べる問は、候補を設問文に番号付きで並べ、選択肢は番号で指す)。否定の問は、否定の語が 1 つで、太字で強調されている | 否定の語を強調していない否定の問、二重否定。複数選択になっている。選択肢にコードのブロックや複数行のコードがある。図や画像がないと答えが決まらない |
| J2 | 状況の自然さ | 「データエンジニア(チーム、企業)」の現状(使っている機能・表・パイプライン)と、起きていること(遅い、失敗する、新しい列が届く、別のチームに読ませたい)が書かれ、状況の 1 つの事実が答えを分けている。要件の文は 0〜2 つでよい。状況を成り立たせる架空の数値(件数、頻度、時刻、レイテンシの目標など、シナリオの設定)は、自然に使ってよい | 状況が長いだけで、答えを分ける事実がない。製品の既定値・上限・保持期間を、設定なのか事実の主張なのか読み取れない形で、答えを分ける要件にしている(事実の主張の数値が出典と合うかは、検証役が見る) |
| J3 | 選択肢の質 | 誤答が、「5. 誤答の作り方」の型(同じ層の別の機能・モード、機能の誤った説明、条件の反転、存在しない名前、構文の誤り、一部だけ満たす、手作業・過剰な構成、権限の過不足など)で、紛らわしく作られている。正答だけが際立って長い形や、状況の語がそのまま正答に出る形でない | 状況と無関係な効果を並べた、一目で誤りと分かる誤答。旧称の同じ機能が誤答になっている。絶対の否定(「方法はない」など)の誤答に頼り、それだけで誤りと分かる。存在しない名前を、正答の集合が閉じていないのに誤答にしている。正答だけが際立って長い、または状況の語と正答の語の一致だけで答えが分かる |
| J4 | 解説の整合 | 総合解説と選択肢ごとの解説が、設問と正解に食い違わず、各誤答がずれている点(コードの問は、正答と違う構文の 1 点)を述べている(出典との照合は検証役の仕事) | 解説が別の選択肢を正解として述べている。誤答のずれが述べられていない |
