# AWS Certified CloudOps Engineer - Associate(AWS-SOA-C03)の書き方

[AWS の資格に共通の書き方](./aws-common.md)に加わる、この資格の値と言い回しです。採点は [点数票](./scorecard.md) です。

## 1. 要点

**設問は長く、選択肢は「操作や設定のやり方を述べる文」で、選択肢どうしが並行します。** 形は Developer - Associate に近く、違いは中身です。新しい構成の設計やアプリのコードではなく、**動いている環境への運用の処置**(観測・通知・修復、設定の反映、統制、原因の特定)を問います。

| 項目 | 目安 |
| --- | --- |
| 設問文の文字数(複数選択の表記を除く) | 150〜360(満点)、110〜450(部分点) |
| 状況の文(問いより前の文)の数 | 2〜6 |
| 設問文の段落 | 状況の段落と、問いの段落を分ける。問いの段落は 100 字以内 |
| 状況つきの設問の割合(束) | 90% 以上(状況の文が 2 文以上あるもの) |
| 最長の選択肢の文字数 | 150 以内(満点)、220 以内(部分点) |
| 選択肢の最長÷最短 | 3 倍以内(満点)、4.5 倍以内(部分点) |
| 選択肢どうしの類似度(バイグラムの Dice) | 0.97 未満 |
| 複数選択の割合(束) | 60% 以下(複数選択がない束も通す) |
| 設問文の中央値(束) | 180〜290 字。90 パーセンタイルは 370 字以下 |
| 選択肢の形(束) | 文が 80% 以上 |
| 設問文の先頭 8 文字が同じものの割合(束) | 45% 以下 |

## 2. 設問の構成

```text
[状況の段落]  主体 → 稼働中の構成 → 起きていること・追加の要件 → 判断を分ける条件(2〜6 文)
[問いの段落]  この要件を満たす〜はどれでしょうか。/(2 つ選択)(1 文)
```

- 主体は「ある企業は」「ある企業では」が主です。業種を添えてよい(答えには効かせない)。状況の中に、運用を担う「CloudOps エンジニア」を登場させ、その人が対処する形にします。「あなたは」も使えます。
- 状況は、**稼働中の構成**(ロードバランサーと Auto Scaling と EC2、S3 と CloudFront、EC2 と RDS、Organizations の複数アカウントなど)から始めます。サービス名は 1〜数個にとどめます。
- 続きは、次のどれかにします。
  - **症状**: 遅い、つながらない、エラーや状態の名前が出る、データを取りこぼす。原因の層か、直し方を問う。
  - **運用の要件**: 〜したら通知する、準拠していないものを自動で直す、全リージョンや全アカウントを見る。仕組み(検知 → 通知 → 修復のつなぎ方)を問う。
  - **統制の要件**: 〜させない、〜だけに許す、設定をそろえる・配る。ポリシーと付け先を問う。
  - **設定の確認**: 値の組み合わせ(TTL、CIDR、ルールの番号、ポリシー)を示し、結果を問う。まれに使う。示す断片は短くする。
- 判断を分ける条件(「将来追加するリージョンも対象にする」「接続先は変えない」「すでに〜は設定済み」など)を、状況に 1〜2 個置きます。この条件で正答が 1 つに決まるようにします。
- 判断の軸(運用の手間を最小に、自動で、最も安全に、コストを最小に)は、付ける設問と付けない設問を混ぜます。軸を付けない設問は、機能の事実(できる・できない、あとから変えられない、既定の動き)で決まるようにします。
- 数値(台数・容量・期間・しきい値)は、答えを分けるときだけです。
- 否定の設問は使いません。
- 問いの末尾は、「〜はどれでしょうか」「〜はどれですか」「〜は何でしょうか」が主です。複数選択は「(2 つ選択)」が主で、「(3 つ選択)」はまれです。

## 3. 選択肢

| 項目 | 決まり |
| --- | --- |
| 数 | 単一 4、複数 5(2 つが正答)。3 つが正答のときは 5〜6 |
| 形 | **文**。「〜する。」で終える(句点あり)。1 問の中でそろえる |
| 内容 | **操作や設定のやり方**(「A で B を設定し、C に通知する」)。「〜して、〜する」の連なりや、2 文の選択肢を使ってよい |
| 並行 | 選択肢どうしは書き出しと構成を共有し、**1 つの要素だけ**違う。替える要素は、サービス・機能の名前、設定の項目、向き、付け先、置き場所。2 つの要素を 2 値ずつ組み合わせて 4 つにする作りを使ってよい |
| 長さ | 最長÷最短は 3 倍以内。そろえる |
| 偏り | 正答の位置と長さに偏りを作らない |

- 誤答は、**実在する機能だけ**で作ります。存在しない機能名・設定名・オプションを、誤答に使いません。
- 誤答の作り方は、次を主にします。
  - よくある誤解: そのサービスにない能力を持たせる(記録だけのサービスで通知や修復をする、など)。古い手段を使う。
  - 似たサービス: 同じ系統の兄弟の機能(Systems Manager の各機能、CloudWatch の各機能など)に入れ替える。
  - 範囲の違い: 付け先や範囲をずらす(アカウントごと・リージョンごとの個別の設定、対象外のリソースに効く機能)。
  - 条件の逆: 向き(インバウンドとアウトバウンド、許可を出す側と受ける側)や、有効と無効を逆にする。
- 運用の手間を問う設問では、直接つなげるところに Lambda などの中継や自作の処理を足した案を、誤答として置けます。
- 複数選択は、**役割の分担**(検知とアクション、評価と修復、許可を出す側と受ける側、ログの取得と検索)で、別の層から 1 つずつ選ぶ形を主にします。同じ目的の別解を 2 つ選ばせる形は、正答が 1 つに決まりにくいので避けます。

## 4. 作問の指示に落とすとき

1. 設問文は **状況の段落+問いの段落**(空行で分ける)。状況 2〜6 文、150〜360 字。
2. 状況は、企業の稼働中の構成から始め、CloudOps エンジニアが対処する形にする。症状・運用の要件・統制の要件のどれかに進める。
3. 判断を分ける条件は、事実カードで根拠を示せるものだけにする。長くするために、根拠のない要件を足さない。
4. 選択肢は文にして句点で終える。最長の選択肢は 150 字以内にする。
5. 誤答は、正答の部品を 1 つ入れ替えて作る(兄弟の機能、別の付け先、逆の向き)。事実カードの主張で誤りを示せるものにする。実在しない名前は使わない。
6. 難易度との対応は拘束しない。この資格は全体が Associate の難しさなので、`easy` も状況つきで書くのが自然。
7. 問いは「です・ます」で書く。選択肢の「〜する。」は常体のままにする。

## 5. 範囲の注意

- 設問は、サービスの選択よりも、**運用の処置**(設定のやり方、手順の前後と前提、つなぎ方、付け先)を問います。手順の前提(停止が要るか、作り直しが要るか、リージョンごとに要るか)は、よい論点です。
- 分野 4 は、複数アカウントの統制(Organizations と SCP、委任管理者、IAM Identity Center、組織の証跡、Config のルールとコンフォーマンスパック)を中心にします。
- 試験ガイドの対象外のタスク(分散アーキテクチャ・CI/CD パイプライン・ネットワークの設計、ソフトウェアの開発、要件の定義、キャパシティの計画、コストと総保有コストの分析、課金と請求の管理)は問いません。コストは、推奨を出すサービスによる適正化の範囲にとどめます。
- 試験ガイドの改訂で足された対象(新しいサービスやスキル)も、試験ガイドの出題範囲の項目に沿って扱います。
- 置き換えられた機能(起動設定、CloudFront の旧形式のキャッシュの設定など)を、正答の前提にしません。
- 解説は長めにし、正答の理由と手順の要点、選択肢ごとの誤りの理由を書きます。

## 6. 判定の基準

公開している問題を、**公開 / 非公開 / 書き直しで復帰できる**のどれにするかを決める基準です。判定と理由コードの共通の決まりは、[README](./README.md) の「判定の基準」にあります。基準は二層で、機械の観点は点数票が測り、LLM の観点は判定役(`question-judge`)が、次の文章に照らして判断します。

### 機械の観点

点数票の項目(A1〜A10、B1〜B7、S1〜S5)と、「1. 要点」の表の帯のとおりです。値は表にだけ置き、ここには重ねて書きません(食い違いを防ぐため)。合格点は、問題 1 問が 80 点、束が 70 点で、変えません。問題 1 問ごとの項目(A と B)で不合格になる問題(合格点に届かない、または止める項目に違反する問題)は、判定の依頼に「候補」として載ります(判定役は全件を判定します。束の項目 S は、候補には使いません)。

### LLM の観点

| ID | 観点 | この資格で見ること | 外れの例 |
| --- | --- | --- | --- |
| J1 | 設問の型 | 状況の段落(稼働中の構成から始まる)と問いの段落に分かれ、選択肢が「操作や設定のやり方を述べる文」である | 状況のない用語の問い。選択肢がサービス名だけ |
| J2 | 状況の自然さ | 稼働中の構成から、症状・運用の要件・統制の要件へ進み、判断を分ける条件が答えを分けている | 新しい構成の設計だけを問う。サービス名の羅列で状況が成り立たない。根拠のない要件を足している |
| J3 | 選択肢の質 | 選択肢が書き出しと構成を共有し、1 つの要素(機能・設定の項目・向き・付け先)だけ違う。誤答は実在する機能の入れ替えで作られている | 選択肢の構成がばらばら。実在しない機能名を使う。誤答が状況と無関係で、一目で誤りと分かる |
| J4 | 解説の整合 | 総合解説と選択肢ごとの解説が、設問と正解に食い違わず、誤答の理由が、その選択肢が誤りである理由になっている(出典との照合は検証役の仕事) | 解説が別の選択肢を正解として述べている。誤答の理由が設問に合わない |
| J5 | 一意性と範囲 | 正答(複数選択は個数も)が 1 つに決まり、運用の処置(監視・修復・設定・統制・トラブルシューティング)の範囲に収まり、試験ガイドの対象外のタスクを問わない | 条件が足りず、複数の選択肢が正しくなりうる。同じ目的の別解を選ばせる。請求の管理やアーキテクチャの設計を問う。置き換えられた機能を正答にする |
