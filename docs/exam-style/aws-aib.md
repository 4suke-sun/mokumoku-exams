# AWS Certified AI Business Strategist(AWS-AIB-C01)の書き方

[AWS の資格に共通の書き方](./aws-common.md)に加わる、この資格の値と言い回しです。採点は [点数票](./scorecard.md) です。

## 1. 要点

**設問は中くらいの長さで、技術の細部よりも、導入・ガバナンス・責任ある AI・データの質・コスト・組織の進め方といった意思決定を問います。** 単一選択だけで、選択肢は短い文が並行し、長さがそろいます。Cloud Practitioner と Developer - Associate の値は流用できません。

| 項目 | 目安 |
| --- | --- |
| 設問文の文字数(複数選択の表記を除く) | 120〜300(満点)、90〜360(部分点) |
| 状況の文(問いより前の文)の数 | 2〜6 |
| 設問文の段落 | 状況の段落と、問いの段落を分ける。問いの段落は 100 字以内 |
| 状況つきの設問の割合(束) | 90% 以上(状況の文が 2 文以上あるもの) |
| 最長の選択肢の文字数 | 100 以内(満点)、140 以内(部分点) |
| 選択肢の最長÷最短 | 2.5 倍以内(満点)、3.5 倍以内(部分点) |
| 選択肢どうしの類似度(バイグラムの Dice) | 0.85 未満 |
| 複数選択の割合(束) | 0% 以下(複数選択は置かない) |
| 設問文の中央値(束) | 160〜240 字。90 パーセンタイルは 300 字以下 |
| 選択肢の形(束) | 文が 80% 以上 |
| 設問文の先頭 8 文字が同じものの割合(束) | 45% 以下 |

## 2. 設問の構成

```text
[状況の段落]  主体・現状 → 課題や数値 → 目標・要件(2〜6 文)
[問いの段落]  これらの要件を満たすのはどれですか。/最も適切なのはどれですか。(1 文)
```

- 主体は「ある〜企業(会社・銀行・組織・団体・機関・法人・メーカーなど)は」が主です。「ある企業は」でもよい。業種や規模の語を挟んでよい。ほかに「あなたは」。社名の形(「A 社は」)や、開発者を主役にした形は使いません。
- 状況は、**現状の取り組み**(導入した AI、チームの体制、データの状態)から始め、課題や数値に進み、「同社は〜したいと考えています」「〜する必要があります」で要件を示します。
- 問いは「これらの要件を満たすのはどれですか」「最も適切な対応はどれですか」「最初に実施すべきステップはどれですか」「最も可能性が高い原因は何ですか」が主です。
- 否定の設問は使いません。
- 問いの末尾は、すべて「です・ます」(「〜ですか」「〜どれですか」)です。

## 3. 選択肢

| 項目 | 決まり |
| --- | --- |
| 数 | 4(単一選択だけ) |
| 形 | **短い文**。「〜する。」で終える(句点あり)。1 問の中でそろえる。複数の短文を並べた選択肢も使ってよい |
| 内容 | 取り組み・対応・方針を述べる文。技術の設定値よりも、順序・範囲・タイミング・責任の所在といった意思決定の違い |
| 並行 | 選択肢どうしは、形がそろう。誤答は、正答と同じ種類の取り組みで **1 点**(順序・範囲・タイミング・責任の所在)だけ違うか、状況の別の関心事に答える取り組み(取り違え)になっている |
| 長さ | 最長÷最短は 2.5 倍以内。そろえる |
| 偏り | 正答の位置と長さに偏りを作らない |

## 4. 作問の指示に落とすとき

1. 設問文は **状況の段落+問いの段落**(空行で分ける)。状況 2〜6 文、120〜300 字。
2. 選択肢は短い文にして句点で終える。最長の選択肢は 100 字以内にする。単一選択だけで書く。
3. 誤答は、次のどちらかの作り方で作る。(a) 正答と同じ種類の取り組みで、順序・範囲・タイミング・責任の所在のどれか 1 点をずらす(下書きの誤答の `type` は、`scope-difference`・`condition-reversal`・`numeric-difference`・`similar-service` のうち合うもの)。(b) 状況の別の関心事への取り違え(課題と違う関心事に答える取り組み)にする(`type` は `misconception`)。どちらも、状況でもっともらしく、事実カードの主張で誤りを示せるものにする。共通の決まり([aws-common.md](./aws-common.md))の「誤答は正答と同じ分類のものから選ぶ」は、この資格では (b) を足す(別の関心事への取り違えは、分類の違う誤答として許す)。
4. 状況の要件・制約は、事実カードで根拠を示せるものだけにする。長くするために、根拠のない要件を足さない。ただし、状況を成り立たせる架空の数値(精度、割合、差異など、シナリオの設定)は、事実の主張ではないので、事実カードで根拠を示さなくてよい。設定の数値が答えを分ける要件になるときは、設問文の中で設定の値だと分かる書き方にする。サービスの仕様・上限・料金・規制の内容を数値で述べるときは、設定にせず、事実カードで根拠を示す。
5. 難易度との対応は拘束しない。意思決定を問う設問が中心なので、`easy` も状況つきで書くのが自然。
6. 問いは「です・ます」で書く。選択肢の「〜する。」は常体のままにする。

## 5. 範囲の注意

- 設問は、サービスの設定や API よりも、**AI を導入・運用・統治する側の判断**を問います。
- 解説は、正答の理由と、各誤答がずれている点を述べます。

## 6. 判定の基準

公開している問題を、**公開 / 非公開 / 書き直しで復帰できる**のどれにするかを決める基準です。判定と理由コードの共通の決まりは、[README](./README.md) の「判定の基準」にあります。基準は二層で、機械の観点は点数票が測り、LLM の観点は判定役(`question-judge`)が、次の文章に照らして判断します。

### 機械の観点

点数票の項目(A1〜A10、B1〜B7、S1〜S5)と、「1. 要点」の表の帯のとおりです。値は表にだけ置き、ここには重ねて書きません(食い違いを防ぐため)。合格点は、問題 1 問が 80 点、束が 70 点で、変えません。問題 1 問ごとの項目(A と B)で不合格になる問題(合格点に届かない、または止める項目に違反する問題)は、判定の依頼に「候補」として載ります(判定役は全件を判定します。束の項目 S は、候補には使いません)。

### LLM の観点

| ID | 観点 | この資格で見ること | 外れの例 |
| --- | --- | --- | --- |
| J1 | 設問の型 | 状況の段落(現状の取り組み、課題と数値、要件)と問いの段落に分かれ、単一選択で、選択肢が短い文である | 状況のない用語の問い。複数選択になっている。設定値の細部を問う |
| J2 | 状況の自然さ | 「ある〜企業」の現状の取り組みから、課題、要件へ進み、要件が答えを分けている。状況を成り立たせる架空の数値(精度、割合、差異など、シナリオの設定)は、自然に使ってよい | 状況が長いだけで、答えを分ける要件がない。数値が、設定なのか事実の主張なのか読み取れず、答えを分ける要件になっている(事実の主張の数値が出典と合うかは、検証役が見る) |
| J3 | 選択肢の質 | 誤答が、次のどちらかの作り方で、紛らわしく作られている。(1) 正答と同じ種類の取り組みで、順序・範囲・タイミング・責任の所在のどれか 1 点だけずれている。(2) 状況の別の関心事(例: 課題はデータの質なのに、モデルの性能を上げる取り組み)への取り違えで、その状況でもっともらしい | 誤答が、状況とも正答とも無関係で、一目で誤りと分かる。(1) のつもりで 1 点ではなく複数の点がずれている。誤答が正答と同じくらい正しくなりうる(これは J5 の一意性でも見る) |
| J4 | 解説の整合 | 総合解説と選択肢ごとの解説が、設問と正解に食い違わず、各誤答がずれている点を述べている(出典との照合は検証役の仕事) | 解説が別の選択肢を正解として述べている。誤答のずれが述べられていない |
| J5 | 一意性と範囲 | 正答が 1 つに決まり、AI を導入・運用・統治する側の判断の範囲に収まる。基準の末尾に試験ガイドの範囲の一覧があるときは、対象外のサービスが設問の主題や正答になっていない | 条件が足りず、複数の選択肢が正しくなりうる。サービスの設定や API を問う。対象外のサービスを主題や正答にする |
