# Databricks の資格に共通の書き方

Databricks の資格の問題に共通する、文章の構成の特徴です。資格ごとの値は、[Data Engineer Associate](./dbx-dea.md) にあります。
採点は [点数票](./scorecard.md) です。

## 1. 設問の構成

設問は、次の 2 つの部品でできています。

1. **状況**(任意): 誰が(ある企業・データエンジニア・チーム)、何をしようとしているか、どんな要件があるかを書きます。
2. **問い**(必須): 状況の要件を満たすものを、1 文で問います。

| 部品 | 決まり |
| --- | --- |
| 状況 | 1 文目で主体と目的・現状を書き、次の文以降で課題や要件・制約を示す(「〜する必要があります」「〜したいと考えています」)。要件を並べず、現状と課題だけから問いに進んでもよい。文の数と要件の数は資格別 |
| 問い | 状況とは別の 1 文。末尾は問いの形(です・ます)で終える。状況つきの設問は、状況と別の段落にする |
| 主体 | 状況の書き出しは「あるデータエンジニア(チーム、企業)は」が主。ほかに「あなたは」。製品の機能を直接問う設問は、製品名や機能名を主語にしてよい |
| 1 文 1 要件 | 要件・制約は、1 文に 1 つ。並べるときは文を分ける |
| 根拠 | 正答を決める要件・制約は、出典と事実カードで根拠を示せるものにする(状況を成り立たせる架空の設定の数値は、下の「状況の数値」のとおり除く) |

設問には、2 つの型があります。**状況の問**(状況の段落+問いの段落)と、**知識の問**(機能や仕様を直接問う 1 文)です。資格によって、2 つの割合が違います。

### 状況の数値

- 状況を成り立たせる架空の数値(件数、ファイル数、データ量、頻度、時刻、実行時間、レイテンシの目標など、シナリオの設定)は、事実の主張ではないので、事実カードで根拠を示さなくてよい。
- 設定の数値が答えを分ける要件になるときは、設問文の中で設定の値だと分かる書き方にする(「このチームは、〜を 5 分以内に問い合わせたいと考えています」のように、主体の要件として書く)。
- 製品の既定値・上限・保持期間・料金を数値で述べるときは、設定にせず、事実カードで根拠を示す。

## 2. 問いの形

- 末尾は「どれですか」「何ですか」「〜すべきですか」「〜でしょうか」か、「〜を選択してください」で終えます。句点の有無は問いません。
- 「どれか。」のように、「です・ます」を含まない末尾は避けます(点数票で減点します)。
- 機能を問うときは「どの機能(コマンド、オプション、トリガー)を〜」の形を使ってよい。
- 複数選択は、必ず選ぶ数(「(2 つ選択)」)を書き、正答の数と一致させます。
- 否定の設問(〜でないもの、〜サポートされていないもの)は、資格別の割合の上限の中でだけ使います。否定の語は 1 つにし、太字で強調します。

## 3. 選択肢

| 項目 | 決まり |
| --- | --- |
| 数 | 単一選択は 4。複数選択は 5(2 つが主) |
| 形 | 製品名・機能名・コマンドの語、語句、文が混在してよい。1 問の中では、形と句点の有無をそろえる |
| 内容 | 機能名や方式を選ぶ設問は、同じ層の別の機能(例: 同じ用途の別のコンピュート、別の取り込み方式)を中心に並べる |
| 並べ方 | 正答の位置と長さに偏りを作らない。正答だけが際立って長い(短い)形にしない |
| 誤答 | 正答と同じ分類のものから選び、ずらす(方式・範囲・条件・順序)。機能を問う設問では、同じ層の別の機能・機能の誤った説明・似た名前。やり方を問う設問では、正答の部品(オプション、句、権限、順序)を入れ替えたもの。コードの設問では、構文の違い。権限の設問では、権限の過不足。1 問の中で型を混ぜる(型と割合は資格別)。分類の違うもの(無関係な効果)は混ぜない。事実カードの主張で誤りを示せるものにする |
| 一括り | 「すべて正しい」「いずれでもない」は置かない |

## 4. 表記

- 製品名・機能名・設定名は、英語の表記のまま書きます(例: Delta Lake、Unity Catalog、Auto Loader)。
- 用語と機能の説明の仕方(機能の役割、モードやオプションの呼び方、動作の言い表し方)は、公式ドキュメントの記載に準じます。根拠にした事実カードの主張から外れた言い換えをしません。
- 名称が変わった機能(Delta Live Tables と Lakeflow 宣言型パイプライン、Databricks Jobs と Lakeflow Jobs、Databricks Asset Bundles とバンドルなど)は、新しい名称で書きます。旧称は、初出に括弧で添えてよい。どちらの名称を使うかは、事実カードの主張に合わせます。
- 旧称と新称を、別の選択肢に並べません(同じものを指すので、正答が 2 つになる)。旧称を誤答の材料にしません。
- コードやコマンドの断片は、設問文の中で段落を分けて示します。複数行のコードは、設問文の中にコードのブロックで置きます。
- 選択肢にコードのブロックは置きません。選択肢でコードを示すときは、文中のコード(`` `…` `` で囲んだ 1 行の SQL 文・式・コマンド)で書きます(選択肢で使える記法は、[データの仕様](../data-spec.md)の「6. 文字の書き方」)。

## 5. 要件と制約の言い回し

状況の要件を示す、短い定型句です。Databricks の資格では、「最もコスト効率が高い」のような定型の最上級よりも、状況の中の 1 つの事実(新しい列が届く、決まった時刻に動かす、上流の表が更新されたら動かす)が、同じ層の選択肢のうち 1 つを選ばせる形が多くなります。

| 種類 | 言い回しの例 |
| --- | --- |
| 必要性 | 〜する必要があります/〜が求められています |
| 目的 | 〜したいと考えています/〜を予定しています |
| 照合 | この要件を満たす〜 |
| 増分 | 新しく届いたファイルだけを処理したい/変更があった行だけを反映したい |
| レイテンシ | 近リアルタイムで問い合わせたい/到着から数分以内に使えるようにしたい |
| 運用の負荷 | 手作業をなくしたい/保守の手間を最小限にしたい/事前の起動を待ちたくない |
| コスト | アイドルの費用を抑えたい/コストを削減したい |
| スキーマの変化 | 新しい列が届いても、処理を止めたくない |
| 権限 | 最小権限で/読み取りだけを許したい |
| ガバナンス | リネージを追いたい/アクセスを監査したい |
| 重複 | 同じレコードを二重に取り込みたくない |
| 頻度・時刻 | 毎晩決まった時刻に/1 時間ごとに |

- 数値(データ量・頻度・件数)は、**答えを分けるときだけ**書きます。飾りで入れません。
- 形容詞だけの制約(「安全に」「効率よく」)は、答えを分けないので避けます。
- 長くするために、根拠のない要件を足しません。

## 6. 解説

問題文の書き方とは別に、解説の傾向です。既存の規則(`explanation-*`)と重ならない部分だけを書きます。

- 構成は、正答の節、誤答ごとの節(選択肢の数−1)、末尾の参照です。
- 誤答の節は、その選択肢が何の機能・モード・構文かを述べたうえで、この設問の要件に合わないことを示します。
- コードの問は、正答と誤答で違う点(語順、キーワード、引数、オプション名)を明示します。
- 長さは資格別です。
