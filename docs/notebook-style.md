# 体系ノートの文体の規則

体系ノート(`data/notebook.<コード>.json`)の本文を、教科書として読みやすい日本語にするための決まりです。
機械が書いた文に出やすい癖を、名前を付けて挙げ、見つけ方と直し方を書きます。直し役のサブエージェント
(`.claude/agents/notebook-reviser.md`)は、この文書だけを正にして本文を直します。手で書くときも、同じ決まりに従います。

本文の書き起こしの順は、**書く → この規則で直す → 公式の文書で検証する**です。言い換えで意味がずれることがあるため、検証を最後に置きます。
出典の扱いは[出典と権利の方針](./source-policy.md)に従います(自分の言葉で書き、公式の文を写さない)。

## 1. かける範囲

- かけるのは、体系ノートの本文だけです。中分類の `intro`・`diagram` の文字・`comparison` のセルと、見出しの `oneLine`・`body`・`examAngle`(後述の例外あり)・`checks` です。
- **問題文にはかけません。** 問題データ(`data/questions.*.json`)の設問文・選択肢・解説は、試験の言い回しに寄せる別の規則
  ([作問のスタイルガイド](./question-style.md)、[資格ごとの出題スタイル](./exam-style/README.md))に従います。
  この規則で直すと、試験に似せた言い回しが崩れ、二つの規則がぶつかります。

## 2. 触らないもの

次のものは、直す対象から外します。癖に見えても、そのまま残します。

| 触らないもの | 理由 |
| --- | --- |
| コード(`` `…` `` の中と、コードのブロックの中) | 構文と表記を正しく示すため |
| ID(`id`・`unit`・`related` など)と、`order`・`status` | データの参照と状態だから |
| 出典(`references` の題と URL) | 公式のページの題と所在だから |
| 用語そのもの(`term`、本文の中のサービス名・機能名・コマンド名・設定名) | 言い換えると、試験と公式の文書の表記から外れるため |
| `examAngle` の中の、試験の言い回し(鉤括弧で示した問い方や要件の書き方) | 試験でどう聞かれるかを示す部分で、言い回し自体が情報だから |

`keyPhrase` は `oneLine` の部分文字列です。`oneLine` を直したときは、`keyPhrase` も同じ文字列に合わせます。

## 3. 基本の書き方

- です・ます調で書きます。1 文には 1 つのことだけを書きます。
- 文の主語(何が、誰が)を書きます。「データファイルは」「利用者が」「Unity Catalog が」のように、動作の主を名指しします。
- 言い切れる事実は言い切ります。条件があるときは、条件を書いてから言い切ります(「既定では」「Delta Lake のテーブルだけ」)。
  ぼかしの語(「〜と言えるでしょう」「〜かもしれません」)で、条件を書く手間を省きません。
- 数値、既定値、必要な権限、使える範囲は、具体的に書きます。「重要です」「便利です」のような評価だけの文は書きません。

## 4. 直す癖の一覧

規則の名前は、直し役の報告に出る名前です。「見つけ方」は、目で見るか、文字列で探せる手がかりです。

### 4.1 記号

| 規則 | 見つけ方 | 直し方 |
| --- | --- | --- |
| `em-dash` | 全角ダッシュ(`―`、`—`、`──`)がある | 読点、コロン、括弧、文を分ける、のどれかにする |
| `quote-emphasis` | 固有名詞でも引用でもない語を鉤括弧で囲む(「軽い」「とりあえず動く」) | 鉤括弧を外す。強めたいなら、語を具体にする |
| `nakaguro-list` | 中黒で 3 つ以上の語を並べる(A・B・C) | 「A、B、C」か「A と B」にする。名前の一部の中黒は残す |
| `decoration` | 段落の末の絵文字、記号の飾り、閉じていない `**` | 消す |

### 4.2 語

| 規則 | 見つけ方 | 直し方 |
| --- | --- | --- |
| `stock-phrase` | 決まり文句(「〜において」「〜を実現します」「〜が可能です」「〜することができます」「〜と言えるでしょう」「ポイントは〜です」「〜を押さえておきましょう」) | 中身のある動詞にする(「〜できます」「〜を使います」)。中身がなければ文ごと消す |
| `favored-word` | 抽象的な語の多用(本質、重要、鍵、柔軟、シームレス、強力、効率的、最適、包括的) | 何がどう重要かを、数値や条件で書く。書けないなら消す |
| `overstatement` | 大げさな言い方(劇的に、圧倒的に、あらゆる、完全に、必ず、常に、革新的) | 公式の文書で言える範囲の強さに下げる。「必ず」は、例外のない仕様のときだけ使う |
| `translationese` | 翻訳調の動詞(〜を示しています、〜を意味します、〜を担います、〜を提供します) | 日本語の普通の述語にする(「〜です」「〜を受け持ちます」「〜を使えます」) |
| `katakana` | 普通の日本語に戻せるカタカナ語(コンテキスト、ユースケース、アプローチ、メリット) | 日本語に戻す(文脈、使いどころ、方法、利点)。製品の用語と公式の表記は残す |
| `adverb-stack` | 1 段落に程度の副詞(非常に、とても、かなり、大きく)が 2 つ以上 | 1 つ以下にする。多くは消しても意味が変わらない |

### 4.3 文

| 規則 | 見つけ方 | 直し方 |
| --- | --- | --- |
| `missing-subject` | 主語のない文が続き、何が動くのか読み取れない | 主語を書く。前の文と同じ主語でも、段落の最初では書く |
| `false-agency` | 物が人の動作をする(「テーブルが判断します」「データが示します」) | 実際に動く主(利用者、Unity Catalog、ジョブ)を主語にする |
| `contrast-frame` | 「A ではなく B」「単なる A ではなく B」で、誰も言っていない A を立てる | B を直接書く。取り違えやすい対があるときだけ、対比を残す |
| `both-sides` | 両論併記(「A もあり、B もあります」「〜もありますが、〜もあります」「場合によります」)で、どれを選ぶかを書かない | 公式の推奨や選ぶ条件を書く(「〜のときは A、それ以外は B」)。条件がなければ、片方を消す |
| `one-fact-per-sentence` | 1 文に事実が 3 つ以上入る、読点が 4 つ以上ある | 文を分ける |
| `negative-list` | 否定の列挙(「A でもなく、B でもなく、C です」) | 「C です」と書く |

### 4.4 構成

| 規則 | 見つけ方 | 直し方 |
| --- | --- | --- |
| `propositional-heading` | 見出し(`term`、本文の `## `)が主張の文になっている(「〜は〜だ」「〜すべき理由」) | 用語や話題の名前(名詞句)にする |
| `uniform-rhythm` | 段落の長さや文の長さ、文末がそろいすぎている(どの段落も 3 文、どの文も「〜します。」で終わる) | 段落の長さに差をつける。文末に「〜です」「〜ます」「〜ません」「体言+です」を混ぜる |
| `excess-bullets` | 文で書ける説明を箇条書きにする。箇条書きの項目が 1 語や断片だけ | 理由や順序のつながりがある説明は文にする。箇条書きは、並列で順序のない項目(要件、権限の一覧など)に使う |
| `triple-list` | 理由や利点を、いつも 3 つ並べる | 実際にある数だけ書く。2 つや 1 つでよい |
| `closing-summary` | 段落や見出しの末に、まとめ直しの文(「このように〜」「つまり〜」「まとめると〜」) | 消す。一言(`oneLine`)と比較の表が要約の役を持つ |
| `opener-preamble` | 前置き(「〜について見ていきましょう」「〜を理解することは重要です」) | 消して、本題から書き始める |

## 5. 直す例

直す前 → 直した後。どれも、意味を変えずに直しています。

1. `em-dash`・`stock-phrase`
   - 前: 外部テーブル――それはデータの柔軟な管理を実現するための仕組みです。
   - 後: 外部テーブルは、データファイルを利用者のクラウドストレージに置いたまま、Unity Catalog に登録するテーブルです。
2. `false-agency`・`missing-subject`
   - 前: DROP TABLE を実行すると、テーブルがデータファイルの削除を判断します。
   - 後: DROP TABLE を実行すると、Unity Catalog はマネージドテーブルのデータファイルを、復元の期間のあとに消します。
3. `both-sides`
   - 前: CTAS で作り直す方法もありますし、SET MANAGED を使う方法もあります。状況に応じて選びましょう。
   - 後: 外部テーブルをマネージドテーブルに変えるときは、SET MANAGED を使います。CTAS で作り直すより、止まる時間が短いためです。
4. `overstatement`・`favored-word`
   - 前: マネージドテーブルを使えば、あらゆる最適化が完全に自動化され、性能が劇的に向上します。
   - 後: マネージドテーブルでは、予測的最適化などの最適化を Unity Catalog が受け持ちます。
5. `contrast-frame`
   - 前: UNDROP TABLE は単なる取り消しではなく、メタデータの復元です。
   - 後: UNDROP TABLE は、削除したテーブルのメタデータ(権限や列の定義など)を戻します。
6. `closing-summary`
   - 前: (本文の末に)このように、DROP の挙動を理解することがテーブルの種類を選ぶ鍵となります。
   - 後: (文ごと消す)
7. `propositional-heading`
   - 前: `## 外部テーブルは削除してもデータが残る`
   - 後: `## 削除したときの挙動`

## 6. 欄ごとの決まり

| 欄 | 決まり |
| --- | --- |
| `intro` | 1〜2 文。中分類で扱う用語と、その違いの軸を書く |
| `oneLine` | 1 文。用語が何かを、主語と述語のそろった文で書く。`keyPhrase` はこの文の部分文字列 |
| `body` | 段落とコードのブロックで書く。箇条書きは `excess-bullets` の範囲で使う。最後をまとめの文で終えない |
| `examAngle` | 試験でどう問われるかを書く。鉤括弧の中の試験の言い回しは、この規則で直さない(地の文は直す) |
| `checks` | 問いは、答えが 1 つに決まる形にする。理由は、答えの根拠を 1〜2 文で書く |
| `diagram`・`comparison` | 短い名詞句か、短い文で書く。同じ行のセルは、同じ観点でそろえる |

## 7. 直すときの約束

- 意味を変えません。数値、条件、適用範囲、否定と肯定、主張の強さ(「既定では」「〜だけ」)は、そのまま残します。
- 直すと意味が変わるおそれがある箇所は、直さずに残し、場所を報告します。
- 足すのは、主語と、すでに本文にある条件だけです。新しい事実を足しません。
- 1 回で直しきれないときも、2 回目は同じ規則でかけ直します。規則にない好みで書き換えません。

## 8. 規則を足す・変えるとき

この文書の表に行を足し、直す例を 1 つ添えます。直し役の定義には、規則を写しません(この文書が正です)。
