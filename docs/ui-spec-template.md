# 画面の仕様のひな形

新しいモードや画面を作る前に、この形で短い仕様を書き、**人の承認を得てから実装します**。
仕様は、画面の見た目の方針([デザイン方針](./app/design-tone.md))、データの契約([問題データの仕様](./data-spec.md)、[データの設計](./app/data.md))を、再利用する前提で書きます。
設計の判断の記録(ADR。`docs/app/adr/`)とは、役割が違います。ADR は判断の理由を残し、仕様は画面ごとの作りを決めます。

## 1. いつ書くか

| 書く | 書かない |
| --- | --- |
| 新しい画面・モードを足す | 文言の修正 |
| メニューの階層やナビゲーションを変える | 既存の画面の微調整(余白、色、並びの小さな変更) |
| 新しいデータの項目や、データの契約の変更が要る | 不具合の修正 |

迷うときは、書きます。実装の前に迷う点があれば、仕様の「未決の点」に書いて、承認のときに決めます(`CLAUDE.md` の「進め方」)。

## 2. どこに置くか

- 小さな仕様は、Issue の本文に書きます。
- 残したい仕様は、`docs/app/specs/<名前>.md` に置きます(置き場の決まりは [`docs/app/specs/README.md`](./app/specs/README.md))。

## 3. 承認の流れ

1. 実装の前に、仕様を書く。
2. 人に見せて、承認を得る。承認が出るまで、実装に入らない。
3. 承認のあとに仕様が変わるときは、仕様を直して、承認を得直す。

## 4. ひな形

次の見出しを、この順に書きます。空欄にせず、ないものは「なし」と書きます。

```markdown
# <画面またはモードの名前>の仕様

## ユーザーの流れ

入口から終わりまでの操作を、番号つきの手順で書く。

1. …
2. …

## 画面の構成とメニューの階層

- 画面の一覧と、各画面の主な要素。
- ナビゲーションの階層(どのメニューから、どこへ行くか)。

## 再利用する既存の部品とレイアウト

- 使う部品とレイアウトの名前を、実装のパスで示す(例: `packages/app/src/components/…`)。
- 新しく作る部品は、再利用できない理由を添える。

## 必要なデータ

- 読む・書くデータと、その契約([問題データの仕様](../../data-spec.md)、[データの設計](../data.md))との対応。
- データの契約の変更が要るか(要るなら、何を足すか)。

## 前提

- 認証(ログインが要るか、管理者だけか)。
- 画面スタイル(リッチ / シンプル)、ライト / ダーク、動きを減らす設定への対応。

## 未決の点

決まっていないことを、質問の形で列挙する。承認のときに決める。
```

## 5. 書き方の注意

- 環境固有の値、個人情報、機密を書きません(`CLAUDE.md` の「書いてはいけないもの」)。
- 既存の文書(デザイン方針、データの仕様、ADR)の内容は書き写さず、参照します。
- 出来事を語る書き方にせず、決めたことを書きます。
