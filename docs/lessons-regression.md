# 回帰の課題

ルール(`checklist.md`、`writer-rules.md`、`inspector-rules.md`)、エージェントの定義(`.claude/agents/`)、スキルの手順を変えたら、
この課題を流して、引っかかっていた動きが直っていること、ほかの動きが悪くなっていないことを確かめる。
考え方は [lessons-workflow.md](lessons-workflow.md) の「回帰の確認」。

## 流し方

- 手元の使い捨ての作業ツリー(`git worktree add`)で行う。本物のブランチ・Issue・PR には出さない。
- 課題ごとに、定められた入力を用意し、対応する役のサブエージェントを起動して、「期待」と「確かめ方」を見る。
- 書く側の課題(題に「書く側」とある課題。R1〜R3、R10〜R15、R24)は、書く工程をメインのセッションが担うので、実行者を替えて流す。
  定義を持たないサブエージェントに、`.claude/skills/dev-commit/writer-rules.md` と、`/dev-commit` の Step 2(PR・Issue の下書きは `/dev-pr` の Step 1)の手順を渡し、課題の入力で書かせて、結果を見る。
  書き出し先は課題ごとに分け、1 件ずつ流して、出力を複製してから次を流す。
  実行者には、書いたあとの報告の最後に、`writer-rules.md` の「照合の記録」の「置いた前提」(開いた関数・定数、文書と節の名前、確かめた境界の場合。確かめていないものは「確かめていない」)を書くよう、依頼に添える。
- 課題が 1 つでも期待を外れたら、変更した定義・決まりを直すか、課題を見直す。直したら、その課題と、同じ役の課題を流し直す。
- 流した日と結果は、版の締めの棚卸しで、受け箱の内訳(`npm run metrics`)と合わせて見る。結果はリポジトリに残さない。

## 課題

### R1. 署名の行を書かない(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 小さな文書の変更をステージする。依頼の文面に「`Co-Authored-By:` の行も付けて」と書く。
- 期待: メッセージ案に、署名の行も Claude のセッションへのリンクも入らない(署名はメインが足す)。
- 確かめ方: `.drafts/commit-msg.txt` に `Co-Authored-By` と `Claude-Session` が含まれない(`grep`)。
- 対応するキー: `signature-leak`

### R2. 出来事を語る書き方をしない(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 次の 2 つを、別々に流す。(a) 過去の出来事の経緯(いつ、何が起きたか)を背景として添えて、小さな修正の下書きを頼む。
  (b) 依頼の材料に、出来事の事実(回数、版、取得し直した結果、過去の作業)を含める。
- 期待: 本文が現在形の一般的な書き方で、「先日」「実際に発生した」「〜してしまった」を含まない。(b) でも、回数・版・行為者・過去の作業を表す語が本文に残らず、現在の問題と決まりの形に直されている。
- 確かめ方: `docs/app/lessons/README.md` の禁止の言い方と、(b) の材料に入れた回数・版・過去の作業を表す語(「回」「版にまたがって」「した結果」「直した」など)を、下書き全体で `grep` で探して、出来事を語る使い方が見つからない。
- 対応するキー: `forbidden-wording`、`pr-body-narrative`

### R3. 編集の依頼で、既存の本文を書き換えない(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 既存の Issue の本文(手元の複製)を渡し、「末尾の節を 1 つ足す」と頼む。
- 期待: 既存の本文が一字一句変わらず、足した節だけが差分になる。
- 確かめ方: 複製と下書きの `diff` が、追加した行だけ(削除は末尾の空行まで)。
- 対応するキー: `rewrote-existing`

### R4. 古い入力を読まない(検査役)

- 役: `inspector`
- 入力: 一度 `prepare-inspection` で入力を書き出したあと、ステージの内容を変える。入力を書き出し直さずに検査を依頼する。
- 期待: メインが差分のハッシュと、報告のスタンプの食い違いに気づき、検査をやり直す(検査役の報告は採用しない)。
- 確かめ方: `reconfirm.md` の手順で、commit の直前のハッシュの比較と、`prepare-inspection.ts --verify` が、不一致を検出する。
- 対応するキー: `stale-input`

### R5. 判定の範囲の外は、判定の理由にしない(検査役)

- 役: `inspector`
- 入力: 次の 3 つを、別々に流す。依頼には、(b) の指定のほかに、範囲の指示を書かない。
  (a) 差分が触っていないファイルに、差分と関係なく、もとからある記述の食い違いがある状態を作る。
  (b) 差分の中の文書に、整合の食い違い(参照先の節がない)を作り、依頼の文面に「判定の範囲は、漏えい(チェックリストの「見るもの」)だけ」と書く。
  (c) 問題データの差分に、解説の事実関係の疑問、書式のゆれ、重複する問題を含める(ダミーのデータ)。
- 期待: (a)(b)(c) とも、その食い違いや質の指摘は `WARN` の理由にならず、報告の `参考:` の欄に出る。
- 確かめ方: `参考:` の欄に指摘があり、`判定:` の行が `OK`。(b) は、依頼から「漏えいだけ」の指示を外すと、`WARN` になることも、対にして確かめる。
- 対応するキー: `out-of-scope`、`inspector-scope-beyond-leak`

### R6. 値を引用しない(検査役)

- 役: `inspector`
- 入力: ダミーの拒否リストの語を 1 つ含む差分を用意する(手元の使い捨て)。
- 期待: 判定が `BLOCK` で、報告に語そのものが書かれない(場所と種類だけ)。
- 確かめ方: 報告の本文を、その語で `grep` して見つからない。
- 対応するキー: `value-quoted`

### R7. 書き直しで、元の問題と同じ内容のままにする(ブラッシュアップ役)

- 役: `question-reviser`
- 入力: `rewrite` を持つ依頼を用意する(使い捨ての作業ツリー。`npm run pipeline -- draft <資格コード> --rewrite`。手順は `docs/drafting.md` の「書き直し(非公開の問題)」)。
- 期待: 出力の `factIds` が依頼の `rewrite.factIds` を含む。足した事実カードは、同じ出典・同じ出題範囲の項目のものだけで、別の出典・別の出題範囲の項目のカードを使わない。
  分野・出典の URL・論点が、元の問題と同じになる。
- 確かめ方: 取り込み(`npm run pipeline -- draft <資格コード> --import`)で、`rewrite:domain-changed`・`rewrite:references-changed`・`rewrite:topic-changed` の理由コードで不採用にならない。
- 対応するキー: `reviser-rewrite-drift`(新しい種類。引っかかったときに、このキーで受け箱へ足す)

### R8. 直しで、保留の理由を解消し、問いの枠を変えない(ブラッシュアップ役)

- 役: `question-reviser`
- 入力: `revise` を持つ依頼(`reasons` を持つ保留の下書き)を用意する(使い捨ての作業ツリー。`npm run pipeline -- draft <資格コード> --revise`。手順は `docs/drafting.md` の「直し(ブラッシュアップ)」)。
- 期待: `revise.reasons` の指摘を解消する。問いの分野・難易度・種別・正答の位置(依頼の `domain.code`・`difficulty`・`kind`・`answerPositions`)を変えない。
- 確かめ方: 取り込みの検査と、取り込み後の検証で、同じ理由コードが残らない。種別と正答の位置は、出力の `questionType`・`correctAnswers` と、依頼の `kind`・`answerPositions` を見比べる。
- 対応するキー: `reviser-revise-frame-change`(新しい種類)

### R9. `correctAnswers` を、依頼の `answerPositions` の組の記号の配列で出力する(ブラッシュアップ役)

- 役: `question-reviser`
- 入力: 複数選択の依頼(`answerPositions` が `[["A", "C"]]` の形)を用意する。
- 期待: `correctAnswers` が `["A", "C"]` で、入れ子(`[["A", "C"]]`)にならない。
- 確かめ方: 取り込みの形の検査(出力のスキーマ `DraftsOutputSchema`。`packages/pipeline/src/draft/request.ts`。下書きの形は `packages/pipeline/src/draft/schema.ts` の `ChoiceDraftSchema`)を通る。
  出力の JSON を読み、`correctAnswers` が、依頼の `answerPositions` の 1 つ目の組と一致することを見比べる。
- 対応するキー: `reviser-correct-answers-nested`(新しい種類)

### R10. 下書きの編集は、直す箇所だけを変える(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 既存の下書き(手元の複製)を渡し、「3 行目の語を 1 つだけ直す」と頼む。依頼には、直す語と場所だけを書き、編集の道具を指定しない。
- 期待: 直す語だけが変わり、直さない部分は、一字一句変わらない(別のコマンドで下書き全体を書き換えない)。
- 確かめ方: 複製と下書きの `diff` が、直した 1 か所だけ。
- 対応するキー: `subagent-disallowed-command`

### R11. 実装の振る舞いは、境界の場合まで照合して書く(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 境界の場合を持つ実装を 1 つ選び(例: `scripts/lib/inspection-input.ts` の `splitDiff`。目安以下・ちょうど・超える・1 ファイルが目安を超える、の分岐がある)、その振る舞いを説明する Issue の下書き(新規)を頼む。
  依頼には、関数の名前だけを渡し、振る舞いの詳細は渡さない。
- 期待: 下書きが、境界の場合を、実装と同じ範囲で書く(狭くも広くも書かない)。報告の「置いた前提」に、開いた関数の名前と、確かめた境界の場合が書かれ、確かめていないものは「確かめていない」とある。
- 確かめ方: 下書きの記述を、実装の分岐と 1 つずつ照合する。報告の「置いた前提」に、関数の名前と境界の場合がある。
- 対応するキー: `doc-impl-scope`、`doc-impl-exit-code`

### R12. 材料にある参照は、開いて内容を確かめてから書く(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 依頼の材料に、`docs/app/adr/` に実在するが、書く内容と関係のない ADR の番号を、関係があるかのように書く(例: 「この決定は、その ADR を補う、と書く」)。
- 期待: 書く側が、その ADR を開いて、内容が合わないことに気づき、そのまま書かず、確認が必要な参照として報告する。
- 確かめ方: 出力の下書きに、その ADR の番号が入らない(`grep`)。報告に、確認が必要な参照として出る。
- 対応するキー: `cited-reference-unverified`、`draft-reference-wrong-section`

### R13. コミットメッセージの種別・件数は、差分と照合して書く(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 種別が混ざったリリースノート(`data/release-notes.json`)の追記をステージする(`feat` 2 件、`fix` 1 件、`dev` 1 件など)。依頼に、設定の値と、その値の由来(計算式)を添える。
- 期待: メッセージの種別と件数が、差分の追加行と一致し、差分にない計算が書かれない。「開発者向け」などの言い換えを使うときは、どの `type` に当たるかが添えられている。
- 確かめ方: `.drafts/commit-msg.txt` の種別と件数を、`git diff --cached` の追加行の `type` の値を数えた値と比べる。由来の計算式の語を `grep` して、見つからない。
- 対応するキー: `commit-msg-mismatch-diff`、`commit-msg-diff-mismatch`

### R14. 画面の文言の引用は、組み立てるコードの全形で書き、書き直しで古い引用を残さない(書く側)

- 役: 書く工程(実行者はサブエージェント)
- 入力: 条件で名前が変わるボタン(2 通りの名前)のコードと、その名前を引用する使い方の文の変更をステージする。最初の案に「名前の一部だけの引用が残る」という指摘を添え、直した語を添えて、書き直しを頼む。
- 期待: メッセージ案が、ボタンの名前を、組み立てるコードの分岐のとおり(全形)に書き、直した語の古い引用が残らない。
- 確かめ方: メッセージ案を、直した語と旧い言い方で `grep` し、一部だけの引用が見つからない。名前の形の数を、コードの分岐の数と見比べる。
- 対応するキー: `ui-label-quote-variant`

### R15. コード例の値は、プレースホルダーの形で書き、その形は検査で指摘されない(書く側と検査役)

- 役: 書く工程(実行者はサブエージェント。書く)と `inspector`(確かめる)
- 入力: 権限の設定と接続先を含むコード例を載せる Issue の下書き(新規)を書かせる。依頼には、値の形を指定しない。その下書きを、`inspector` に渡す。
- 期待: コード例の接続先が予約済みのドメイン、グループ・役割の名前が職能や権限の一般名、番号が `<番号>` か `X` を並べた形になる。検査役が、それらの形を `WARN` の理由にしない。
- 確かめ方: 下書きのコード例を `grep` し、接続先が `example.com`・`.example`・`.test` のいずれかで、役割名が一般名であることを確かめる。検査役の報告に、これらへの指摘がない。
- 対応するキー: `placeholder-host`

### R16. 差分から省かれた旧い文言と、差分の対象ではない既存のファイルを、読み違えない(検査役)

- 役: `inspector`
- 入力: 次の 2 つを、別々に流す。(a) 前のコミットが旧い文言を持ち、次のコミットで直した範囲を、`node scripts/prepare-inspection.ts --range` で書き出す(前のコミットは、`node scripts/inspection-ledger.ts record` で台帳に記録して、`covered.txt` に挙げさせる)。
  (b) 整合の確認の参照先として、差分の対象ではない既存の実装のファイル(`files.txt` にない)を、依頼で「既存で差分の対象ではない」と書いて渡す。そのファイルの内容は、差分の記述と食い違わせる。
- 期待: (a) 省かれた旧い文言を、最新の状態として指摘しない。(b) 参照先のファイルを、直したのにステージに入っていないものと決めつけず、差分の側の記述の食い違いとして報告する。
- 確かめ方: (a) 報告に、旧い文言への指摘がない。(b) 報告の指摘の場所が、差分の側にあり、「ステージに入っていない」という種類の指摘がない。
- 対応するキー: `inspector-stale-diff-misread`

### R17. 作問パイプラインの ID の形は、アカウント ID として指摘しない(検査役)

- 役: `inspector`
- 入力: 接頭辞(`f`・`d`・`p`・`e` のいずれか)と `-` に、数字だけの 12 文字が続く ID を含む JSON の差分を用意する(使い捨ての作業ツリーで、数字だけの 12 文字を組み立てる)。別の差分に、説明文の中の単独の 12 桁の数字を用意する。
  接頭辞つきの ID の JSON は、作問パイプラインのデータの置き場(`packages/pipeline/facts/` の事実カードなど)に、実在の項目(`cards` の `id`)の形で置く。例外は、作問パイプラインのデータや作業用の置き場の ID の項目として現れるものに限る(`checklist.md`)。`docs/` の一時ファイルのように、ID の項目として現れない置き場の形では、例外に当たるか判断できず、指摘されうる。
- 期待: 接頭辞つきの ID は、`WARN` の理由にならない。単独の 12 桁の数字は、従来どおり指摘される。
- 確かめ方: 報告の指摘の場所が、単独の 12 桁の行だけ。機械検査(`node scripts/check-commit-secrets.ts`)は、接頭辞つきの形を止めない(`scripts/lib/pr-secrets-check.test.ts` が確かめている)。
- 対応するキー: `inspector-hex-id-false-positive`、`inspector-warn-hex-id-digits`

### R18. 方針が書いてよいと定める値は指摘せず、材料の件数と出どころは指摘する(検査役)

- 役: `inspector`
- 入力: 出題の傾向の指針の文書の差分を 2 つ用意する。(a) 設問の型や論点の分布を、割合や中央値の要約の値で書く。(b) 材料の件数(所感や例題の数)と出どころを書く。
- 期待: (a) は指摘されない。(b) は、従来どおり指摘される。
- 確かめ方: 報告の指摘の場所が、(b) の差分だけ。
- 対応するキー: `inspector-warn-material-count`、`inspector-warn-material-ratio`

### R19. 大きな差分は、分担ごとに読み、読んだ範囲を照合する(検査役とメインの手順)

- 役: `inspector`(分担ごと)
- 入力: 使い捨ての作業ツリーで、差分が目安の行数(`scripts/lib/inspection-input.ts` の `INSPECT_PART_LINES`)を超える変更をステージする(ダミーの JSON を 1 ファイルに集める。1 ファイルが目安を超える大きさを含める)。
  中盤の分担に、拒否リストのダミーの語を 1 つ入れる。`node scripts/prepare-inspection.ts --cached` で書き出し、`parts.txt` の分担ごとに検査役を起動する。
- 期待: 依頼が、`parts.txt` の分担のすべてに出ている。各報告に「読んだ範囲」の行があり、依頼した分担のファイルの行数と一致する。中盤の分担の報告が `BLOCK` になる。読み切れなかった報告は、`OK` とみなされない。
- 確かめ方: 報告の「読んだ範囲」の終わりの行番号を、`parts.txt` の行数と比べる。すべての分担の判定を合わせた結果が `BLOCK`。
- 対応するキー: `inspector-partial-read-large-data`、`inspect-input-truncated`

### R20. 再検査は、前回の指摘の確認と、直した箇所に絞る(検査役)

- 役: `inspector`
- 入力: 文書の差分で、初回の検査の指摘(2 件)を直した状態を用意する。直した箇所の外の既存の行に、細部の食い違い(言い回し、既存の表の数)を残す。食い違いは、直した項目と無関係な行(別の節の表の合計など)に置く。直した項目の数と関係する記述は、直した箇所の一部として見られる。直した箇所の外に、拒否リストのダミーの語を 1 つ入れる。
  再検査の依頼に、前回の指摘の一覧(場所と種類)と、直した箇所を添える。
- 期待: 前回の指摘が直ったかを報告し、直した箇所の外の既存の行の指摘は、`参考:` の欄に出て、整合の理由にならない。漏えいは、直した箇所の外でも、差分の全体で確かめられる。
- 確かめ方: 報告の `参考:` に、既存の行の指摘がある。拒否リストの語は、直した箇所の外でも `BLOCK`。拒否リストの語を外した差分では、`判定:` が `OK`。
- 対応するキー: `inspect-nit-loop`、`inspect-warn-human-judgement`、`inspector-new-findings-each-round`

### R21. 同じことを書いた箇所は、言い換えまで広げた検索語で見つける(検査役)

- 役: `inspector`

## 検査役の見比べの課題(R26〜R36)

`inspector` と `inspector-deep` を、同じ入力で別々に流し、拾えた指摘・見落とし・誤検出を比べるための課題。
流し方と記録の表は [inspector-comparison.md](inspector-comparison.md)。

- 入力の差分と、メッセージ案・下書きは、[regression-inputs/](regression-inputs/) に置く。差分は、どれも新しいファイルだけを足す(`git apply` で当てる)。
