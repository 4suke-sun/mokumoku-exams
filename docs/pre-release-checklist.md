# 公開前のチェックリスト

リポジトリを公開する前に、1 項目ずつ確かめます。各項目に、確認の方法を書いています。結果は、場所と種類だけで記録し、値は書きません。

公開すると、履歴のすべてのコミット(途中のコミットも含む)が見えるようになります。あとから消せないので、公開の前に確かめます。

## 1. 機密

| 項目 | 確認の方法 |
| --- | --- |
| 全履歴の追加行・ファイル名・メッセージ・作者に、認証情報や環境固有の値がない | すべてのブランチを対象に、`node scripts/check-push-secrets.ts` を実行する(下の「全履歴の検査」)。終了コードが 0 |
| 個人固有の語(拒否リスト)が、履歴のどこにもない | `.pr-secrets-denylist` の語を、全履歴の差分・コミットメッセージに対して `git log --all -p` と `grep -F -f` で数える(タグは軽量タグで、タグ自体のメッセージはない)。0 件。語は報告に書かない |
| アクセスキー・秘密鍵の形の文字列がない | `git log --all -p` の出力に、`AKIA`・`ASIA`・`-----BEGIN … PRIVATE KEY` の形が 0 件 |
| メールアドレスが、GitHub の noreply と `example.com` だけ | 追加行のメールアドレスを集計して確かめる |
| アカウント ID・ARN・配信のドメインが、プレースホルダーだけ | 追加行の 12 桁の数字、`arn:aws:…:<12 桁>:`、`cloudfront.net` などのドメインを集計して確かめる。実値がなく、`123456789012`・`xxxx.cloudfront.net` のような例だけ |
| 作者・コミッターが、意図したものだけ | `git log --all --format='%an|%cn|%ce' \| sort \| uniq -c`。メールアドレスは noreply だけ。表示名は、公開してよいニックネームだけ |
| Issue・PR・リリースの本文に、上と同じものがない | `gh issue list` / `gh pr list` / `gh release list` の本文を、同じ観点で確かめる(コメントも含める) |
| `.env`・`.drafts/`・`.pr-secrets-denylist` が、追跡されていない | `git ls-files` に、これらが出ない |
| 公開リポジトリの Secrets・変数に、不要な値がない | リポジトリの設定の Secrets and variables を開き、使っていないものを消す |

### 全履歴の検査

```sh
git fetch --prune --tags
# すべてのリモートブランチを、履歴の最初から検査する(リモートの SHA を 0 にすると、最初からになる)
for r in $(git for-each-ref --format='%(refname)' refs/remotes | grep -v HEAD); do
  printf '%s %s %s 0000000000000000000000000000000000000000\n' "$r" "$(git rev-parse "$r")" "$r"
done | node scripts/check-push-secrets.ts
```

機械検査に加えて、人の目(またはレビュー担当)で、文脈での確認もする。正規表現で拾えない、社外の名称や経緯を示す語を見る。

## 2. 権利

| 項目 | 確認の方法 |
| --- | --- |
| 問題・解説・教材が、このリポジトリの作問で、他の問題集や試験の問題の写しではない | `docs/adding-an-exam.md` の手順で作ったデータだけが `data/` にある。出典は、ベンダーの公式ドキュメントのドメインだけ(`npm run validate:data` が検査する) |
| 外部の文章・図・画像を、許可なく載せていない | `data/` と `packages/app/public/` の画像・文章を見直し、出所がわからないものがない |
| 依存パッケージのライセンスが、MIT と両立する | `npm ls --all` で依存を出し、ライセンスが GPL などの強いコピーレフトのものがないか確かめる |
| 資格名・製品名の商標について、README に断りがある | README の「商標について」の節がある |

## 3. ライセンス

| 項目 | 確認の方法 |
| --- | --- |
| `LICENSE` がある | リポジトリの直下に `LICENSE`(MIT License)がある |
| 著作権者の表記が、公開してよい名前 | `LICENSE` の著作権者の行が、GitHub のユーザー名 |
| README のライセンスの節が、`LICENSE` と一致する | README の「ライセンス」の節が、`LICENSE` を指している |

## 4. 設定値

| 項目 | 確認の方法 |
| --- | --- |
| 環境固有の値が、コードやドキュメントに書かれていない | 上の「機密」の検査が通る。値は `.env`(gitignore 済み)にだけある |
| `.env.example` が、プレースホルダーだけ | `.env.example` を開き、実値がない |
| 必須の設定値が、足りないときに、名前だけを示して止まる | `packages/infra/lib/config.ts` のテスト(`npm test`)が通る |
| 初めての人が、README の手順で開発環境を立ち上げられる | まっさらな clone で、README の「開発の始め方」を上から順にやり、`AUTH_FAKE=1 npm run dev` でログインの画面が開く |

## 5. 動作確認

| 項目 | 確認の方法 |
| --- | --- |
| lint・型検査・ビルド・テスト・データ検査が通る | CI(`.github/workflows/ci.yml` の `check`)が、main で成功している |
| 主要な画面の通し確認が通る | CI の `e2e` が成功している(ログイン、資格の一覧、出題、結果) |
| リリースノートとタグが対応している | `npm run check:release-notes` が通る |
| デプロイした環境で、ログインなしに開けるのが、公開の経路だけ | 配信のドメインで、`/login` が 200、そのほかの画面が 307(ログインへ)、API が 401 になる |
| 配信を通らない直接のアクセスが断られる | Lambda の Function URL への直接のアクセスが 403 になる |
| 管理者の経路が、管理者以外に開かない | `src/authorization.test.ts` が通る。デプロイした環境でも、管理者以外で `/admin` がホームへ戻る |
| ログイン後の主要な流れが、実機で動く | デプロイした環境で、ログイン → 出題 → 結果 → 実績を、一通り操作する |

## 6. 公開の手順

1. 上の項目がすべて確かめられていることを、PR またはコメントに記録する(値は書かず、場所と種類だけ)。
2. リポジトリの可視性を切り替える前に、最後にもう一度、「全履歴の検査」を実行する。
3. 切り替えたあと、公開の画面で、Issue・PR・リリースの本文を、第三者の目で見直す。
