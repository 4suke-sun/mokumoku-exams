# 既知の問題

解決していない制約や不具合の一覧です。利用者と開発者が確認できるようにします。

## 書式

1 件につき、次の項目を書きます。

```markdown
### 題(症状を短く)

- 症状: 何が起きるか
- 影響: だれの、どの操作に影響するか
- 回避策: 当面の対処(なければ「なし」)
- 状態: 調査中 | 対応予定(Issue 番号) | 解決済み(版)
```

## 更新ルール

- 新しい問題が見つかったら、この文書に項目を足し、対応する Issue を立てて、番号を「状態」に書きます。
- 解決したら、項目を消さずに、「状態」を「解決済み(版)」にします。次の版のリリースノートで、解決を知らせます。
- 解決済みの項目は、解決した版から数えて 2 つ後の版で、この文書から取り除きます(例: v0.3.0 で解決したら、v0.5.0 で取り除く。履歴は Git に残ります)。
- 症状・影響・回避策は、一般的な書き方で書きます。環境固有の値、個人情報、認証情報は書きません。

## 一覧

### `main` への強制 push のあとは、新しいコミットの中身を CI が検査できない

- 症状: `main` への強制 push では、push 前の位置が新しい履歴に残らないため、CI の機密検査は「検査を完了できませんでした」で失敗し、新しいコミットの中身は検査されない。
- 影響: 強制 push で履歴に載った値は、CI では見つからない(失敗として検知はできる)。
- 回避策: `main` への強制 push は、しない(履歴の書き換えは、人の承認を得てからにする)。やむを得ず行ったときは、手元で `pre-push` と同じ検査を、新しい履歴の全体にかける。
- 状態: ブランチ保護が使えるようになるまで続く(方針は CONTRIBUTING.md の「Pull Request」の節)。

### `main` を新しく作る push では、CI の機密検査の範囲が空になりうる

- 症状: `main` が存在しないリモートへの最初の push では、CI のチェックアウトの時点で `origin/main` が先頭と同じ位置になり、検査の範囲が空になる。
- 影響: 最初の push の中身は、CI では検査されない。
- 回避策: 最初の push の前に、手元の `pre-push` の検査(全履歴が対象)で確認する。
- 状態: 最初の push のあとは起こらないため、対応しない。

### 結果の一覧と「解いた回数」が、新しい 50 件までに限られる

- 症状: サーバーから取得する結果の一覧は、1 回に新しい 50 件までで、それより古い結果は一覧に出ない。「解いた回数」も、取得した結果から数えるため、サーバーに保存した分は 50 回を超えると増えない(通信に失敗して端末にだけ残った分は、加わる)。
- 影響: 50 回を超えて解いた利用者の、古い結果の確認と、解いた回数の表示。
- 回避策: なし。
- 状態: 対応予定(#313)
