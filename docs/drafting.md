# 出題計画と下書きの手順

作問パイプラインの 3 つ目と 4 つ目の段階(出題計画、下書き)の手順です。
通過した事実カードから、作る問題の数と中身を決め、選択式(単一・複数)と自由記述の問題の下書きを作ります。
判断の理由は ADR 0007〜0009 にあります。作り方の決まりは[作問のスタイルガイド](./question-style.md)、
前の段階は[事実カードの作法と運用手順](./fact-cards.md)、出典の扱いは[出典と権利の方針](./source-policy.md)にあります。

## 1. 置き場所

| 場所 | 内容 | コミット |
| --- | --- | --- |
| `pipeline-work/plan/<コード>/plan.json` | 出題計画(分野ごとの目標と不足、区分ごとの数) | しない |
| `pipeline-work/draft/<コード>/requests/<鍵>.json` | エージェントへの下書きの依頼 | しない |
| `pipeline-work/draft/<コード>/out/<鍵>.json` | エージェントが書いた下書き | しない |
| `pipeline-work/draft/<コード>/drafts.json` | 取り込んだ下書き(通過・保留。不採用は本文を持たない) | しない |
| `pipeline-work/draft/<コード>/state.json` | 失敗の回数、取り込み済みの依頼の鍵、出し直しの回数、計画の項目ごとの未達の理由(理由コードだけ) | しない |
| `pipeline-work/draft/<コード>/review.md` | 人の確認用の表(要判断の下書き: 通過・保留の下書きと、人が却下した下書き。抜き取りのときは、通過のうち選んだものだけ。設定 `review.autoApprove` に挙げた試験では、基準を満たして承認を省ける下書き、書き出し済みの下書き、基準を満たすが来歴の検査で止まる下書きを節に載せず、冒頭に件数と ID だけを出す) | しない |
| `pipeline-work/draft/<コード>/review-sheet.json` | 判断を書き込むシート | しない |
| `pipeline-work/export/<コード>/report.md` | 書き出しの差分レポート(件数と種類だけ) | しない |
| `packages/pipeline/provenance/<コード>.json` | 問題の来歴(下書きの ID、根拠の事実カードの ID、出典の URL、取得日、本文のハッシュ。書き出したあとは、問題の ID) | する |
| `packages/pipeline/decisions/<コード>.json` | 人の判断の記録(対象の ID、判断、理由コード。[人の判断の記録](./human-decisions.md)) | する |

`<コード>` は、試験コードを英小文字にしたものです。置き場所は `packages/pipeline/pipeline.config.json` で決まります。

**台帳(来歴)に載せるのは、ID、リンク、日付、ハッシュだけです。** 設問文、選択肢、事実カードの主張、言い換えは載せません。
下書きの本文は `pipeline-work/` だけに置きます。公開データ(`data/`)には、書き出しの段階で、出典の URL と題(`references`。題は台帳の公式ページの題で、台帳に題がない出典は題なし)だけが載ります。
出題計画と下書きの段階では、`data/` を読み取るだけで、書き換えません(書くのは、書き出し(`export`)と、公開と非公開の移動(`unpublish`・`restore`)の段階だけです)。

## 2. 出題計画

```sh
npm run pipeline -- plan <試験コード>
```

- 目標の問題数は、**本番の出題数 × 倍率**です(設定 `plan.targetMultiplier`。既定は 3)。試験ごとに `plan.overrides.<試験コード>.targetTotal` で上書きできます。
- 目標は、分野の重みに比例して分野へ配り、分野の目標を、難易度(`easy`・`medium`・`hard`)と種別(`single`・`multiple`・`free-text`)の配分で 9 つの区分に分けます。
  配分の既定は、難易度が 3:5:2、種別が 75%:20%:5% です(`plan.difficultyMix`・`plan.typeMix`。試験ごとに上書きできます)。
- パイプラインで作る問題は、公開済みの問題に**足します**(置き換えません。[ADR 0012](./app/adr/0012-pipeline-adds-to-published-questions.md))。
- `data/questions.<コード>.json` を読み、公開済みの問題のうち、資格の分野に属するもの(データの検査が、問題の分野が資格マスタにあることを確かめるので、実際にはすべて)を既存の数に入れ、目標との差(足りない分)を、区分ごとに出します。難易度のない既存の問題は、`medium` として数えます。
  目標を満たす分野の不足は 0 で、その分野の分野・難易度・種別の項目も出ません(論点の枠の項目は、下のとおり別に出ます)。
- 計画はスキーマで検査してから書き出し、読み込むときにも検査します。報告は、分野ごとの目標・既存・不足の件数です(対象サービスの目標があるときは、下の対象サービスの報告も出します)。
- 計画の項目ごとに、下書きの根拠にできる事実カードの数を、`根拠の事実カード: <項目の ID> <分野か focus:枠の名前> <件数> 件` で報告します。根拠にできるカードは、通過で、再検証の印がなく、根拠の出典がどれも `active` で本文が変わっていないものです(下書きの依頼が候補にするカードと同じ範囲)。
  誤答は設計ごとに根拠が要り、根拠のない誤答の下書きは不採用になるので、目安として、1 つの項目に 4 件(正答と誤答 3 つ)を置き、届かない項目には `(不足。目安 4 件)` を付けます。止めません(カードの数が足りても、質が足りるとは限らないため)。報告は項目の ID、分野か枠の名前、件数だけで、主張の本文を載せません。
  台帳か事実カードを読めないとき、有効(`active`)で取得済み(本文のハッシュがある)の出典(試験ガイドを除く)が台帳にないときは、この報告を出しません(未処理の出典の検査と同じ条件です)。
- 試験ごとに、対象サービスの目標(`plan.overrides.<試験コード>.services`)を持てます。各サービスが出る問題の数の下限(`minPerService`)と、1 つのサービスが出る問題の割合の上限(`maxShare`)です(同じ場所の `minMultiServiceShare` は、点数票の束の警告にだけ使います。[点数票](./exam-style/scorecard.md) の「4」)。
  サービスの一覧は、台帳に取り込んだ試験ガイドの対象サービスの一覧(`guide.services`)を使います。目標は、計画の項目(分野・難易度・種別)を変えず、下書きの依頼で事実カードを選ぶ順に効きます(「3. 下書きの手順」)。
  目標と一覧がそろうと、plan は、公開済みの問題について、`対象サービスの目標`(一覧の件数、下限に届かない件数、上限を超える件数)、`下限に届かないサービス`、`上限を超えるサービス` を報告します。
  目標があって一覧がないときは、試験ガイドの取り込み直しを促す報告だけを出し、計画は作ります。判断の理由は [ADR 0018](./app/adr/0018-exam-guide-service-list-and-targets.md) にあります。
- 試験ごとに、論点の枠(`plan.overrides.<試験コード>.focus`)を持てます。分野の不足とは別に、決まった論点の問題を、決まった数だけ作るための項目です。
  枠ごとに、名前(`id`)、分野、難易度、種別(`single`・`multiple`)、作る数(`count`)、根拠にする出典の URL の接頭辞(`sourcePrefixes`)、問いの形の一言(`instruction`)を書きます。
  plan は、枠ごとに計画の項目を 1 つ足します(項目の ID は枠の名前から決まり、名前を変えると別の項目として数え直します)。数は枠の数のままで、分野の目標・既存・不足には数えません(分野の目標を満たしていても、枠の項目は出ます)。
  満たしたかは、ほかの項目と同じく、その項目の不採用でない下書きの数で見ます。資格マスタにない分野を書くと、出題計画の誤りで止まります。
  決まった問いの形がある論点は、出題計画の最初の実行の前に、枠に置きます(拾い方と、名前と一言を最初に決める理由は、[問題を作る手順書](./question-production.md)の「6.1 論点の枠を、最初から使う」)。

  ```json
  "focus": [{ "id": "maturity-level", "domain": "domain4", "difficulty": "medium", "kind": "single", "count": 5,
    "sourcePrefixes": ["https://docs.example.com/maturity-model/"], "instruction": "企業の現状を書き、いまどの段階かを選ばせる" }]
  ```
- 問題にサービスが出るかは、設問文と選択肢に、サービスの名前が出るかで数えます(文字列の一致による目安)。括弧の外の名前と括弧の中の略称のそれぞれについて、接頭辞(`Amazon `・`AWS `)のある形とない形を探します。
  大文字小文字は区別し、前後が英数字なら別の語の一部とみなします。長い呼び方を先に当て、当てた所で短い呼び方を重ねて数えません。1 つの問題で、同じサービスは 1 回だけ数えます。
- 事実カードをまだ抽出していない出典が残っていると、計画を書かずに「事実カードの未処理」(出典の URL と件数)を出し、終了コード 1 で止まります。
  見分け方は facts の依頼の段と同じで、取得済みの active な出典(試験ガイドを除く)のうち、今の本文と今の `fact-extractor` の定義で抽出済みでないものです。
  再試行の上限に達した出典は数えません(facts を繰り返しても減らないため)。facts は、「件数の上限」が出なくなるまで、依頼・抽出・取り込みを繰り返してから plan に進みます。
  本文がキャッシュにない出典(facts の「事実カードの本文なし」)は、facts を繰り返しても減りません。収集をやり直して本文をキャッシュに戻してから、facts を回します。
  台帳に取得済みの出典がなければ、この検査はしません。

## 3. 下書きの手順

1. **依頼を書く。** 通信も、モデルの呼び出しもしません。

   ```sh
   npm run pipeline -- draft <試験コード>
   ```

   計画の項目ごとに、依頼が書かれます。依頼には、分野、難易度、種別、書かせる数(設定 `draft.maxPerRequest` まで)、
   根拠にしてよい事実カード(通過したもので、再検証の印がなく、根拠の出典がどれも `active` で本文が変わっていないもの。下書きの根拠にされた回数の少ないものを先にし(人が却下した下書きと、直して置き換えた下書きの根拠も、回数に数える)、回数が同じものの間では、
   対象サービスの目標と一覧がそろうときは主張に下限に届かないサービスが出るもの(出るサービスがすべて割合の上限を超えるものは後ろ。数えるのは公開済みの問題と、不採用でない下書き)、根拠にされた回数の少ない出典のもの、確度の高いものの順に並べ、
   同じ出典のカードが続かないよう出典を 1 巡ずつ回して、`draft.maxFactsPerRequest` 件まで)、
   選択式では正答を置く記号(`answerPositions`。これまでの下書きで使われた回数の少ない記号の組を先に割り当てる)、
   適用するスタイル規則、結果を書く場所が入ります。同じ実行の依頼は、同じ分野でも先頭の事実カードが重ならないようにします。
   - `--domain=<分野のコード>`(例: `--domain=domain1`)を付けると、その分野の計画の項目だけに依頼を書きます。ほかの分野は見ないので、
     事実カードのない分野の `no-facts` で失敗になりません(未達の記録も、その分野の項目だけを置き換えます)。資格マスタにない分野は、入力の誤り(終了コード 2)です。
     `--import`・`--check`・`--review`・`--decide`・`--revise` には付けられません(これらは、全分野を対象にします)。
   - 論点の枠の項目(「2. 出題計画」)では、根拠の候補を、出典のどれかが枠の接頭辞で始まる事実カードに絞ります(分野は問いません。並べ方は同じ)。依頼には、問いの形の一言(`focus.instruction`)と、カードごとの先頭の出典のページと節(`facts[].source`。主張がページの主題を名前で書いていないときの文脈)を載せ、エージェントはその形で書きます。一言は依頼の鍵に入ります(一言を変えると、出し直します)。枠を持たない項目の依頼と鍵は変わりません。
   - 分野に根拠にしてよい事実カードがなければ、依頼を作らず、`下書きの誤り: no-facts <分野>` を出して終了コード 1 で終わります。論点の枠の項目で、範囲にカードがなければ `no-facts focus:<枠の名前>` です。
   - 1 回に出す依頼の数は、設定の `maxItemsPerRun` までです。超えると「件数の上限」を出します。再実行すると続きから進みます。
   - 同じ入力(計画の項目、書かせる数、出し直しの回数、事実カードの ID と主張、規則と依頼の版、エージェントの定義のハッシュ、人が却下した下書きの数、論点の枠の一言)の依頼は、取り込み済みなら再び出しません。
2. **下書きを書かせる。** Claude Code で、エージェント `question-drafter` に、依頼のファイルを 1 つずつ渡します(依頼ごとに別の起動にします)。
   エージェントは、依頼の `outputPath` に下書きを書きます。
3. **取り込む。**

   ```sh
   npm run pipeline -- draft <試験コード> --import
   ```

   書かれた下書きを、次の順に検査します。
   1. 出力の形、依頼との一致(資格・依頼の鍵・計画の項目)、数が依頼を超えないこと、依頼のあとに事実カードとエージェントの定義が変わっていないこと
      (事実カードが消えた、通過でなくなった、主張が変わった、再検証の印が付いた、根拠の出典が `active` でなくなったか本文が変わった。または定義の指示かモデルが変わった。直しの依頼では、直す前の下書きが保留でなくなった(「直し」)。どれかなら `request-stale` で依頼を捨て、次の依頼の段(`draft`、直しの依頼は `draft --revise`)で、必要なら作り直します。直しの依頼は、直す前の下書きが保留でなければ出ません)
   2. 種別が依頼と同じか、根拠の事実カードが依頼にあるか
   3. スタイル規則(止める規則に違反したら不採用)
   4. 誤答の検査(選択式だけ)
   5. データの契約への適合(問題の形に組み立てて、スキーマと検査規則で確かめる。誤答の設計の理由は、その選択肢の解説になる)
   6. 出典の本文の写し(設問文・選択肢と選択肢の解説・解説・補足・誤答の理由を、根拠の出典の本文と比べる。事実カードの主張と同じ検査。本文がキャッシュにないと確かめられないので、保留にする)
   7. 来歴を作れるか(事実カードが存在して通過していること、出典が台帳にあること)
   8. 重複の検出(公開済みの問題と、ほかの下書きと比べる。直した下書きは直す前の下書きと、書き直した下書きは書き直す元の問題の下書き(来歴でつながる下書き)とは比べない)

   取り込みのあとに、選択式の下書き(通過・保留)と公開済みの問題を合わせて、正解の偏りを数えます。正解の記号の分布と、択一で最長の選択肢が正解の問題の割合を、
   データの検査(`npm run validate:data`)と同じ指標としきい値(`packages/data-schema/src/exam-data/bias.ts`)で確かめ、超えたら `正解の偏り` を報告します。報告するだけで、取り込みは止めません。
4. **来歴を検査する。**

   ```sh
   npm run pipeline -- draft <試験コード> --check
   ```

   来歴の事実カードが存在して通過していること、出典が許可したドメインの https の URL で、その資格のベンダーのもので、根拠の事実カードの出典であることを確かめます。
   あわせて、来歴と台帳の今の状態を比べ、再検証が要るものを原因ごとの理由コードで失敗にします(`recheck-fact`・`source-changed`・`source-check-<検査の名前>` など。
   一覧は[出典の収集](./source-collection.md)の「5. 出典の本文が変わったときの再検証」)。
   **不採用でない下書きに来歴がなければ、先へ進めません**(`来歴なし`、終了コード 1)。検証の段階(下の「検証」)は、この検査を通った下書きだけを扱います。
5. **人が確かめる。** 要判断の下書き(通過・保留の下書き)を、すべて人が確かめます(人が却下した下書きも、確認済みとして表に載ります)。設定 `review.autoApprove` に挙げた試験では、人が判断しなくてよい下書きを要判断から外します(この手順の下の段落)。抜き取りに切り替えているときは、通過の下書きのうち選んだものを確かめます([問題を作る手順書](./question-production.md)の「8.1 抜き取りで確認する」)。

   ```sh
   npm run pipeline -- draft <試験コード> --review
   npm run pipeline -- draft <試験コード> --decide
   ```

   `--review` は、作業用の置き場に、確認用の表(`review.md`)と、判断を書き込むシート(`review-sheet.json`)を書きます。
   表は、下書きごとに、分野・難易度・種別、設問文、選択肢と正答(自由記述は観点と合格点)、解説、根拠にした事実カードの主張と節、検証役が読む根拠の節の場所(`検証の節`。出典の URL・節の名前・見出し)、出典の URL、保留・不採用の理由コード、警告、直した下書きなら直す前の下書きの ID(`直す前の下書き`)を載せます。取得した本文は載せません。
   検証の節の場所は、事実カードの先頭の出典から決まります(検証の依頼が節を切り出すのと同じ選び方)。確かめるときは、その URL の見出しの節を読み直します。
   シートの各行の `decision` に `approve`(承認)・`release`(保留の解除)・`reject`(却下)を、`reason` に理由コードを書き、`--decide` で[人の判断の記録](./human-decisions.md)に取り込みます。
   空の行は取り込みません。理由のない判断、知らない下書き、保留でない下書きの解除があると、行の番号と種類を出して、何も取り込みません。
   保留の下書きは、承認(`approve`)だけで、保留も解けます。解除(`release`)は、承認はまだせず、保留だけを解くときに使います(解除と承認を両方書く必要はありません)。
   `--review`・`--decide`・`--check` は、要判断の下書きの確認の済み(承認・却下)と未済の件数を報告します。
   設定 `review.autoApprove` に挙げた試験では、人が判断しなくてよい下書きを、要判断から外し、別の件数にします。基準を満たして承認を省ける下書き(書き出しの「基準で承認を省く」と同じ判定)、書き出し済みの下書き(通過した下書きで、来歴に問題 ID がある)、基準を満たすが来歴の検査で止まる下書き(人の承認では書き出せない)の 3 つです。
   表(`review.md`)は、要判断の下書きだけを節に並べ、外した下書きは冒頭に件数と ID だけを出します。判断のシートにも、要判断の下書きの行だけが載ります。
   外した下書きをあとから却下するときは、[人の判断の記録](./human-decisions.md)を直接直します。非公開の問題を書き直した下書きは、必ず要判断にします。書き出し済みでない下書きで、人の判断(承認・却下)がすでにあるものも、基準を満たしても外さず、要判断にします。
   `review.autoApprove` に挙げていない試験では、不採用でない下書きをすべて要判断にします(件数の行の、外した 3 つの件数は 0 件になります)。
   `review.autoApprove` に挙げた試験では、基準の判定に公開済みの問題を読むので、問題データが読めないときは、`--review`・`--decide`・`--check` が `問題データの誤り` を出して終了コード 1 で止まります(`--decide` は、判断を何も取り込まずに止まります)。
   人の確認を抜き取りに切り替えているときは、通過の下書きのうち選んだものだけが載ります([問題を作る手順書](./question-production.md)の「8.1 抜き取りで確認する」)。
6. **来歴と判断の記録をコミットする。** `packages/pipeline/provenance/` の来歴と、`packages/pipeline/decisions/` の人の判断の記録だけをコミットします(`/dev-commit`)。`pipeline-work/` の中身はコミットしません。

どのコマンドも `--dry-run` を受け付けます。書き込みをせず、検査と報告だけを行います。

### 検証

```sh
npm run pipeline -- verify <試験コード>            # 検証の依頼を書く
npm run pipeline -- verify <試験コード> --import   # 検証役の出力を、下書きの宣言と照合して取り込む
```

作る役(`question-drafter`)とは別の検証役(`question-verifier`。モデルは [ADR 0021](./app/adr/0021-pipeline-judge-role.md) の表)が、**根拠にした出典の節だけ**を読み、選択肢ごとの正誤を再導出して、下書きが宣言した正解と照合します。

1. **対象。** 不採用でなく、来歴のある下書き(通過と保留)です。保留の理由は問いません。検証で解けるのは `ambiguous:*` の保留だけで、`review:*` の保留は、検証が合格でも保留のまま残ります(人が解きます)。人の承認がある下書きも検証します。
2. **節を取り出す。** 下書きの根拠の事実カードの出典のアンカー(見出し)から、キャッシュの本文を切り出します。本文がキャッシュにない、見出しが本文にないときは、依頼を出さず、`検証の節なし: <下書きの ID> <理由>` を報告して止まります(終了コード 1。通す側に倒しません)。
3. **写しを先に落とす。** モデルを呼ぶ前に、下書きの設問文・選択肢・解説・誤答の理由・補足を、節の本文と比べます(試験ガイド・事実カードと同じ関数 `detectCopy`)。連続して一致する長さが 30 文字を超えるか、英語の本文を言い換えても残る数値とラテン文字の語の並び(8 個以上)が、本文の近い範囲(その語数の 4 倍以内)に同じ順でそのまま現れると、写しです。落ちた下書きは、依頼を出さず、`verify:copy` で不採用にし、本文を残しません。
4. **再導出の依頼。** 1 件につき 1 件(`check: rederive`)。載せるのは、設問文、選択肢(記号と文言)、根拠の節の本文だけです。**正解、解説、誤答の設計、事実カードの主張は載せません**。検証役は、選択肢ごとに「正しい / 誤り / 判定できない」を、根拠にした節の見出しと短い言い換えとともに返します。再導出は 1 回です。
5. **照合。** 宣言した正解は「正しい」、そうでない選択肢は「誤り」でなければなりません。食い違い、判定できない選択肢、根拠の見出しが節にないものは、保留です。一致すれば、解説の確認に進みます。
6. **解説の確認の依頼。** 再導出が一致した下書きだけに、別の依頼(`check: explanation`)を出します。解説は正解を示すので、再導出と同じ依頼に入れると、再導出が独立でなくなるためです。ここで初めて、正解と解説を載せます。見るのは、解説が節と食い違わないか(`explanation-conflict`)、誤答の理由が正しいか(`reason-wrong`)、節にある適用範囲や条件を超えた断定がないか(`overclaim`)の 3 点です。指摘は、場所(`explanation`、`choices.B.explanation`、`distractors.C.reason`)とともに残します。指摘があれば保留です。
7. **判定。** 合格・保留・不採用の 3 つで、複数の理由があるときは重い判定(不採用、保留、合格の順)を採り、理由コードはすべて残します。

検証役の 1 回の起動には、同じ `check` の依頼を、設定の `verify.bundleSize` の数まで(束)渡せます。束は、`verify <試験コード> --bundles` が、出力がまだない依頼を `check` ごとに区切って表示します(読むだけ)。出し直しの回数が設定の `verify.maxAttempts` に達した依頼と、依頼のあとに検証役の定義が変わった依頼は、束に入れず、件数だけを報告します。依頼のファイルと出力は、束にしても依頼ごとで、取り込みも依頼ごとです。再導出の依頼と解説の確認の依頼は、同じ束に入れません(解説の確認の依頼は正解を載せるため)。検証役は、依頼ごとに、その依頼の節だけを根拠に判定します。束の途中で止まったときは、出力のある依頼だけが取り込まれ、出力のない依頼は待ちのまま残ります(`検証の出力なし`)。残った依頼は、別の束にして起動し直します。

判定は、下書きの状態(`drafts.json`)の `verification` に残します。持つのは、判定、理由コード(`verify:<コード>`)、指摘の場所、検査(再導出・解説・写し)ごとの結果と選択肢ごとの判定の分布、根拠の節と下書きの内容のハッシュ、検証役の定義(役・モデルの ID・ハッシュ)だけで、本文の写しは持ちません。
`verification` がない `passed` が検証前、`verdict` が `pass` のものが、検証を通った合格です。`verdict` が `null` は、再導出は合格で、解説の確認待ちです。保留は `status` を `held` に、不採用は `rejected`(本文は持たない)にします。
同じ入力(下書きの内容、節、検証役の定義)では、依頼を出し直しません。下書きの内容(設問文、選択肢、正解、解説、誤答の設計)、節、定義のどれかが変わると、検証をやり直します。

- 自由記述の下書きは、選択肢の正誤を再導出する形が使えないので、モデルを呼ばず、`verify:free-text-unchecked` で保留にします。人が確かめて承認すれば、書き出せます。
- 検証の判定が保留で、人が承認した下書きは、人の判断を優先して書き出せます。不採用は本文を持たないので、承認しても書き出せません。検証をしていない下書きも、承認があっても書き出せません。
- 人の確認を抜き取りにしているときは、確認しないと記録した、検証が `pass` の下書きは、承認なしで書き出せます([問題を作る手順書](./question-production.md)の「8.1 抜き取りで確認する」)。
- 出力の形が違う、依頼と合わない場合は、`draft` と同じく、回数の上限(設定の `verify.maxAttempts`)まで出し直します。依頼のあとに検証役の定義、下書き、根拠の節が変わったときは、出力の形を見る前に `request-stale` で依頼を作り直します。

### 直し(ブラッシュアップ)

```sh
npm run pipeline -- draft <試験コード> --revise   # 直しの依頼を書く
# エージェント(question-reviser)が、依頼ごとに直した下書きを書く
npm run pipeline -- draft <試験コード> --import   # 直した下書きを、新しい下書きとして取り込む
```

保留になった下書きを、0 から作り直さずに、ブラッシュアップ役(`question-reviser`。モデルは [ADR 0021](./app/adr/0021-pipeline-judge-role.md) の表)に直させます。

- **対象**: 保留の選択式の下書きで、人の判断(承認・解除・却下)がまだないもの。人が却下した下書き(本文を持たない)と、自由記述(再導出の形で検証できず、保留が直しでは解けない)、写しを確かめられない保留(`review:copy-unchecked`。本文のキャッシュを戻して作り直さないと解けない)は対象にしません。作り直すときは、通常の `draft` の依頼で行います。
- **依頼**: 保留の下書きごとに 1 件で、書かせる数は 1 です。依頼の `revise` に、直す下書きの本文、保留の理由コード、検証の指摘(理由コードと場所)、根拠の節の場所(出典の URL・節の名前・見出し。本文は載せない)が載ります。
  `facts` には、元の下書きの根拠の事実カードを先に、続けて周辺の事実カード(同じ分野の使えるカードを、元の根拠と同じ出典のもの、同じ出題範囲の項目のもの、それ以外の順に、それぞれ根拠にされた回数の少ないもの、ID の順)を、`draft.maxFactsPerRequest` 件まで載せます。
  正答の位置(`answerPositions`)は、元の下書きのものを保ちます。元の根拠の事実カードが使えなくなった下書きは、依頼しません(`直しの保留: <下書きの ID> fact-not-usable`、終了コード 1)。
- **鍵**: 通常の依頼と同じ材料に、直す下書きの ID を足して決まります。取り込み済みの鍵は、再び依頼しません。
- **取り込み**: 直した下書きは、新しい下書きとして、通常の下書きと同じ検査(スタイル規則、誤答、データの契約、写し、来歴、重複)を通ります。重複の検査では、直す前の下書きとは比べません。
  直した下書きの記録には、直す前の下書きの ID(`revisionOf`)を残します。直した下書きが不採用でなければ、直す前の下書きは不採用(理由 `revised`)になり、本文と来歴を持たなくなります(`直しの取り込み: <直す前の ID> → <直した ID>`)。直した下書きが不採用なら、直す前の下書きは保留のまま残ります。
  設問文と根拠の事実カードを変えない直し(解説や選択肢だけの直し)は、下書きの ID が直す前と同じになります。このときは、直す前の下書きの記録を、直した内容で置き換えます(`直しの取り込み: <ID>(同じ ID で置き換え)`。検証の結果は持たないので、検証からやり直します。`revisionOf` は持ちません)。
  理由 `revised` は欠陥による不採用ではないので、理由の集計(`reasons`)に入れません。
  依頼のあとに、直す前の下書きが保留でなくなった(人が判断した、ほかの直しで置き換わった)ときは、取り込まずに `request-stale` で依頼を捨てます。直しの依頼は、出し直しの回数(`state.rounds`)に数えません。
- **論点の枠の下書き**: 論点の枠の項目の下書きは、直しの依頼の対象にならないことがあります。直しの依頼は、周辺の事実カードを、下書きの分野の使えるカードに絞ります。根拠に、枠の分野と別の分野のカードを含む下書きは、依頼されず、`直しの保留: <下書きの ID> fact-not-usable`(終了コード 1)になります。
  保留になった枠の下書きは、人が却下して、通常の `draft` の依頼で作り直します。終了コードが 1 のまま残る点は、来歴のない問題の書き直し(下の「書き直し(非公開の問題)」)と同じ扱いです。
- **人の判断**: 直す対象は、人の判断がまだない下書きだけです。直した下書き(同じ ID で置き換えたものを含む)を、検証からやり直し、人が確かめます。
  直した下書きが不採用になった(直す前の下書きは保留のまま)、または同じ ID のまま再び保留になったときは、同じ入力の直しの依頼は出し直しません(取り込み済みの鍵)。人が承認か却下を判断するか、通常の `draft` の依頼で作り直します。
  別の ID になった直した下書きが再び保留になったときは、それ自体が新しい直しの対象になります(直す下書きの ID が変わるので、鍵も変わります)。
- **根拠の事実カードの扱い**: 本文を持たなくなった下書き(人の却下、直したことによる置き換え)は、根拠にした事実カードの ID だけを残します(`factIds`)。補充の依頼で事実カードを選ぶとき、この ID も根拠にされた回数に数えるので、同じカードが使われていない扱いに戻って、再び先に選ばれることはありません。

### 書き直し(非公開の問題)

```sh
npm run pipeline -- draft <試験コード> --rewrite   # 書き直しの依頼を書く
# エージェント(question-reviser)が、依頼ごとに書き直した下書きを書く
npm run pipeline -- draft <試験コード> --import    # 書き直した下書きを、元の問題の ID を持つ下書きとして取り込む
```

非公開のファイル(`data/unpublished.<コード>.json`。[データの仕様](./data-spec.md)の「13. 非公開の問題」)の問題を、同じ内容のまま質を上げて書き直します。役は直しと同じブラッシュアップ役(`question-reviser`)です。
決まりの理由と、ADR 0019 の直し(`revisionOf`)との関係は [ADR 0023](./app/adr/0023-rewrite-unpublished-questions.md) です。公開に戻す作業は、[問題を作る手順書](./question-production.md)の「7.7 書き直して公開へ戻す」(`restore`)です。

- **対象**: 非公開のファイルで、判定が `rewritable` の選択式の問題。判定が `unpublish` の問題と、自由記述は対象にしません。すでに書き直しの下書きがある問題(不採用でないもの)は、さらに依頼しません。人が却下して不採用になったときは、新しい依頼で書き直せます(依頼の鍵に、人が却下した数が入ります)。取り込みの検査で不採用になった下書きは、同じ入力では依頼し直さず、入力(本文、事実カード、役の定義)が変わって鍵が変わったときだけ、再び依頼されます。
- **依頼**: 問題ごとに 1 件で、書かせる数は 1 です。依頼の `rewrite` に、現行の本文、判定の理由コード、元の根拠の事実カードの ID(`factIds`)、根拠の節の場所が載ります。
  `facts` は、元の根拠の事実カードを先に、続けて周辺の事実カードを、直しと同じ選び方で載せます。正答の位置と難易度は、元の問題のものを保ちます(難易度がなければ `medium`)。
  元の根拠は、来歴(`packages/pipeline/provenance/<コード>.json`)の、その問題の ID を持つ項目から引きます。来歴がない問題(`書き直しの保留: <問題の ID> no-provenance`)と、元の根拠の事実カードが使えなくなった問題(`fact-not-usable`)は、依頼せず、終了コード 1 にします。
- **鍵**: 通常の依頼と同じ材料に、問題の ID、現行の本文のハッシュ、その問題の書き直しの下書きを人が却下した数を足して決まります。
- **取り込み**: 通常の下書きと同じ検査(スタイル規則、誤答、データの契約、写し、来歴、重複)を通ります。重複の検査では、書き直す元の問題の下書き(来歴でその問題の ID につながる下書き)とは比べません(同じ問いを書き直したものなので、似ているのが当然なため)。計画の項目は持たないので、問題の ID から決めた項目の ID を使います。
  さらに、元の問題と、**分野・出典の URL の集合・論点**が同じであることを機械で比べます。違うものは不採用にします(`rewrite:domain-changed`・`rewrite:references-changed`・`rewrite:topic-changed`)。論点は、根拠の事実カードの、分野と出題範囲の項目の組の集合です。
  元の問題が非公開のファイルにない、または元の根拠の来歴がないときは、`rewrite:original-missing` で不採用にします。
  下書きの記録には、元の問題の ID(`rewriteOf`)を残します。`revisionOf` は持たず、元の問題は非公開のファイルに残ります(復帰まで変えません)。
  依頼のあとに、元の問題が非公開のファイルから消えた・本文が変わった・判定が変わった、またはほかの書き直しの下書きが生きているときは、`request-stale` で依頼を捨てます。
- **論点の枠の問題**: 書き直しの依頼も、候補にする事実カードを、問題の分野の使えるカードに絞ります(直しと同じ)。根拠に別の分野のカードを含む問題は、`書き直しの保留: <問題の ID> fact-not-usable`(終了コード 1)になります。
- **直し**: 書き直しの下書きが保留になったときは、通常の `draft --revise` で直せます。直した下書きも `rewriteOf` を引き継ぎ、同じ内容かの比較を受けます。
- **検証・人の確認・判定**: 検証(`verify`)は下書きと同じです。人の確認は、抜き取りの対象にせず、必ず確認します(確認の表に、書き直す問題の ID が載ります)。
  判定(`judge`)は、検証を通った書き直しの下書きを、元の問題の ID で、公開の問題と一緒に判定します。
- **書き出しとの関係**: 書き出し(`export`)は、書き直しの下書きを対象にしません(採番しません)。公開へ戻すのは `restore` です。

### 理由の集計

```sh
npm run pipeline -- reasons <試験コード>
```

不採用と差し戻しの理由を集計し、下書きの指示(`.claude/agents/question-drafter.md` など)の改善に使える形で書き出します。元の記録(`data/`、コミットする台帳、下書きの置き場、人の判断の記録)は変えず、集計を作業用の置き場にだけ書きます。

- 入力は、事実カードの台帳、下書きの置き場(`drafts.json`)、人の判断の記録の 3 つです(判定の記録は事実カードの台帳と下書きの置き場、レビューの記録は人の判断の記録)。記録が空でも、エラーにならず、空の集計を返します。
- **段階**は、事実カード(`facts`)、下書き(`draft`)、検証(`verify`。`verify:` で始まる理由)、人の確認(`human`。人の却下 `human-rejected`)です。**割合**は、その段階で判定された件数に対する割合です。
- 理由コードごとに、件数、割合、保留と不採用の内訳、論点(分野)ごとの件数、ID(昇順で 20 件まで)を出します。論点ごとの保留・不採用の件数と、人の判断(承認・解除・却下)の理由コードごとの件数も出します。出典の受け入れ(`accept`)は、不採用や差し戻しではないので、集計に含めません。
- 各理由コードに、**意味、よくある不採用の型、指示に足すとよい制約の候補**を添えます(`packages/pipeline/src/reasons/catalog.ts`。この文書の理由コードの表のコードは、すべて載せています。載っていないコードは、接頭辞(`style:` など)の一般的な説明になり、接頭辞にも当たらなければ「説明なし」になります)。
- 出力に、問題の本文・選択肢・出典の本文は含めません。ID と件数、理由コード、固定の説明文だけです。
- 結果は `pipeline-work/reasons/<コード>/summary.json`(機械が読む形)と `summary.md`(人が読む形)に書きます(コミットしない)。下書きの指示を直す人(とメインのセッション)が `summary.md` を読み、よく出る理由コードの「指示に足すとよい制約の候補」を、指示に足すかを判断します。エージェントが自動で読む仕組みは持ちません。指示(エージェントの定義)の書き換えは、通常の PR で、人の確認を経ます。

### 書き出し

人が承認し(`approve`)、来歴の検査を通り、検証を通った下書きを、公開データに追加します(ADR 0020)。抜き取りで確認しないと記録した下書きは、承認の代わりに、記録と検証の `pass` を条件にします。設定 `review.autoApprove` に挙げた試験では、基準を満たした下書きも、承認なしで書き出します(下の「基準で承認を省く」)。

```sh
npm run pipeline -- export <試験コード>
```

- 対象は、通過で、承認の記録があり、検証を通った(`verification.verdict` が `pass`、または検証が保留で人が承認した)もので、来歴があり、来歴の検査(再検証の印と出典の状態を含む)を通り、まだ書き出していない下書きです。承認のない下書きは書き出しません(承認待ちに数えます。抜き取りで確認しないと記録した、検証が `pass` の下書きと、基準を満たした下書きを除きます)。検証を通っていない下書きも書き出しません(検証前・検証で止まったものに数えます)。
- **基準で承認を省く**: 設定 `review.autoApprove` に挙げた試験では、次の基準をすべて満たした選択式の下書きを、人の承認なしで書き出します(`export/criteria.ts`)。満たさない下書きは、これまでどおり承認が要ります。非公開の問題を書き直した下書きは、この対象にせず、必ず人が確かめます。人が却下した下書きは書き出しません。
  (1) 検証役の判定が合格(`pass`)。(2) 点数票の問題 1 問の得点が合格点以上で、止める項目(A2 の不一致・A5)の違反がない。(3) 対象サービスの目標があるとき、出るサービスがすべて割合の上限を超えるものではない(数えるのは公開済みの問題と、検証が合格の選択式の下書き。台帳に対象サービスの一覧がなければ、どの下書きも満たさない)。
  書き出しの報告の末尾に、追加のうち基準を満たして承認なしで書き出した件数を出します。
- 問題の形に組み立て、出典(`references`)には、来歴の出典の URL と、台帳にあるその URL の題を付けます(許可したドメインの https、同じ URL は重ねない、10 件まで)。台帳に題がない出典は、題なしで書き出し、`題が取れない出典` として報告します。あとから、`collect <試験コード> --titles` で台帳に題を足し、`export <試験コード> --titles` で、題のない出典に題を足します(同じ URL の題は、すでにあるものにそろえます)。誤答の設計の理由は、その選択肢の解説になります。
- 問題 ID は、資格マスタの `idPrefix` で、今の問題・退役した ID(`retiredQuestionIds`)・書き出し済みの来歴の ID を含めた最大の番号の次から、連番で採番します。
- 作業ツリーの `data/questions.<コード>.json` に追加の分だけを書き、ほかの問題は変えません。整形は Biome でそろえます。書いたあとにデータの検査を通し、失敗したら書き出し前に戻して、終了コード 1 で終わります(`データの検査の失敗`)。
- 書き出した問題の ID を、来歴の `questionId` に書き戻します。書き出し済みの下書きは、再び書き出しません。
- 差分レポートを、作業用の置き場(`pipeline-work/export/<コード>/report.md`)に書きます。追加の件数、分野別の件数、根拠にした事実カードの数、出典のドメイン別の数、保留・不採用の件数と理由の種類だけで、本文は載せません。
- 書き出したら、`data/` の差分と差分レポートを人が確かめ、来歴・判断の記録と一緒に、通常の PR で取り込みます。`--dry-run` では、追加する件数だけを報告します。

## 4. 判定と理由コード

取り込んだ下書きは、次のいずれかになります。報告は、下書きの ID、理由コード、場所、相手の識別子、類似度だけで、本文は出しません。

| 判定 | 意味 | 先へ進めるか |
| --- | --- | --- |
| 通過(`passed`) | すべての関門を通った | 進める |
| 保留(`held`) | 人または検証役が確かめる必要がある | 確かめるまで進めない |
| 不採用(`rejected`) | 関門に落ちた。本文は保存しない(ID と理由コードだけ。人の却下と、直して置き換えた下書きは、根拠の事実カードの ID も残す) | 進めない |

| 理由コード | 判定 | 内容 |
| --- | --- | --- |
| `kind-mismatch` | 不採用 | 種別が、依頼と違う |
| `fact-not-in-request` | 不採用 | 根拠の事実カードが、依頼にない |
| `style:<規則>` | 不採用 | 止めるスタイル規則に違反した([スタイルガイド](./question-style.md)) |
| `distractor:<コード>` | 不採用 | 誤答の設計がない、理由や根拠が足りない |
| `scope:out-of-scope-subject` | 不採用 | 試験ガイドが対象外と示すサービスが、設問文か正答の選択肢に出る(範囲の検査。台帳に試験ガイドの対象外サービスの一覧があるときだけ。[ADR 0024](./app/adr/0024-scope-check-by-exam-guide-service-lists.md)) |
| `provenance:<コード>` | 不採用 | 来歴を作れない(`fact-not-found`・`fact-not-passed`・`source-not-in-ledger`) |
| `data-invalid:<場所>` | 不採用 | 問題データに組み立てると、データの契約に合わない。場所は、項目の名前と番号をハイフンでつないだもの(例: `rubric-passing-points`、`choices-0-key`。全体なら `root`。値は含めない) |
| `long-copy` | 不採用 | 設問文・選択肢・解説・誤答の理由が、根拠の出典の本文を長く写している |
| `review:copy-unchecked` | 保留 | 根拠の出典の本文がキャッシュになく、写しを確かめられない(人が出典の本文と照らして確かめる。機械の検査をやり直すときは、収集をやり直してから、下の「下書きをやり直すとき」の手順で作り直す) |
| `duplicate:similar-existing` / `duplicate:similar-draft` | 不採用 | 設問文が、公開済みの問題 / ほかの下書きとほぼ同じ |
| `ambiguous:similar-to-correct` / `ambiguous:supported-by-fact` | 保留 | 正答が複数になりうる誤答の候補(検証の再導出が宣言した正解と一致し、解説の確認にも合格すると、保留が解ける。一致しなければ保留のまま) |
| `verify:answer-mismatch` | 保留 | 検証役が節から再導出した結果、宣言した正解の選択肢が正しくない |
| `verify:distractor-correct` | 保留 | 誤答とした選択肢が、節では正しい |
| `verify:undetermined` | 保留 | 節だけでは判定できない選択肢がある |
| `verify:evidence-not-found` | 保留 | 判定の根拠の見出しが、節にない |
| `verify:explanation-conflict` / `verify:reason-wrong` / `verify:overclaim` | 保留 | 解説が節と食い違う / 誤答の理由が誤り / 適用範囲や条件を超えた断定(場所は `verification.findings`) |
| `verify:free-text-unchecked` | 保留 | 自由記述は、再導出で検証できない(人が確かめる) |
| `verify:copy` | 不採用 | 下書きが、根拠の節の本文を写している(依頼を出さずに落とす) |
| `review:similar-existing` / `review:similar-draft` | 保留 | 設問文が、公開済みの問題 / ほかの下書きに近い |
| `review:topic-existing` / `review:topic-draft` | 保留 | 論点が同じ(同じ事実カードの組か、同じ正答の組で、設問文が少し似ている) |
| `revised` | 不採用 | 直した下書き(ブラッシュアップ役の出力)に置き換わった。欠陥による不採用ではないので、理由の集計に入れない(「直し」) |
| `rewrite:domain-changed` / `rewrite:references-changed` / `rewrite:topic-changed` | 不採用 | 書き直した問題の分野 / 出典の URL の集合 / 論点が、元の問題と違う(「書き直し(非公開の問題)」) |
| `rewrite:original-missing` | 不採用 | 書き直しの元の問題が、非公開のファイルにない、または来歴がない |

範囲の検査の警告(下書きは止めない。場所だけを持ち、サービスの名前は持たない): `scope-out-of-scope-distractor`(対象外のサービスが誤答の選択肢だけに出る。誤答の作り方として自然な場合がある)、`scope-unlisted-service`(対象にも対象外にもない、「Amazon」か「AWS」で始まるサービスらしい名前が出る。場所は、出た所が設問文なら `questionText`、選択肢だけなら `choices`。一覧の抽出漏れか新しい名前かを人が確かめる。対象サービスの一覧があるときだけ)。

`similar-existing` の比べる相手は、公開済みの問題のすべてです(足す方針のため、公開済みの問題を相手から外しません)。

取り込みを止める理由コード(出力のファイルを捨てて、失敗の回数を 1 増やします): `output-invalid`(形が違う)、`request-mismatch`(依頼と違う)。
`request-invalid`(依頼のファイルが壊れている)と `request-stale`(依頼のあとに事実カードかエージェントの定義が変わった。直しの依頼では、直す前の下書きが保留でなくなった。依頼を捨て、次の依頼の段で、必要なら作り直す)は、回数に数えません。
データの契約(`packages/data-schema`)に合わない下書きは、出力ごとは止めず、その下書きだけを不採用にします(上の表の `data-invalid:<場所>`)。

下書きの形の上限は、採点基準の観点名とキーワードの長さだけ、データの契約と同じ値を使います(`packages/pipeline/src/contract.ts` が、データの契約の定数をそのまま渡します)。
それ以外の上限(設問文・解説の長さ、誤答の設計の数など)は、データの契約に上限がない項目に、下書きの側で置く値です(同じ項目に上限があるものは、同じ値です)。下書きの形を通っても、データの契約の検査(本文に URL を含まない、など)に落ちたら `data-invalid` で不採用になります。

- 止めた出力は、理由を添えて、同じエージェントに書き直させます。やり直せる回数は、依頼ごとに設定の `draft.maxAttempts` までです。
  超えると、`再試行の上限` を出し、その依頼を出さなくなります(終了コード 1)。
- 1 つの依頼の下書きが**すべて不採用**になったときは、同じ計画の項目の依頼を出し直します。出し直せる回数は、設定の `draft.maxRounds` までです。人の却下は、この回数に数えません(却下で足りなくなった分は、依頼の鍵が変わって依頼し直されます。「下書きをやり直すとき」)。
- 依頼を書く実行は、満たせなかった計画の項目の理由を、状態のファイルの `unmet` に、計画の項目の ID と理由コードだけで残します
  (`no-facts`: 根拠にしてよい事実カードがない、`max-attempts`: 依頼の鍵ごとの `draft.maxAttempts` を超えた、`max-rounds`: 計画の項目ごとの `draft.maxRounds` を超えた)。
  報告も `再試行の上限: <計画の項目> max-attempts` のように、2 つの上限を分けて出します。
  次の実行は、はじめに `前回の未達: <計画の項目> <理由コード>` を報告し、その実行の判定で記録を置き換えます(解消した項目と、計画にない項目は外れます。
  件数の上限で見なかった項目は、前の記録を残します)。`request-invalid` と `request-stale` は、失敗の回数に数えず、未達の理由にも記録しません。
- 重複のしきい値は設定の `draft.similarity` です。設問文の類似度(文字の 2 つ組の Dice 係数)が `duplicate`(既定 0.85)以上なら不採用、
  `hold`(既定 0.6)以上なら保留です。論点が同じ候補は、設問文の類似度が 0.3 以上のときに保留にします。
- 設問文は、末尾の決まり文句(「最も適切なものはどれですか。」「2 つ選択してください。」など)を外してから比べます
  (`packages/pipeline/src/draft/similarity.ts` の `stemSimilarity`)。多くの設問に共通する言い回しで、論点の違う設問が似て見えないようにするためです。
  決まり文句を残すと、論点の違う短い設問どうしでも、保留のしきい値を超えることがあります。言い換えただけの設問は、外したあとも重複の高さに残ります。
  しきい値を変える前に、公開済みの問題どうしの類似度の上位の組を見て、本当に同じ論点かを確かめます([失敗の記録 0009](./app/lessons/0009-strip-stem-boilerplate.md))。

### 下書きをやり直すとき

下書きの依頼の鍵は、計画の項目、書かせる数、出し直しの回数、事実カード、規則と依頼の版、エージェントの定義のハッシュ、計画の項目の人が却下した下書きの数、論点の枠の項目では問いの形の一言で決まります。
人が却下した数は、1 件以上のときだけ鍵に入ります(却下のない項目の鍵は、この材料がなかったときと同じで、取り込み済みの依頼は出し直しになりません)。
人が下書きを却下すると、その項目の鍵が変わるので、次の `draft` で、足りない分の依頼が出ます。作業用の置き場を消す必要はありません。
却下した下書きの根拠の事実カードは、根拠にされた回数に数えたままにするので、足りない分の依頼では、使われていないカードが先に選ばれます(「直し」の「根拠の事実カードの扱い」)。
人の却下は、出し直しの回数(`draft.maxRounds` の上限に数える回数)に数えません。出し直しの回数が増えるのは、取り込みで全件が機械的に不採用になったときだけです。
指示(`.claude/agents/question-drafter.md` の本文)かモデルを直すと鍵が変わるので、取り込み済みの入力も、次の `draft` で依頼し直されます(定義の説明文だけを直しても変わりません)。
依頼のファイルには、役の名前・モデルの ID・定義のハッシュ(`agent`)が書かれ、取り込んだ下書きの状態(`drafts.json`)にも同じ記録が残ります(指示の本文は残しません)。
依頼のあとに定義が変わったときは(出力の形を見る前に判定します)、`--import` は出力を取り込まず `request-stale` で依頼を捨てます(失敗の回数には数えません)。`agent` の記録がない古い依頼も、同じく捨てます。
すでに取り込んだ下書き自体は、定義を変えても消えません。作り直すときは、次のようにします。

1. 作業用の置き場の `pipeline-work/draft/<コード>/` を消します(下書き、状態、依頼、出力が消えます)。
2. 来歴(`packages/pipeline/provenance/<コード>.json`)から、消した下書きの項目を消します(消さないと、もう下書きのない来歴の項目が残ります)。
3. `draft <試験コード>` から、手順をやり直します。

## 5. レビューの観点

保留の下書きと、警告の付いた下書きを、人が確かめます。見るものは次のとおりです。

- **根拠との対応**: 設問文と正答が、根拠の事実カードの主張だけで言えるか。主張にないことを足していないか。
  事実カードの出典を開いて、主張が本文と合っているかも確かめます(事実カードの抜き取りの見かたは[事実カードの作法](./fact-cards.md)の「4. レビューの観点」)。
- **誤答の理由**: 誤答ごとの理由が、設問文の条件のもとで本当に誤りになっているか。根拠の事実カードや適用範囲の言い表しが、理由と合っているか。
- **曖昧さ**: 誤答が、条件によっては正しくなりうるか(保留の `ambiguous:*`)。設問文に条件を足せば解消できるか、誤答を差し替えるべきか。
- **重複**: 保留の相手(公開済みの問題の ID か、下書きの ID)と、同じ論点を問うていないか。同じ論点なら、どちらかを捨てるか、観点を変えます。
- **版・リージョンの適用範囲**: 事実カードの適用範囲(`scope`)と、設問文が言う範囲が合っているか。特定の版やリージョンの話を、一般の話のように書いていないか。
- **自由記述**: 観点が主張の要素に対応しているか。キーワードが広すぎて、無関係な回答にも当たらないか。合格点が妥当か。

保留の下書きは、人が確かめるまで先へ進めません。確かめた結果は、[人の判断の記録](./human-decisions.md)に、下書きごとに
`release`(保留を解いて通過にする)、`approve`(承認)、`reject`(却下)で書きます。次に `draft` を実行したとき(どのモードでも)に反映されます。

## 6. 規約

- 環境固有の値、個人情報、機密を、下書きにも、依頼にも、報告にも書きません。
- 公式の文書の本文を、下書きに写しません。
- モデルを呼ぶのは、エージェントだけです。CLI は、依頼の用意と、出力の検査・取り込みだけを行います。
- `data/` の問題データは、書き出し(`export`)で追加の分を書くほかは、公開と非公開のあいだの移動(`unpublish`・`restore`)だけが書きます。既存の問題の本文は書き換えません(書き直しは、非公開のファイルの問題を別の下書きにして行い、`restore` は、その下書きの本文を同じ ID の問題として公開へ戻します)。
